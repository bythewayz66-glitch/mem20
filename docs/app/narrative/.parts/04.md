### 7.2 The second pass: 177 members

The 14 November entry is the larger one, and it states the rule that drove it:

> **Rehoming complete (extended):** All long `mem20*z` subsystems (`name length > 15`) absorbed into
> short runtimes (`len < 15`) with full trees copied into `<target>/absorbed/<member>/`, member
> READMEs appended to target READMEs, tests copied to `<target>/tests/absorbed/<member>/` (and
> `pkg_tests` where applicable), originals deleted. 177 members rehomed across rounds (87+42+45+3) +
> 1 stale pycache-only remnant removed (`mem20versioncontrollargeassetandrecoverypipelinez`, source
> already in `mem20pipez/pipes/...`). **0** long standalone `mem20*z` dirs remain (short runtimes 56,
> `mem20benchmarkz` len==15 unchanged). No symlink compatibility shims.

The rule is a name-length rule: any subsystem whose directory name is longer than fifteen characters
is absorbed into a runtime whose name is shorter. 177 members, in four rounds of 87, 42, 45 and 3.

That is an extraordinary criterion for a refactor, and it is worth being clear about what it is and
is not. It is not an architectural principle — there is no reason a fifteen-character boundary
corresponds to a module boundary. It is a *mechanical* rule, chosen because it can be applied without
judgement, and its virtue is that it is checkable: after the pass, `0` long standalone directories
remain, and that is a fact you can verify with `ls`.

The cost is recorded honestly in the same entry:

> **Import compatibility:** Added `mem20_absorbed.py`, `_mem20_absorbed_finder.py`,
> `.mem20-absorbed-map.json`, and venv `.pth` (`.venv/lib/python3.13/site-packages/_mem20_absorbed.pth`)
> to resolve `mem20<member>z` imports to canonical absorbed locations (177 mapped; 39 multi-target).

So the refactor required a custom import finder, a JSON map of 177 entries with 39 members mapping to
more than one target, and a `.pth` file in the virtualenv. That is the price of moving 177 packages
without breaking every import in the estate, and it is a price the entry does not hide.

### 7.3 What the finder broke, and how

The failures corpus records the consequences, and they are exactly what a custom import finder
predicts:

> **Broken imports after symlink removal (resolved):** Removing top-level symlinks for absorbed
> members left old `mem20<member>z` import paths unresolved. Fixed by adding
> `_mem20_absorbed_finder.py` + `.mem20-absorbed-map.json` and venv `.pth` for canonical resolution;
> bootstrapped in MCP/gateway.

And then, on 21 November — the last day of the window — the finder itself is found to be broken in a
clean checkout:

> `_mem20_absorbed_finder.py`: resolve the absorbed map relative to the checkout instead of the
> hard-coded `/opt/mem20`, and rebase recorded absolute paths onto this root. Without it every
> absorbed member failed to import and the ecosystem probe reported 0 peers.

That is the single most instructive failure in the window, and it deserves its own treatment.

> **What broke.** The import finder that made the 177-member consolidation possible resolved its map
> against a hard-coded absolute path, `/opt/mem20`. On the machine where the consolidation was
> performed, that path existed and everything worked. In a clean checkout anywhere else, every
> absorbed member failed to import and the ecosystem probe reported **0 peers** — a number that looks
> like a measurement and is actually an absence.
>
> **What we learned.** A refactor that requires a custom resolver has moved the failure mode from
> "the import is wrong" to "the resolver is wrong," and the second is much harder to see because it
> fails silently and plausibly. `0 peers` is not an error; it is a valid probe result. The only thing
> that distinguishes "this subsystem has no peers" from "this subsystem's peers could not be
> imported" is knowing that it should have peers — which is exactly the knowledge a clean checkout
> does not have. **A resolver must be rooted in the thing it is resolving, not in the machine it was
> written on.** The fix is one line of path arithmetic; the cost of not having it was a probe that
> reported a confident zero for an unknown number of days.
