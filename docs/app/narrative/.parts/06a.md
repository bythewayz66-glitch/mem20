*"The subtotals were correct, which is exactly why it survived a read-through"* is the most useful
sentence in the corpus. A document whose parts are right and whose total is wrong is a document that
rewards careful reading with a false confirmation.

The second is the decimator that refused:

> **2026-09-27 — QEM, second attempt: refused rather than shipped broken**
> - **Decision:** `decimate` defaults to `cluster`, the only method measured to preserve the surface
>   (watertight, 0 degenerate, 0 non-manifold). `method: "qem"` refuses with that reason rather than
>   returning a larger mesh. A decimator that hits its triangle count while destroying the shape is
>   worse than a simpler one that preserves it, and one that returns 278% of the input is not a
>   decimator at all.

A decimator that returns 278% of its input is a function that has failed and reported success. The
refusal is the correct behaviour, and it is recorded as a decision rather than a bug.

The third is the exporter that was one off:

> **2026-09-25 — OBJ exporter wrote every face index one too high**
> - **Actual error:** my own importer rejected kiln's export with "face references vertex 275 but
>   only 274 vertices exist". Blender accepted the file anyway.
> - **Cause:** `int base = 1;` combined with writing `base + v + 1`, so the first mesh's indices
>   started at 2 instead of 1.
> - **Why it survived:** nothing round-tripped OBJ through kiln before, and Blender is lenient about
>   a trailing out-of-range index.

*"Blender accepted the file anyway"* is the reason the defect survived, and it is the general shape of
every lenient-parser bug: the tool that should have caught it was more forgiving than the tool that
produced it.

> **What broke.** Three separate defects in the engine's own history, each of which produced output
> that looked correct: a hand-summed total that contradicted its own subtotals, a decimator that
> destroyed the shape while hitting its count, and an exporter that wrote indices one too high and
> was accepted by the only external tool that read it.
>
> **What we learned.** The corpus's own rule — *"never publish a hand-summed count. Publish the
> grep"* — is the same rule this post applies to the tool count in §3, and it is the same rule the
> publication note violated in §1. The corpus has been saying it since September. The window contains
> at least three fresh violations of it, which is the honest measure of how much a written rule is
> worth without a gate behind it.
