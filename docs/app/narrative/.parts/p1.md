
## 4. Twenty-two agents, one hour, and two absences

On 1 November the owner issued a directive that is, in this chronicle's reading, the single most
important document of the window. It is 192 lines, it names ten verified gaps, and it assigns
twenty-two agents to close them with an acceptance criterion for each.

It is important for two reasons. The first is that it is the clearest statement in the repository of
the program's evidence standard:

> **Standing rule (owner, restated):** a deliverable exists only as a **commit SHA on a pushed
> branch** or a **permanent URL committed under `docs/`**. Chat-only claims do not count and will be
> scored as absent.

The second is that it was scored, honestly, an hour later, and the score is in the repository.

### 4.1 The ten gaps

The directive's §2 register is worth reproducing in full, because it is the best single snapshot of
what was wrong on 1 November:

| # | Gap | Evidence |
|---|---|---|
| G1 | `Tests` check is RED on main | 14 check-runs on `2ea44922`: 13 success, 1 failure |
| G2 | 13 merged-but-undeleted branches | 13 non-`main` heads, all ancestors of main |
| G3 | Launch artifacts stale on version | `docs/index.html` and `mem20.com` both carry `270 tools` ×8, `27 domains` ×8, `v3.0.0` ×4 |
| G4 | Tag is 63 commits stale | `compare/v3.1.1...main` → ahead_by 63, behind_by 0 |
| G5 | PyPI 404s | `mem20`, `mem20-mcp`, `mem20-sdk` all 404 |
| G6 | Three domains unregistered | `.org` / `.store` / `.info` return GitHub 9,115-byte 404 |
| G7 | Chronicle is 5 days stale | `serial-2026-10-27.md` is the only narrative file |
| G8 | Retired infra still on main | `Sidney`, `gabe`, `jaysonai` still present after PR #145 |
| G9 | Benchmark quality gaps | adversarial_hard and unanswerable slices still need a scored row |
| G10 | `/sites/` anonymous 403 | no anonymous-reachable launch URL exists |

G7 is this serial's own row, and it is worth recording what it asked for, because it is the only
place in the repository where the chronicle's obligations are written down by someone other than the
chronicle:

> **22. Mem20-naration** — G7
> - Bring the chronicle series current. `serial-2026-10-27.md` stops at frontier `e7758bd`; publish
>   the next instalments covering: main `2ea44922`, 270 tools / 27 domains, `VERSION` 3.1.0 + tag
>   v3.1.1, the at-risk convergence **10 → 3 → 0** (`docs/ops/branch-inventory-2026-10-31.md` §196),
>   and the retirement of the Sidney/gabe infra.
> - **Acceptance:** new files under `docs/app/narrative/` committed on a branch, each pinned to a
>   real baseline SHA and citing the command behind every figure.

Parts one and two of this serial did exactly that, and the roster score credits them:

> | 22 | Mem20-naration | **DELIVERED** | `feba039c68c76bf724896d00153e30e6e744c693` | `docs/app/narrative/serial-2026-11-01.md` + `-11-01b.md` + publication note (`1376fb47`) |

Note the SHA. The roster credits `feba039c` for the two posts and `1376fb47` for the publication
note. `1376fb47` is the commit whose subject says *"main moved to 3.1.2 mid-run"* — the correct
version, before the 18 November sweep rewrote it. The roster score is therefore a second, independent
record that the note originally said 3.1.2, and it is the record that makes §1 provable rather than
merely argued.

### 4.2 The score

The directive was issued at 17:22:57Z. The roster was scored at 18:24:00Z, sixty-one minutes later,
by Mem20-admin, and the scoring method is stated so it cannot be softened later:

> **Strictness rule (stated so it cannot be softened later):** a row is DELIVERED only if the
> artifact is carried by a commit whose committer date is **after** the roster commit
> (`17:22:57Z`). Pre-roster trees on `main` — e.g. `docs/finance/CLAIMS_CHECK_H18.md` from 2026-10-31
> — are work from an **earlier** round and are **not** credited here. Crediting them would be the
> same error as crediting a chat claim.

The result:

| | Count |
|---|---:|
| Rows scored | 23 |
| DELIVERED | 21 |
| ABSENT | 2 |
| Delivered with an unmet sub-criterion | 2 |

Twenty-one of twenty-three in sixty-one minutes, with 67 commits landing on 21 refs in the window.
That is a genuinely impressive throughput, and the score document does not oversell it: it flags the
two partial deliveries rather than rounding them up.

### 4.3 The two absences

The two absences are named plainly, and the language is worth preserving because it is the register
this chronicle is trying to hold:

> **Row 7 · AI Engineer — ABSENT.** The named deliverable
> `docs/benchmarks/retrieval-gap-analysis-2026-11-01.md` is present on **no** ref. A tree-wide search
> for `retrieval-gap` / `gap-analysis` across all 21 refs returned nothing. The only post-roster
> benchmark work is row 8's registry flags, which is a different deliverable. This is not "in
> progress" — nothing was pushed.
>
> **Row 9 · Mem20 Benchmark Dataset Builder — ABSENT.** `benchmarks/results/latest.md` and
> `latest.json` are unchanged since `35500f4c` (2026-10-31 18:18 −0600), i.e. **before** the roster.
> No scored adversarial_hard or unanswerable row was published in the window. The existing
> `latest.md` still carries adversarial rows at hit rate `0.000`, which is the gap the row was meant
> to close.

Both absences are on the same gap, G9, and both are about the same thing: the benchmark rows that
would show where retrieval fails. The adversarial rows sit at hit rate `0.000` and nobody published a
scored replacement.

This matters more than a missing document usually would, because of what the project's own
engineering culture says about partial passes. `PROOF.md`'s rule — *"A partial pass is not a clean
pass"* — is the standard the chronicle is written to, and the benchmark gap is the place where the
project's own numbers most need that standard. An adversarial slice at `0.000` is not a benchmark
result; it is a measurement that the system fails a category completely, published without a
diagnosis of why.

### 4.4 The two partial deliveries

The score flags two rows as delivered with an unmet sub-criterion, and both flags are instructive:

> - **Row 1 · GitHub Repo Assistant** — 2 of 3 acceptance criteria met with evidence: `Tests` is
>   **green** on `48c241a1` (was the red check in G1) and `v4.0.0` now points at main head (was 63
>   commits stale, G4). **Not met:** the 13 merged refs were **not** deleted — the remote still
>   carries **21** heads. G2 remains open.
> - **Row 13 · Mem20 Content Creator** — a branch SHA under `docs/gtm/` was delivered
>   (`aaffc08b`, an audit harness). **Not met:** `docs/gtm/mem20-launch-copy.md` itself was **not
>   rewritten** — the diff against baseline is empty. It already reads 270/27/3.1.x with zero
>   `v3.0.0`, so the copy is not wrong; the rewrite the row asked for did not happen.

Row 1's partial is the more interesting one, because of a detail in the score's own header. The
header says `main` at deadline is `48c241a1` and annotates it `(v4.0.0)`. That annotation is wrong
for the same reason the publication note is wrong: `48c241a1` is 3.1.2. The roster score was written
on 1 November, before the sweep, so the annotation was added later — or the score document was itself
swept. Either way, the document that exists today contains a version claim that contradicts the
commit it names, and the contradiction is the sweep's, not the author's.

Row 13's partial is the more honest one. The agent delivered an audit harness instead of the rewrite,
and the score says so without softening it: *"the rewrite the row asked for did not happen."* It also
says why the omission did no harm — the copy was already correct — which is the right way to record a
missed deliverable that turned out not to matter.

> **What broke.** Two of twenty-three assigned deliverables were not produced, and two more were
> produced partially. The two absences were both on the same gap, and both concerned the benchmark
> rows that would show where retrieval fails.
>
> **What we learned.** The score document is the most valuable artefact of 1 November, and it is
> valuable precisely because it was written to a rule that forbids rounding up. "This is not 'in
> progress' — nothing was pushed" is a sentence that costs an agent its credit and buys the program a
> true record. The lesson is the one the project keeps relearning: **the value of a score is entirely
> in what it refuses to count.** A scoreboard that credits chat claims is worse than no scoreboard,
> because it produces confidence without evidence.

## 5. The branch count that fell from fifteen to two

At the frontier there were fifteen remote heads and the directive was complaining about thirteen
stale refs. At publication there are two. The fall is real, and it is not the story the numbers
suggest.

### 5.1 What the directive asked for

G2 asked GitHub Repo Assistant to delete thirteen merged refs, with this acceptance criterion:

> **Acceptance:** branch SHA with `Tests` = `success` in check-runs; `git ls-remote --heads` shows
> only `main`; `compare/<newtag>...main` → `ahead_by 0`.

The score records that this did not happen:

> **Not met:** the 13 merged refs were **not** deleted — the remote still carries **21** heads. G2
> remains open.

So the count went *up* on 1 November, from 15 to 21, because six new branches were pushed and none
were deleted. The score says so in its "what changed" section:

> - Remote heads: 15 → **21** (6 new branches; none deleted).

### 5.2 What happened between then and now

By 16 November the count is 103:

> **Snapshot:** 10/13 checks green (76.9%); 103 remote heads; 12 ahead; 0 open PRs; 1 open issue;
> 132 tags; 11,439 tracked files; 1,158 commits on main.

One hundred and three heads, of which twelve are ahead of `main` and **none has an open PR**. The
program status names this as blocker B2 and quantifies it:

> B2 | **50 at-risk commits on 12 branches**, unmerged, **no PR open for any of them** — they will
> rot. Triage order in §3.

### 5.3 The fall

Between 16 November and 21 November the count goes from 103 to 2. That is a hundred and one refs
removed in five days, and the repository does not record a single commit that says "delete the
branches." The refs were pruned, and the pruning is not in the history because branch deletion is not
a commit.

What is in the history is the consequence: the fifty at-risk commits are gone from the remote. The
`gtm/claim-ledger-v7-rebase` branch with fourteen commits, the `fix/post20-defects` branch with nine,
the three SDK branches — none of them is in `git ls-remote --heads origin` today.

Whether those commits were merged first or discarded is not something this post can determine from
the repository. What it can determine is that the program status predicted the outcome exactly:
*"they will rot."* Twelve branches with no PR, fifty commits, and a five-day window in which the refs
disappeared. The prediction was correct and the triage order it recommended was not executed, because
the triage order was a recommendation and the pruning was an operation.

> **What broke.** Fifty commits on twelve branches, with no PR open for any of them, were removed
> from the remote within five days of being catalogued as at-risk. The program status predicted this
> in writing and prescribed a triage order; the triage order was not followed.
>
> **What we learned.** A branch with no PR is not work in progress; it is work in a queue that nobody
> is serving. The directive's G2 asked for thirteen *merged* refs to be deleted, which was safe
> because they carried zero unmerged commits. The 16 November state was the opposite: twelve refs
> carrying fifty unmerged commits and no PR. The distinction between "safe to delete" and "at risk"
> is entirely in whether the commits are ancestors of `main`, and the program had the command for
> that (`git merge-base --is-ancestor`) and used it correctly on 1 November. **The lesson is that
> the check has to run at deletion time, not at audit time.** An audit that says "these twelve are at
> risk" is only useful if the deletion is gated on the same check.

## 6. The conformance sweep: seventy-nine issues in two days

The largest single body of work in the window is a conformance sweep that ran on 6, 7 and 8 November
and closed seventy-nine issues. It is the reason the commit count for those three days is what it is,
and it is the clearest example in the window of a program executing a written plan at scale.

### 6.1 The seven criteria

The sweep is organised around a seven-criterion conformance standard, defined in
`docs/renovation/4.0/RENOVATION_PLAN.md`. The plan's exit gate is unambiguous:

> 1. `conformance.py --all --fail-under 1.0` exits 0 — all 211 subsystems at 7/7.

Two hundred and eleven subsystems, seven criteria each. The plan's baseline table records where the
program started:

> | Subsystems fully conformant (7/7) | **6** |

Six of 211 at the start. The plan also names the cheapest win and the reason it should be batched:

> Criterion 5 (README examples) at 30.8% is the cheapest win and should be batched with criterion 6,

And it explains why the substrate had to land first:

> **Why first:** these are the modules every other subsystem must import to satisfy criterion 6. If
> [they are not first], criterion 6 work in waves 2–3 would be built [on sand].

### 6.2 What criterion 6 actually requires

Criterion 6 is the one that caused the most trouble, and the failures corpus records why. From the 6
November entry:

> **2026-11-06:** Conformance criterion 6 still failed after adding genuine cross-module calls
> because the calls sat inside a multi-line dict literal and coverage only marked the assignment
> line. NEXT ACTION: done — every mem20 call in `estate_context()` is now its own statement; the
> gate logs list each call site and report 7/7.

And from 8 November, more precisely:

> Criterion 6 is strict (import AND call on covered line via AST+coverage); guessed peer APIs caused
> missing covered calls

So criterion 6 is not "does this module import a peer." It is "does this module import a peer **and
call it on a line that coverage marks as executed**," verified by AST analysis plus a coverage run.
That is a much harder standard, and it explains the volume of work: every subsystem needed six real
peer integrations, each one a genuine call on a covered line, and each one against a peer API that
had to be discovered rather than assumed.

The failures corpus is full of the API mismatches this produced, and they are the most concrete
evidence in the whole window of what "real integration" costs. A sample, all from 7 November:

> - `mem20simz.simulate_load` returns a list (scaling/bottleneck take the list);
>   `mem20syntheticevaluatorarenaz.create_arena`/`evaluate` use hashable agent/subject IDs (strings),
>   not dicts.
> - `mem20gameproductioncontrolcenterz.milestone_status` takes numeric `due_day/today` and
>   `production_health` expects done/velocity fields; `mem20studioz.resource_allocation` takes
>   `{resource:capacity}` dict and demand `amount`; `mem20simz.funnel` takes stage dicts with
>   `conversion`, `growth_score` takes `viral_k/conversion/retention`.
> - `counterfactualmemorysimulatorz.replay` takes `(memory, steps_list)` not `(memory,int)`.
> - `mem20universalintegrationcompilerz.validate_mapping/transform` need field-mapping shape (not
>   wrapper dict); `mem20ambientteamradioz.send_message` returns `{ok,message}` and mutates channel
>   messages, so adapter must append message to channel before `channel_activity`.
> - `mem20intenttomissioncompilerz.compile_mission` expects intent dict (`goal`/`parts`), not plain
>   string.
> - `collectivemodelintelligencez.ensemble_predict` takes numeric predictions (not dicts);
>   `alternativedatabaseplaygroundz.suggest_index` takes `(columns, cardinalities_list)` and
>   benchmark needs plan dict; `crdtcollaborationenginez` GCounter/PNCounter `value` may be
>   property/callable; `prioritycollisionresolverz.submit(item, priority)` takes 2 args.

Every one of those is a signature that was guessed wrong and then discovered by running the code.
That is the honest cost of criterion 6, and it is worth recording that the standard was not relaxed
to make the sweep go faster. The failures corpus says so explicitly:

> Criterion 6 is strict (import AND call on covered line via AST+coverage); guessed peer APIs caused
> missing covered calls — fixed 336 (BatteryAwareAgentScheduler, energy_cost/greenest_node/
> migration_plan), 337 (offerassemblyfabricz/compoundingproductecosystemz/businessmodelsimulatorz/
> capabilitymarketplacez real APIs), 338 (modalitybridgez.analyze_bridge path restored,
> personalworkflowtwinz create_twin/observe/twin_health), 339 (restored leveldesign compile_level_plan
> import, dynamicnarrativeenginez create_story/add_node/current_text, replaced missing
> universaltranslatorcoprocessorz with loreragcontentgeneratorz, fixed `word_count(text)`→
> `word_count(parsed)`).

### 6.3 The user intervention

On 7 November, partway through the sweep, the owner intervened, and the failures corpus records it
verbatim:

> **2026-11-07:** User feedback: "stop using shared patterns, use real meaningful implementations."
> Applied from #317 onward: peer integrations composed into domain outcomes (e.g. #317 computes
> production-control report where team presence affects effective capacity, resilience adjusts risk,
> economics/release/forge/assets contribute real sections) rather than only collecting probe
> `signals`. Cross-module calls remain real and covered for criterion 6.

This is the most important sentence in the window, and it is worth reading slowly. The sweep had been
satisfying criterion 6 by *collecting probe signals* — calling six peers and gathering their health
outputs into a `signals` dict. That passes the AST-plus-coverage check, because the calls are real
and on covered lines. It does not produce a subsystem that does anything with its peers.

The owner's correction changed the standard from "call six peers" to "compose six peers into the
domain outcome." The example given is concrete: `#317` computes a production-control report where
team presence affects effective capacity, resilience adjusts risk, and economics/release/forge/assets
contribute real sections. That is a different kind of code. It is also much more work per subsystem,
which is why the sweep's pace changes after 7 November.

> **What broke.** For the first part of the sweep, criterion 6 was satisfied by collecting peer
> health signals into a dict — technically real calls, technically covered, and functionally
> decorative. The gate passed and the subsystems did not compose.
>
> **What we learned.** A conformance criterion that can be satisfied without producing the behaviour
> it is named for is a criterion that will be satisfied that way. The gate was not wrong — it checked
> exactly what it said it checked — but what it said it checked was "import and call," and "import
> and call" is not "integrate." The owner's correction is the general form of the lesson: **when a
> gate is passing and the product is not improving, the gate is measuring the wrong thing, and the
> fix is to change the gate, not to add more passing instances.** The sweep's later entries show the
> change taking effect — `#317` through `#329` are all described as "meaningful" rebuilds rather than
> conformance fixes, and the commit subjects change from `fix(conformance)` to `fix:`.

### 6.4 The regression inside the sweep

The sweep also produced a regression, and the failures corpus records it with unusual precision:

> **Regression detected/fixed:** 332 and 334 domain/test extensions (appended earlier) were missing
> from disk later; restored `analyze_bridge`/pipeline (`compile_level_plan` etc.) and added tests,
> re-verified 7/7.

Two subsystems had their work appended, then lost, then restored. The corpus does not say why the
files went missing, and this post will not guess. What it does say is that the loss was detected by
re-running the conformance check rather than by reading the diff, which is the only way it could have
been detected: a file that is missing from disk leaves no trace in a commit that did not touch it.

> **What broke.** Work that had been appended to two subsystems was later absent from disk, and the
> absence was found by re-running the gate rather than by any review of the change.
>
> **What we learned.** In a shared working tree with concurrent agents, "I wrote it" and "it is
> there" are different claims. The only check that distinguishes them is a re-read, and the only
> cheap re-read is the gate. This is the same lesson as the 6 November shared-tree race, arriving
> from the opposite direction: there, work was swept *into* a commit it did not belong to; here, work
> was swept *out* of the tree entirely. Both are consequences of many agents writing to one
> directory, and both are only visible to a check that reads the result rather than the intent.

### 6.5 The scale

The sweep's output is best read as a range. The `closes #` references in the window run from **#267**
to **#391**, and there are **79** of them:

```
$ git log --format='%s' 2ea44922..HEAD | grep -c 'closes #'
79
```

Seventy-nine issues closed by commit subject in twenty days, the overwhelming majority in the 6–8
November window. The commit subjects for 6 November alone run to more than thirty lines of
`fix(conformance): <subsystem> 7/7 (closes #NNN)`, and 7 November adds the "full depth spec" variants
for the same subsystems.

That is a program executing a written plan at a pace that is only possible because the plan was
written first. The renovation plan named the criteria, named the substrate that had to land first,
named the cheapest win, and set an exit gate. The sweep then executed it. Whatever else is true about
the window, that part worked.

## 7. The consolidation: 177 members into 56 runtimes

On 9 and 14 November the estate was reorganised twice, and the second reorganisation is the largest
structural change in the window.

### 7.1 The first pass: nine consolidations in one day

The 9 November diary entries record nine consolidations, each one merging a family of long-named
subsystems into a short-named runtime:

> - **consolidate training/cert/apprenticeship into mem20schoolz** — Created `mem20schoolz` (unified
>   training + certification + apprenticeship) ... removed originals `mem20apprenticeshipruntimez`,
>   `mem20trainingz`, `mem20certificationz`.
> - **consolidate all pipe subsystems into mem20pipez** — C
