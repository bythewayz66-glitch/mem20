The program status names the consequence as blocker B1 and refuses to paper over it:

> B1 | `main` not release-clean: 3 of 13 checks red on `0224a649` (`Tests`, `MCP handshake (shallow
> clone)`, `artifact evidence`). Root cause is issue **#229**: `mem20kilnz/engine/` dropped with a
> gitlink in `71939ee0`, so ~200 tests fail loudly by design. Restore the engine source or retire the
> package — **do not paper over it with a skip.** Not an agent call.

*"Do not paper over it with a skip"* is the sentence that makes this entry worth recording. The
cheapest way to make 200 tests stop failing is to skip them, and the program status forbids it in
advance.

### 8.2 The fix

The fix is three commits on 16 November, and the failures corpus records the whole procedure. The
engine repository was cloned into the engine directory of the kiln package, so the source sits inside
the checkout rather than behind a pointer. The engine needs the Assimp development headers for FBX
import, which were installed from the distribution's package manager; the package manager reported a
non-fatal error on a `dbus` post-install script because of container permissions, and the headers
installed successfully regardless. The build then ran clean with the project's makefile — 0 warnings,
0 errors — and produced the `kiln` binary in the engine directory.

The verification is the part that matters: the full test suite passes, **279 passed, 7 skipped in
35.93s**. The seven skipped are named as expected rather than left as an unexplained number — they
require a GUI, Vulkan, or specific fixtures.

Two hundred and seventy-nine passed, seven skipped, and the seven are named as expected rather than
left as an unexplained number. The commits are `58e8b78f` (*"Fix mem20kilnz engine build (issue
#229)"*), `76ea8ca1` and `7196a10b` (*"Add mem20kilnz engine source (from
JaysonAIOnline/mem20kilnz-engine)"*), all dated 2026-11-16 between 04:33 and 04:35 UTC.

Note what the fix is: the engine source is now **in the repository**, not referenced by a gitlink. The
defect was that a pointer to an external repository was treated as if it were the content, and the fix
is to stop doing that. That is the same class of error as the import finder in §7.3 — a reference
that resolves on one machine and not another — and it is worth noticing that the window contains two
independent instances of it.

> **What broke.** A commit that correctly removed a dangling gitlink also removed the only reference
> to the C++ engine source, leaving 200 tests failing at fixture setup for twenty-nine days. The
> failure was loud and correct: the tests were telling the truth about a missing dependency.
>
> **What we learned.** The program status's instruction — *"Restore the engine source or retire the
> package — do not paper over it with a skip"* — is the whole lesson, and it is worth recording that
> the instruction was written before the fix and followed by the fix. Two hundred failing tests are
> not a problem to be silenced; they are a measurement of a missing dependency, and the measurement is
> the useful part. **A skip converts a true failure into a false pass, and the false pass is
> permanent while the true failure was temporary.**

### 8.3 The engine's own failures corpus

`mem20kilnz/failures.md` is 45,085 bytes and is the richest single document in the repository. It is
also, for most of the window, the only part of the failures corpus that is being written to. Its
entries are the register this chronicle is trying to hold, and three of them are worth carrying into
this post because they are the best statements of the project's engineering values that exist.

The first is the count that was wrong:

> **2026-09-25 — Proposal claimed 263 AI-native features; real count was 212**
> - **Actual error:** the per-family subtotals in the same paragraph summed to 212. The 263 was not
>   derived from anything; it was wrong.
> - **Cause:** hand-summed headline figure never reconciled against the item list. The subtotals were
>   correct, which is exactly why it survived a read-through.
> - **Rule learned:** never publish a hand-summed count. Publish the grep.

*"The subtotals were correct, which is exactly why it survived a read-through"* is the most useful
sentence in the corpus. A document whose parts are right and whose total is wrong is a document that
rewards careful reading with a false confirmation.

The second is the decimator that refused:

> **2026-09-27 — QEM, second attempt: refused rather than shipped broken**
> - **Decision:** `decimate` defaults to `cluster`, the only method measured to preserve the surface
>   (watertight, 0 degenerate, 0 non-manifold). `method: "qem"` refuses with that reason rather than
>   returning a larger mesh. A decimator that hits its triangle count while destroying the shape is
>   worse than a simpler one that preserves it, and one that returns 278% of the input is not a
>   decimator at all.

A decimator that returns 278% of its input is a function that has failed and reported success. The
refusal is the correct behaviour, and it is recorded as a decision rather than a bug.

The third is the exporter that was one off:

> **2026-09-25 — OBJ exporter wrote every face index one too high**
> - **Actual error:** my own importer rejected kiln's export with "face references vertex 275 but
>   only 274 vertices exist". Blender accepted the file anyway.
> - **Cause:** `int base = 1;` combined with writing `base + v + 1`, so the first mesh's indices
>   started at 2 instead of 1.
> - **Why it survived:** nothing round-tripped OBJ through kiln before, and Blender is lenient about
>   a trailing out-of-range index.

*"Blender accepted the file anyway"* is the reason the defect survived, and it is the general shape of
every lenient-parser bug: the tool that should have caught it was more forgiving than the tool that
produced it.

> **What broke.** Three separate defects in the engine's own history, each of which produced output
> that looked correct: a hand-summed total that contradicted its own subtotals, a decimator that
> destroyed the shape while hitting its count, and an exporter that wrote indices one too high and
> was accepted by the only external tool that read it.
>
> **What we learned.** The corpus's own rule — *"never publish a hand-summed count. Publish the
> grep"* — is the same rule this post applies to the tool count in §3, and it is the same rule the
> publication note violated in §1. The corpus has been saying it since September. The window contains
> at least three fresh violations of it, which is the honest measure of how much a written rule is
> worth without a gate behind it.

## 9. The keyless rewire, and the dreamer that starved the box

On 11 and 12 November the estate was rewired to run without API keys, and the failures corpus records
the operational consequences with a candour that is unusual even for this repository.

### 9.1 The rewire

Commit `0c785ac3`, dated 2026-11-12T01:35:56Z, subject *"feat(llm): rewire estate to keyless
providers (pollinations + local ollama)."* The diary records the verification: a root-level chat call
returned a pollinations gpt-oss-20b reply with no key and no environment variable set, and an offline
vision call returned a local moondream description with no model argument and no key.

And the smoke tests across the estate:

> - gamez live: a role chat returned `GAMEZ-SMOKE-OK` (6.3s); an orchestrator chat returned
>   `ORCH-SMOKE-OK` (56.8s); a vision chat returned a description (646.7s). A NIM model with no key
>   raised `RuntimeError` — honest.
> - crewz live: `CogBrain().propose(...)` → `{'action':'final','final':'CREWZ-SMOKE-OK'}` (5.8s).
> - rpgz live: asyncio `chat_completion(...)` → `'RPGZ-SMOKE-OK\n'` (8.5s, after freeing CPU).

Note the parenthetical on the last line: *"after freeing CPU."* That is the whole of §9.2.

### 9.2 The dreamer

The failures corpus records the incident in full, and it is the best operational entry in the window:

> - rpgz live smoke FAILED twice (`TimeoutError` 61.1s, 60.5s) — NOT a code defect. Root cause: my
>   own `mem20dreamz idle` loop (PID 233583) was running the keyless panel nonstop: 4 concurrent
>   180s-timeout calls to local Ollama, both `llama-server` runners ~85% CPU, load average 12.6,
>   3-min/500 timeouts in the ollama journal. Fix: stopped the dreamer service, let the queue drain,
>   retried → `RPGZ-SMOKE-OK` in 8.5s. Lesson: on this CPU-only box the idle dream loop starves every
>   other LLM consumer; stop it before latency-sensitive verification, and report saturation instead
>   of blaming the client.

Read the sequence. A smoke test failed twice with a 61-second timeout. The obvious diagnosis is that
the client is broken. The actual cause is that the operator's own background process — an idle
"dream" loop, running the keyless panel continuously — was saturating the CPU with four concurrent
180-second calls to a local model server, driving load average to 12.6. Stopping it made the same
test pass in 8.5 seconds.

The lesson the corpus draws is exactly right and worth quoting again: *"report saturation instead of
blaming the client."*

There is a second entry from the same session that is a smaller version of the same thing:

> - Stopping the dreamer service hit `State 'stop-sigterm' timed out. Killing.` — the process was
>   mid-generation and did not handle SIGTERM until inference returned. Operational note: dreamer
>   restarts can take the full stop timeout (SIGKILL). Not a code change this session; recorded so
>   the next agent does not mistake it for a crash.

And a third, which is the purest example of a self-inflicted false failure in the whole corpus:

> - The `time` binary does not exist on this box — earlier benchmark attempts produced a
>   self-inflicted false failure; the operator used shell timestamp arithmetic instead.

> **What broke.** A latency-sensitive smoke test failed twice, and the cause was the operator's own
> background process saturating the CPU. The failure looked exactly like a client defect, and the
> first two diagnoses were wrong.
>
> **What we learned.** *"Report saturation instead of blaming the client"* is the rule, and it is a
> rule about the order of investigation rather than about the code. Before diagnosing a timeout, look
> at what else is running. The corpus's own framing is the useful part: the entry does not say "the
> test was flaky" or "the client was slow." It says the test failed, the cause was saturation, the
> fix was to stop the saturating process, and the retry passed in 8.5 seconds. **A failure that is
> caused by the environment is still a failure, and recording it as an environment problem is not the
> same as recording it as a non-event.** The distinction matters because the next agent will hit the
> same saturation and needs to know it is saturation.

### 9.3 The stale documentation

The same session produced a documentation correction that is a small masterpiece of the genre:

> - `docs/03-installation.md` still claimed a provider API key was required — stale after the
>   rewire; corrected to keyless-default with optional key.

One line, and it is the whole of §3 in miniature: a document that was true before a change, was not
updated by the change, and was found by someone reading it. The rewire made the key optional; the
installation guide still said it was required. Nothing failed. No test caught it. A person read the
document and noticed.

## 10. The 4.0.0 release and the launch page

The 16 November release is the point at which the project's public surface finally states the number
the server actually serves, and the record of how that was done is the best evidence in the window
that the doc-count drift gate works.

### 10.1 The page before

The launch-page record is unusually precise about the before state:

> - A fetch of the live site returned HTTP 200 with a 10,998-byte body.
> - The SHA-256 of the live body matched the SHA-256 of `docs/index.html` on main at `0224a649`
>   exactly — the served bytes were byte-identical to the file on main.
> - A scan of the served HTML for a tool/domain count returned no match — the page stated no tool or
>   domain figure at all.

That last line is the finding. The page was not *wrong* about the tool count. It stated no tool count
at all. The retired 257/26 band lived in the documents *around* the page — the launch copy, the
competitive matrix, the instrumentation notes — and the page itself deferred the figure to
`README.md`.

So the defect was not a stale number on the page. It was an *absence* of a number on the page, in a
project whose entire positioning is that its numbers are measured. The record says so directly:

> The page's own "On the numbers" note deferred the figure to README.md rather than stating it. That
> is the gap this change closes: the page now carries the measurement, and carries it from the pinned
> source.

### 10.2 The page after

> - The rebuilt `docs/index.html` is 15,327 bytes, and the committed blob size reported by the GitHub
>   API matches the local file byte for byte.
> - The diff against main is 1 file changed, 93 insertions, 11 deletions.

And the content:

> - hero fact strip now reads v4.0.0, 487 MCP tools, 129 domains, Apache-2.0
> - new section "The surface, measured" — 487 tools, 129 domains, 19 unwired tools, plus the twelve
>   largest domains: memory 55, cognitive 19, world 14, versioncontrol 11, cloudservice 10, database
>   10, filesystem 10, lie 10, productivity 10, braid 9, communication 9, dev 9
> - the "On the numbers" note now names `docs/surface.json` and the CI doc-count drift gate as the
>   reason the page and the server cannot disagree

The twelve largest domains are worth recording because they are the only place in the window where
the domain count is broken down. 129 domains, of which the largest is memory at 55 tools. That is a
distribution, not a total, and a distribution is much harder to fake.

### 10.3 The verification

The record's verification section is the model this chronicle is trying to follow:

> Doc-count drift gate, run against the working tree after the rebuild:
> - live pin: 487 tools / 129 domains
> - scanned: 85 live docs
> - result: OK, no retired tool/domain band in any live doc
> - exit code 0
>
> Headless Chromium render of the local file at 1440x1000:
> - TITLE: mem20 — auditable agent memory
> - H1: A memory that can prove what it knows.
> - facts: v4.0.0, VERSION, 487, MCP TOOLS, 129, DOMAINS, Apache-2.0, LICENSE
> - has 487: True, has 129: True
> - retired 257: False, retired 268: False
> - surface numbers: 487 MCP TOOLS, 129 DOMAINS, 19 UNWIRED TOOLS
> - domain rows: 12
> - console errors: none
> - scrollWidth / clientWidth: 1440 / 1440 — no horizontal overflow

Note the two negative assertions: `retired 257: False, retired 268: False`. The verification does not
only check that the new number is present; it checks that the old ones are absent. That is the
difference between a check that confirms a change and a check that confirms the change is complete.

And note the last line of the record, which is the most honest sentence in the window:

> **Not verified in this change:** The post-merge state of the live site. The deployed bytes can only
> be re-checked against main after this branch is merged and the Pages workflow redeploys. The
> pre-change check above (live equal to main, HTTP 200, byte-identical) is the state as of this
> commit.

The record states what it did not check, next to the claim it limits. That is the standard.

> **What broke.** The launch page stated no tool count at all, in a project whose positioning is that
> its numbers are measured. The retired 257/26 band lived in the surrounding documents, and the page
> deferred to `README.md` rather than carrying the figure.
>
> **What we learned.** An absence is harder to find than an error. A page that says 270 when the
> server serves 487 is wrong and can be grepped for. A page that says nothing is not wrong, and no
> scan for a retired band will find it — which is why the fix had to add the number rather than
> correct it. **The doc-count drift gate catches stale numbers; it cannot catch missing ones.** The
> gate's scope is "no retired band in any live doc," and a doc with no band passes it. That is a real
> limit of the control, and the launch-page record is the only place in the window where it is
> stated.
