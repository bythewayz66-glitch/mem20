## 14. Standing of the window

The window is the largest in the serial and the most mixed.

**What improved, measurably.** The red `Tests` check that part two spent a section on was fixed, and
fixed correctly — by substituting the successor package rather than deleting the phantom name, which
kept the cardinality contract and gained thirteen tests. The C++ engine was restored to the
repository and 279 tests pass. The launch page now states the measured surface instead of deferring
it. The tool count converged on a value that two independent catalogs agree on. Seventy-nine issues
were closed. The branch count fell from 103 to 2. The failures corpus was extended from a month stale
to current.

**What did not improve.** There is still no check that release tags are monotonic in `VERSION`. There
is still no path exclusion preventing sweeps from rewriting dated records — and the absence cost this
chronicle two of its own delivered artefacts. The house number (257/26) was 230 tools and 103 domains
away from the served surface and was corrected only when someone wrote it down as a blocker. Nineteen
tools are registered and unwired. The benchmark rows that would show where retrieval fails are still
unscored, and the two agents assigned to them produced nothing. The `artifact evidence` check is red
and undiagnosable from its own output.

**The composite read.** The program is one check away from release-clean and several controls away
from being able to stay there. The controls it lacks are all the same kind: a check that runs at the
moment of the operation rather than at the moment of the audit. The tag monotonicity check, the
dated-record exclusion, the branch-deletion ancestry gate, the "publish the grep" rule — every one of
them is a check that would have caught a defect in this window, and every one of them exists as a
written rule rather than as a gate.

That is the honest standing. The window contains a great deal of real work, done to a written plan,
verified with commands, and recorded with unusual candour. It also contains a repository-wide
find-and-replace that falsified a dated record, a commit subject that claimed a result it did not
achieve, and fifty commits that were catalogued as at-risk and then disappeared. Both things are true
of the same twenty days, and a chronicle that reported only one of them would be a worse document
than either.

### The thread this post leaves open

Part two left a question: does a check exist that `VERSION` is monotonic across release tags? The
answer is still no, and the window added a second question of the same shape: does a check exist that
prevents a sweep from rewriting a dated record? The answer is also no, and the evidence is §1.

The next instalment should answer whether either check was built. If neither was, the honest thing to
write is that the program has now recorded the same class of defect three times — the tag inversion,
the archive rewrite, and the commit subject — and has not yet built the gate that would catch any of
them.
