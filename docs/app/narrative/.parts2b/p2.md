```

Read those two together and you have the whole problem in two sentences. The API does not append a
newline; it *strips trailing whitespace*. So a part that ends with a newline loses it, and the join
between two parts collapses. The fix is to split on line boundaries and join with a newline — the join
puts back exactly what the strip removed.

The earlier commit (`905a68e0`) had the direction of the error backwards. It assumed the API added a
newline; the API removed one. The commit message for `905a68e0` is therefore wrong about the cause,
and the later commits correct it without saying so. That is a small thing, and it is exactly the kind
of small thing the chronicle exists to record: a fix that works for the wrong reason, followed by a fix
that works for the right one.

### 2.5 The trigger that fired on the sentinel

`6191a9bc`:

```
ci(narrative): assembler triggers on a dedicated sentinel file

The .parts2/ push trigger fired on every part commit and deleted the parts
directory after the first one. The trigger is now a single sentinel file
committed last, once every part is in place.
```

This is the same defect as `74ebe539`, fixed a second time. The first fix was to make the workflow
manual-dispatch-only. That worked, but it meant a human had to click a button, and the human was an
agent, and the agent's way of clicking a button was to commit a file. So the trigger came back — but
scoped to a single sentinel path rather than the whole directory.

The final workflow, as it stands at `77b72a1a`, states the design in its header comment:

```
# TRIGGER: push of docs/app/narrative/.assemble-trigger ONLY, committed last
# once every part is in place.
```

And the assembly step:

```
for f in $(ls "$PARTS"/*.md | sort); do
  echo "appending $f"
  if [ "$first" -eq 0 ]; then
    printf '\n' >> /tmp/assembled.md
  fi
  first=0
  cat "$f" >> /tmp/assembled.md
done
printf '\n' >> /tmp/assembled.md
mv /tmp/assembled.md "$TARGET"
rm -rf "$PARTS"
rm -f docs/app/narrative/.assemble-trigger
```

Read that loop carefully. It writes to `/tmp/assembled.md`, not to the target. It moves the result into
place only after the loop completes. It removes the parts directory and the sentinel only after the
move. Every one of those orderings is a fix for a failure described in an earlier commit message.

### 2.6 What the fourteen commits produced

The word count at each assembly commit, measured with `git show <sha>:<path> | wc -w`:

| Commit | Words | What it was |
|---|---|---|
| `b5107c53` | 4,903 | part 1/5, the first fragment |
| `b479c093` | 20,009 | first assembly — polluted, duplicated sections |
| `df055cb6` | 8,066 | second assembly — partial |
| `d1438766` | 8,199 | third assembly — partial |
| `43546167` | 16,264 | fourth assembly — complete, two words short |
| `fcca9535` | 16,266 | fifth assembly — final |

The 20,009-word file is the interesting one. It is larger than the final, and the reason is visible in
its headings. `git show b479c093:docs/app/narrative/serial-2026-11-21.md | grep '^## '` returns 21
headings, of which four are duplicated:

```
## 4. Twenty-two agents, one hour, and two absences
## 5. The branch count that fell from fifteen to two
## 6. The conformance sweep: seventy-nine issues in two days
## 7. The consolidation: 177 members into 56 runtimes
```

The final file has 17 headings and no duplicates. So the first assembly concatenated a parts directory
that contained two copies of sections 4 through 7 — presumably because a failed attempt had left its
parts behind and a later attempt added its own. The assembler did what it was told: it concatenated
everything in the directory. The directory contained more than it should have.

This is the same failure as the 125,740-byte file, in a different guise. Both are the assembler
faithfully assembling a directory that had accumulated debris. The fix in both cases was to make the
directory's contents trustworthy — start from empty, read only one directory, delete the directory
after use.

### 2.7 The four probes

Interleaved with the assembly commits are four commits whose subject begins with `probe:`.

| Commit | Time | Subject | File |
|---|---|---|---|
| `bdfb2cdf` | 11:13:31 -0700 | `probe: verify API write path` | `docs/app/narrative/.write-probe` |
| `b7c12544` | 11:16:08 -0700 | `probe: remove write-path probe` | (deletion) |
| `7098af0d` | 11:45:00 -0700 | `probe: quota check` | `docs/app/narrative/.parts/probe.txt` |
| `3fc93a75` | 11:49:25 -0700 | `probe: write check` | `docs/app/narrative/.parts/probe2.txt` |

Four commits, three files, all of them one line. These are not content. They are tests of whether the
write path works — whether a file can be created at all, whether the quota has room, whether a write
into a subdirectory behaves differently from a write at the top level.

The first pair is the cleanest: write a probe, confirm it landed, delete it. The second pair is less
clean — `probe.txt` and `probe2.txt` were written into `.parts/`, the directory the assembler reads.
That is a real hazard, and it is the same hazard that produced the 20,009-word file: anything in
`.parts/` gets concatenated. A one-line probe file in that directory would have appeared in the
assembled document as a stray line.

Whether it did is not recorded. The final file does not contain the string `probe`, and the parts
directories were deleted by the assembler. What can be said is that the probes were written into a
directory whose contents were being concatenated, and that this is the kind of thing that produces a
stray line in a published document and no error anywhere.

**What broke.** A workflow that cleaned up after itself deleted its own input, because its trigger was a
push to the directory it cleaned. A first assembly appended to an existing target and picked up debris,
producing a 125,740-byte file against a 101,467-byte source. A second assembly concatenated a directory
containing duplicated parts, producing 20,009 words against 16,266. A fix for the newline problem
assumed the API appended a newline when it strips one. And two probe files were written into the
directory the assembler reads.

**What we learned.** The lesson is not "write a better assembler". It is that a build step which reads a
directory must own that directory's contents, and a build step which deletes its input must not be
triggered by its input arriving. Both of those are structural, and both were learned by breaking them.
The commit messages record the breakage in the order it happened, which is why this section can be
written at all: fourteen commits, each one a sentence about what the previous one got wrong.

## 3. The gate that was never built: tag monotonicity

The previous instalment's §2 ended with a question it could not answer:

> Part two §12 asked whether the repository has a check that `VERSION` is monotonic across its release
> tags. `48c241a1` cuts 3.1.2, which is higher than both 3.1.0 and 3.1.1, so the *current* state is
> monotonic. Whether a *check* now exists is a separate question this note does not answer, and the
> next instalment should.

This is the next instalment, and the answer is no.

### 3.1 What was searched

The search was for code, not for intent. A plan document that says a gate should exist is not a gate. A
docstring that describes a rule is not a gate. The question is whether there is an executable check that
would fail if the rule were broken.

Searched:

- Every file under `.github/workflows/` (18 workflows) for `VERSION`, `git tag`, `refs/tags`.
- Every file under `scripts/` for `git tag`, `refs/tags`, `semver`.
- The whole tree for `monotonic`, `tag_monoton`, `tag-monoton`, `version_monoton`, `semver.*monoton`.
- `git log --all --grep='monoton' -i`.

### 3.2 What was found

**In the workflows**, three references to `VERSION` and one to tags:

- `.github/workflows/ci.yml:254` — a comment: *"VERSION, pyproject.toml and version.hpp each state the version and nothing compared them: on 2026-11-01 they read 4.0.0, 3.0.0 and 3.1.0."* Followed by a step that runs `python3 scripts/check_version_consistency.py`.
- `.github/workflows/ci.yml:495` — `print("stdlib-only import ok; api_version =", h.API_VERSION)`, an unrelated API version.
- `.github/workflows/controlz-desktop.yml:123-124` — `tagName: controlz-v__VERSION__`, a release-asset naming template.
- `.github/workflows/release.yml` — the Ruby SDK release, which checks that a pushed tag matches the gem version.

**In `scripts/`**, one file: `scripts/check_version_consistency.py`.

**In the whole tree**, `monotonic` appears in 25 files, none of them a version check. They are
monotonic clocks, monotonic counters, monotonic sequence numbers — `mem20orcaz/concurrency.py`,
`mem20kimiz/batch.py`, `mem20ircz/hub.py`, and so on. The word is used, but never about tags.

**In `git log --all --grep='monoton' -i`**, one commit: `4d166d90`, *"Option C batch 6: traffic control,
webhook network (17 tests)"*. Unrelated.

### 3.3 What `check_version_consistency.py` actually does

This is the closest thing in the repository to a version gate, and it is worth reading in full because
its docstring states precisely what it does and does not cover.

```
"""Fail when the version is stated in more than one place and the places disagree.

mem20 states its version in three files:

  VERSION                              -- the release marker, authoritative
  pyproject.toml  [project] version    -- what `pip install .` records
  sdk/cpp/include/mem20/version.hpp    -- what the C++ SDK was built against

On 2026-11-01 these read 4.0.0, 3.0.0 and 3.1.0. Nothing compared them, so the
package metadata had been two minor releases behind the tree it described and
the SDK baseline one behind. This script is the comparison.

VERSION is authoritative because it is the file the release process writes and
the only one that is a single token with no surrounding syntax to parse.

Exit 0 when all three agree, 1 when they do not, 2 when a file is missing.
"""
```

Three files, compared for equality. That is the whole check. It answers the question "do these three
files state the same version right now". It does not answer "is this version higher than the last one",
and it does not look at tags at all.

The distinction matters because the defect the previous instalment described was not a disagreement
between three files. It was a tag ordering: `v3.1.1` (`52ffe13d`) is an ancestor of `v3.1.0`
(`73343f68`). A tag cut before the release it names. `check_version_consistency.py` would pass on that
repository state, because all three files could agree on a version while the tag graph was still
inverted.

### 3.4 The one place tags are compared

`scripts/ops/scoreboard_signals.sh` does compare branches against `main`:

```
ahead=$(git rev-list --count "${MAIN_REF}..${sha}" 2>/dev/null || echo "?")
if git merge-base --is-ancestor "${sha}" "${MAIN_REF}" 2>/dev/null; then
  st=MERGED; merged=$((merged+1))
else
  st=UNMERGED; unmerged=$((unmerged+1))
fi
```

That is a branch-merge check, not a tag-order check. It iterates `git ls-remote --heads origin`, which
lists branches, not tags. It answers "is this branch merged into main", which is a different question
from "is this tag's version higher than the previous tag's version".

And it is a reporting script, not a gate. It prints a scoreboard. It does not exit non-zero on a
violation, and it is not invoked by any workflow.
