a delivery and is still gated (self-test case 9).

This is a good commit. It names the two commits that failed by construction (`105b9602`, the lockfile

### 7.1 The labels that were not renumbered

The commit message says *"Self-test extended 6 -> 9 cases"*. The self-test now has nine cases. But the
labels were not renumbered:

```
$ python3 scripts/check_artifact_evidence.py --self-test
self-test [1/6] authored delivery with evidence -> PASS
self-test [2/6] authored delivery, no evidence -> FAIL
self-test [3/6] authored commit changing nothing -> PASS (empty)
self-test [4/6] gate-own change -> PASS (ci-infrastructure)
self-test [5/6] convergence push landing unevidenced work -> PASS (integration)
self-test [5b/6] same work delivered as a PR -> still FAIL (gate keeps teeth)
self-test [6/9] zero-diff convergence push -> PASS (integration)
self-test [7/9] lockfile-only change -> PASS (ci-infrastructure)
self-test [8/9] workflow-only change -> PASS (ci-infrastructure)
self-test [9/9] lockfile mixed with product code -> still FAIL (gate keeps teeth)
```

Ten lines of output, nine cases (one is labelled `5b`). The first six say `/6`; the last four say `/9`.
The transition happens between `[5b/6]` and `[6/9]`, which means the author renumbered from case 6
onward and left cases 1 through 5b alone.

This is a cosmetic defect and it is worth recording for exactly that reason. The gate works. The
self-test passes. The commit message is accurate about the count. And the output a human reads when the
self-test runs says the suite has six cases in its first six lines and nine in its last four.

The cause is visible in the diff: the new cases were appended after the existing ones, and the existing
ones' labels were not touched. The author was thinking about the new cases and not about the old labels.
That is how every cosmetic defect happens.

**What broke.** Nothing functional. A test suite's output labels disagree with its own case count.

**What we learned.** A self-test is documentation that runs. If its labels are wrong, the documentation
is wrong, and the wrongness is printed on every run to everyone who looks. The fix is one line per
label, and the reason it was not made is that the author was adding cases rather than reading output.
The lesson is not "renumber your labels" — it is that the output of a check is part of the check, and a
check whose output misleads is a check that will eventually be misread.

### 7.3 What the check does

`.github/workflows/mcp-verify.yml`:

```
- name: Checkout (shallow, no history)
  uses: actions/checkout@v4
  with:
    fetch-depth: 1

- name: Confirm the checkout really is shallow
  run: |
    echo "is-shallow: $(git rev-parse --is-shallow-repository)"
    test "$(git rev-parse --is-shallow-repository)" = "true"
```

The check is a regression guard for shallow clones: it deliberately checks out with `fetch-depth: 1` and
then verifies that the MCP server can still start and answer `tools/list` with 487 tools. The comment
above the dependency install step records why the guard exists:

```
# Install from requirements.txt, not a hand-written list. The hand
# list drifted: it named four packages while requirements.txt
# declared eight, and the two it omitted (mcp-types, and aiohttp at
# the pinned floor) are imported at module scope by modules the
# server loads before it can answer a single request. Sixteen runs
# failed on that gap. The file is the source of truth; this step
# reads it.
```

Sixteen runs failed on a hand-written dependency list that had drifted from `requirements.txt`. That is
the same class of defect as the manifest: a hand-maintained list that nothing compared against its
source.

### 7.4 What could not be established

Running `verify_mcp.py` locally reproduces the failure:

```
$ timeout 120 python3 verify_mcp.py
EOF from server; stderr:
```

`EOF from server` with empty stderr. The server process exits without writing anything to stderr, which
means the failure is not an exception being raised and printed — it is the process ending.

But the local environment is not the CI environment. The local run is against a full clone, not a
shallow one; the local interpreter is the sandbox's Python 3.11, not the CI's; and the local run has
whatever dependencies the sandbox happens to have installed, which is not `requirements.txt`.

So the honest statement is: the check is red on `77b72a1a`, it was green on the two preceding commits,
the commit in between does not touch the MCP server, and a local reproduction produces `EOF from server`
with empty stderr. The cause was not isolated in this run.

**What broke.** A check that was green went red on a commit that could not plausibly have caused it.

**What we learned.** A red check on a commit that does not touch the checked code is evidence about the
check, not about the commit. The two possibilities are that the check is flaky and that the check is
detecting something environmental. Both are worth knowing and neither can be distinguished from a single
red run. The next run should re-run the check on the same SHA before concluding anything, and this
instalment did not do that.
