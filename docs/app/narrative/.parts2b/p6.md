> **Cause:** hand-summed headline figure never reconciled against the item list. The subtotals were
> correct, which is exactly why it survived a read-through.
>
> **Rule learned:** never publish a hand-summed count. Publish the grep.

That rule is the reason §5 of this instalment exists in the form it does. The audit did not sample; it
enumerated thirty-one documents and ran the same check on each. The count of five rewrites is a count
produced by a loop, not by reading and remembering.

**`mem20kilnz/failures.md`, 2026-09-25 — "Sixteen engine functions declared but never implemented (not nine)":**

> **Actual error:** I first reported **nine**. The true count is **sixteen**. My check grepped nine names
> I had picked by hand and confirmed each appeared exactly once. It never audited the full declaration
> list, so seven more were missed.
>
> **Cause:** sampling the header by hand instead of enumerating it.

This is the previous instalment's error, stated a month and a half before it was made. It found two
rewrites by looking in the directory it happened to be reading, and reported two. The true count was
five. The cause is identical: sampling instead of enumerating.

That the same mistake was made twice, by the same series, with the rule already written down in the
corpus it draws from, is the most useful thing in this section. A lesson that is recorded and not applied
is a lesson that has not been learned.

**`failures.md`, 2026-11-04 — the launch-gate entry:**

> launch-gate check flagged the served page because `VERSION` (4.0.0) was itself listed in
> `RETIRED_VERSIONS`. NEXT ACTION: done — `retired_versions_for(current)` filters the live version;
> regression test added.

A gate that flagged the current version because the current version was on its list of retired versions.
That is the same shape as the artifact-evidence gate failing lockfile commits: a check whose rules were
correct in general and wrong for a case the author had not considered. The fix in both cases was to
narrow the rule, not to weaken it.

### 9.2 The corpus's silence

The corpus has no entry for 21 November. It has no entry for the fourteen assembly commits, the four
probes, the 125,740-byte polluted file, the 20,009-word duplicated assembly, or the self-test labels.

Every one of those is a failure in the corpus's own format: attempt, actual error, cause, next action,
rule learned. None of them was logged.

**What broke.** The failure log stopped recording failures at the moment the failures became
process-level rather than code-level.

**What we learned.** A failure corpus that only records product defects will miss the defects in the
process that produces the product. The assembly saga is fourteen failures with causes and fixes, each
one documented in a commit message and none of them in `failures.md`. The commit messages are the better
record here, and that is an accident — they were written to explain a change, not to teach a lesson.
