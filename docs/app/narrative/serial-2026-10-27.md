# Twenty-One Branches and One Merge

**Serial — 2026-10-27** · window: 08:44–15:20 UTC · baseline `45445f4850377814cd95b7fa50c0a9153f76c163` · frontier at publication `e7758bd178d38da63c5359dded0aada8bfc0eea5`

A narrative of one round in the mem20 program, built from commit SHAs and committed URLs rather than
from what was said in the room. Every claim in this document carries its evidence next to it. Where an
agent was given work and no SHA exists, this document says so; it does not soften the absence into
"in progress". Where this document itself was wrong an hour ago, it says that too, at the point the
error was made.

---

## 0. What this document is, and what it refuses to be

At 08:44 UTC on 27 October 2026 the owner of the mem20 repository issued a directive: assign
meaningful work to every AI agent member — twenty-two of them — for one hour of autonomous work, and
then verify every claim at the deadline against a real SHA or a real HTTP 200. The directive was
landed in the repository as a roster before it was acted on, which is the only reason this round can
be audited at all: `docs/ops/workload-roster-2026-10-27.md`, committed on branch
`docs/ws1-workload-roster-2026-10-27` at `05da8465c607ee0fa12982d50268bdbf35f88067`, 08:47:01Z.

That roster contains a sentence the rest of this document is organised around:

> A row is `DELIVERED` only when a live branch head SHA or a committed URL is recorded. Chat does not count.

This is the chronicle of that round, and the honest summary of it is short: **twenty-one of twenty-two
agents delivered a branch carrying at least one commit dated after the dispatch, two commits from the
round reached `main`, and one hundred and seventy-seven branch-commit slots — 168 distinct commits —
sat outside it at the baseline the round was dispatched against.** By publication the second of those
merges had landed and the figure had fallen to 173 slots and 164 distinct commits (§1).

That is the shape. It is not a victory lap and it is not a failure report. It is a scoreboard with a
number on it, and the number that matters is the last one.

### A note on the previous version of this document

An earlier draft of this file, committed at `c5b54596ddfc123d2d91fd61ead7daf0803bc0cb`, reported that
**zero** of the twenty-one branch deliverables existed on the remote, and concluded that "forty-five

twenty-one carry tips dated after 08:44:00Z. The earliest tip is 08:53:12Z and the latest is 09:22:25Z.

The correction is not a footnote, because the earlier document's *thesis* rested on the empty
scoreboard, and the thesis is what changed. §8 of this document records the correction in full, with
the old claim, the new claim, and the command that settles it. The earlier draft's discipline — the
refusal to collapse "nobody delivered" into "nothing has landed yet" — remains correct in principle.
What was wrong was the arithmetic of the clock: a census taken eleven minutes into a sixty-minute
round is a snapshot of the first fifth, not a verdict, and a document that publishes it as a verdict
is doing exactly the thing it warns against.

### Method

Everything below was gathered in this run, from a full clone. Verify the clone is not shallow before
trusting any count:

```
$ ls .git/shallow
ls: cannot access '.git/shallow': No such file or directory
$ git rev-list --count origin/main
299
$ git rev-list --count --all
482
```

Two different questions, two different numbers, neither wrong. `299` is how much history `main` has.
`482` is how many commits exist in this clone across every ref. A document that quotes one for the
other is wrong in a way nothing in its own output reveals.

Every timestamp in this document was converted through
`datetime.fromisoformat(...).astimezone(timezone.utc)` rather than compared as an ISO string. §8
records the error that rule prevents, and this run reproduced it in a different costume.

## 2. The dispatch: a roster committed before it was obeyed

`docs/ops/workload-roster-2026-10-27.md` is 132 lines. It is worth reading closely, because it is the
artifact that makes this round auditable, and because its own structure predicts its findings.

```
$ wc -l < docs/ops/workload-roster-2026-10-27.md
132
```

It opens with a baseline table naming the command behind each number — `git ls-files | wc -l` for the
file count, `git for-each-ref refs/remotes/origin` for the branch count, the repo API's `pushed_at` for
the last push. It then does something unusual for a dispatch document: it **corrects its own
commission**. The owner's directive had named seven in-flight items. Two of them were no longer in
flight, and the roster says so in a table headed *Corrections to the directive's in-flight list*:

> | "PR #112 (Syntax gate)" in flight | **Already MERGED** 2026-10-27T08:28:34Z at `d3ec87699242e89830c66914e49763a352f4f25e`. Do not re-open or duplicate. |
> | "270/27 tool count" still to be landed | **Already on `main`**: README, `docs/index.html`, and `docs/finance/inputs.json` all carry 270/27 with `previous_tools: 257` recorded as retired. Assigning it again would be duplicate work. |

Two assignments were dropped by that correction before anyone could do them twice. This is the
cheapest possible form of the project's central habit: check the artifact, not the instruction.

Then the twenty-two rows. Each names a deliverable, a branch, and the *reason only that agent* should
do it — a justification column, not a task list. Some rows are shaped as negative assignments, which
is worth noticing because a refusal to duplicate is a decision with a cost:

> | 12 | Mem20-Perl-Expert | `#110` is open — **do not duplicate**. New: the 25 long-running tools answer with a `{job_id,status:running}` envelope; the Perl SDK has `wait_for_job` but no test drives it to a terminal state. |

Row 12, row 16, row 17, row 18 and row 20 all begin by forbidding work that already existed in an open
PR. Row 19 explicitly retires a stale branch: `feat/scale-corpus-2000` "is stale (2 ahead, last commit
2026-10-20)". Row 9 forbids redoing an already-reconciled number: "ACV is already reconciled 44/44 at
$14,000 — do **not** redo that."

Five of twenty-two assignments are principally instructions *not* to do something. In a program whose
characteristic failure is confident duplicate work, that ratio is the most interesting number in the
document. And it is vindicated by the census in §3: of the twenty-one branches that landed, **four
were built on top of an existing branch rather than from `main`**, which is what "do not duplicate"
looks like when it is obeyed.

### The chain rule, and where it came from

Section 4 of the roster imposes a second obligation on every row:

> Every agent does **two** things:
> 1. Delivers their own row above, pushed, with a SHA.
> 2. Assigns **one new piece of work** to **one other agent** by `@`-mentioning them.
>
> To @-mention someone you must resolve their real userID: `get_groups_info(["3388661668"])` and read
> `members_detail[userID].nickname`. A nickname in the message text triggers nobody. Never `@` yourself.
>
> The chain ends when the work is in GitHub — not when the messages stop.

That last sentence is the roster's thesis. A chain of mentions is trivially self-sustaining; a chain of
commits is not. The instruction about userIDs is a small piece of operational honesty that most
dispatch documents omit: it states the *failure mode* of the mechanism it is teaching, which is that a
nickname in prose triggers nothing because the runtime routes on an identifier rather than on text.

§3 is what that distinction looks like when you run the command and read the answer.

## 3. The census: twenty-one delivered, one merged

The roster's section 5 defines the checkpoint precisely:

> At **09:44 UTC / 03:44 MDT** Mem20-admin checks every claim against:
> * `GITHUB_GET_A_BRANCH` for the named branch → does the SHA exist, and is its commit date after 08:44 UTC?
> * `curl` for any committed URL → HTTP status and byte count.
>
> Every row is scored `DELIVERED` / `NOT DELIVERED` / `UNKNOWN`. A branch that still sits at its
> pre-dispatch SHA is `NOT DELIVERED` no matter what was said in the room.

dispatch**. That second condition is what separates a delivery from a branch that happened to be lying
around, and it is the condition a naive census drops.

### What actually reached `main`

At the brief's baseline, one commit. By publication, two. The first is worth naming in full because it
is the only row of the round that touched the default branch at the time the round closed:

```
$ git log -1 --format='%H %aI %s' origin/main     # at baseline 45445f48
45445f4850377814cd95b7fa50c0a9153f76c163  2026-10-27T09:13:27-06:00
docs(ops): dispatch the 2026-10-27 workload roster — 22 agents, 1-hour round (#116)
```

And here is the detail that makes "landed on main" a more precise claim than it looks. The commit on
`main` is **not** the commit on the branch. The branch tip is `05da8465c607ee0fa12982d50268bdbf35f88067`,
authored 08:47:01Z; the commit on `main` is `45445f4850377814cd95b7fa50c0a9153f76c163`, authored
15:13:27Z. They are six hours and twenty-six minutes apart and they share no ancestry:

```
$ git merge-base --is-ancestor 05da8465c607ee0fa12982d50268bdbf35f88067 origin/main
$ echo $?
1
$ git merge-base 05da8465c607ee0fa12982d50268bdbf35f88067 origin/main
1264076698a00878acc3adacf7bf1d51eea315cc
```

Exit status 1: the roster commit is **not** an ancestor of `main`. The merge base is `12640766`, the
commit that was `main` when the roster was written. `GITHUB_GET_A_PULL_REQUEST(116)` explains it:

```
merged:            true
merged_at:         2026-10-27T15:13:28Z
merge_commit_sha:  45445f4850377814cd95b7fa50c0a9153f76c163
head.sha:          05da8465c607ee0fa12982d50268bdbf35f88067
commits:           1
additions:         132   deletions: 0   changed_files: 1
```

This was a **squash merge**, so the branch tip is an orphan with respect to `main` even though its
content landed. The proof that the content landed is a blob comparison rather than a graph walk:

```
$ git rev-parse 05da8465c607ee0fa12982d50268bdbf35f88067:docs/ops/workload-roster-2026-10-27.md
a73aef626eafdac4bb0bb9cf9b996b27ac2fc099
$ git rev-parse origin/main:docs/ops/workload-roster-2026-10-27.md
a73aef626eafdac4bb0bb9cf9b996b27ac2fc099
```

Identical blob SHA-1. Same bytes, different commit.

**What broke.** The branch `docs/ws1-workload-roster-2026-10-27` is still on the remote at
`05da8465c607ee0fa12982d50268bdbf35f88067`, its PR is closed as merged, and it appears in the "52 side
branches" count and in the "1 commit ahead" column of §5 — even though its content is on `main` in
full. So the at-risk figure of 177 includes **one commit that is not at risk at all**, because it is
the squash twin of a commit that has already landed.

**What we learned.** An ahead-count measures graph distance, not content risk. After a squash merge,
a branch reads as "1 ahead" forever, and every branch census that sums ahead-counts will count that
commit as stranded work. The check that settles it is a blob comparison, not a merge-base:

```
git rev-parse <branch>:<path> origin/main:<path>    # equal ⇒ content landed, graph didn't
```

This is the same defect class as the project's own `not_measured` convention in §6, one level up:
the number being reported (1 commit ahead) is true, and the meaning being inferred from it (1 commit
of stranded work) is false. A census that cannot distinguish those two is a census that will
over-report risk on every squash-merged branch in the repository.

what the branch was cut from. Of the twenty-one branches, this one and three others sit on an existing
branch rather than on `main`. The unit that answers "what did this row deliver" is the commits dated
after dispatch and their own diffs — not `git diff main...branch`. The roster's evidence rule names a
branch SHA, and a branch SHA is genuinely the strongest single identifier available; but a *census*
built on branch SHAs will systematically over-credit rows that stack, and under-credit rows that make
many small fixes to one file.

## 5. One hundred and seventy-seven, one hundred and sixty-eight, one hundred and eighty-three

The brief for this document says "177 at-risk commits". That number reproduces. It is also the wrong
number to put in a headline, and the reason is worth three commands.

```
$ git rev-list --count --all --not origin/main
183
$ RT=$(git for-each-ref --format='%(refname)' refs/remotes | grep -v 'origin/HEAD' \
        | grep -v 'origin/main$' | tr '\n' ' ')
$ git rev-list --count $RT --not origin/main
168
$ tot=0; for b in $(git for-each-ref --format='%(refname:short)' refs/remotes/origin \
        | grep -v 'origin/HEAD' | grep -v '^origin/main$'); do
      tot=$((tot + $(git rev-list --count origin/main..$b))); done; echo $tot
177
```

Three numbers, one repository, one moment. The decomposition:

| Figure | What it counts | How |
|---|---|---|
| **183** | every commit on any ref — branches *and* tags and stashes — not reachable from `main` | `git rev-list --count --all --not origin/main` |
| **177** | the **sum** of each branch's ahead-count, so shared commits are counted once per branch | loop over `refs/remotes/origin` |
| **168** | the **union** — distinct commits on remote branches, not reachable from `main` | `git rev-list --count $RT --not origin/main` |

The gap between 177 and 168 is **nine**, and it is exactly the nine duplicate-counted commits:

```
$ (per-branch ahead-counts, tallied by commit)
sum: 177
unique: 168
commits on >1 branch: 8   -> extra count: 9
```

Eight commits appear on more than one branch:

| Commit | Count | Branches it appears on |
|---|---|---|
| `fc8e0a440…` | ×3 | `feat/38-command-palette`, `fix/39-offline-degraded-ux`, `fix/43-telegram-turnstile-proof` |
| `ea7450768…` | ×2 | `feat/38-command-palette`, `fix/39-offline-degraded-ux` |
| `d8cc16b23…` | ×2 | `fix/perl-sdk-270-surface`, `fix/ws2-perl-jobs-coverage` |
| `6e19af5f1…` | ×2 | `fix/perl-sdk-270-surface`, `fix/ws2-perl-jobs-coverage` |
| `743a2db2d…` | ×2 | `fix/perl-sdk-270-surface`, `fix/ws2-perl-jobs-coverage` |
| `2bb47a9be…` | ×2 | `fix/perl-sdk-270-surface`, `fix/ws2-perl-jobs-coverage` |
| `ae6e8341d…` | ×2 | `fix/perl-sdk-270-surface`, `fix/ws2-perl-jobs-coverage` |
| `2bbe1fe22…` | ×2 | `fix/perl-sdk-270-surface`, `fix/ws2-perl-jobs-coverage` |

Six of the eight are the Perl SDK commits that `fix/ws2-perl-jobs-coverage` inherited from
`fix/perl-sdk-270-surface`. One is the offline-lifecycle commit `fix/39-offline-degraded-ux` that
`feat/38-command-palette` was built on top of. One — `fc8e0a440`, the Telegram turnstile test — appears
on **three** branches: `fix/43-telegram-turnstile-proof` where it was written, and then on both
command-palette and offline-degraded, which were cut from that tip.

And the gap between 177 and 183 is **six**, which is the ref-namespace difference: `--all` includes
`refs/tags/`, and this repository has fifteen tags, of which the `archive-*` family preserves branch
tips as tags precisely so that deleting a branch loses nothing. A tag pointing at a commit that a
branch also contains contributes zero new commits to the union — which is why 183 − 168 = 15 does not
equal the tag count either. The `--all` figure is a *superset* of the branch union and a *disjoint*
reading of any per-branch sum.

**What broke.** This is the third time in this serial's short life that a commit count has been
mis-stated by a unit error, and it is the subtlest instance yet. The earlier two were: a hand-summed
headline of 263 against subtotals of 212 (§6.3), and a per-day count taken on the wrong clock. This one
is different in kind. Every one of 177, 168 and 183 is **correctly computed by the command beside it**.
None of them is wrong. The error is in the sentence built on top, which says "177 commits are at risk"
when it should say "177 branch-commit slots, 168 distinct commits".

The specific mechanism that makes it easy: the brief supplied 177, the number reproduced exactly, and
a figure that reproduces feels verified. It *is* verified — as a sum. The verification confirmed the
arithmetic and left the unit unexamined, which is the comfortable failure mode. **A number that
reproduces is verified only in the sense in which it was computed.**

**What we learned.** Three questions, asked in this order, settle any "N commits at risk" claim:

```
git rev-list --count --all --not main              # every ref, incl. tags
git rev-list --count <branch-refs> --not main      # distinct commits on branches
# and then: does the per-branch sum equal the union? If not, work is shared.
```

If the sum exceeds the union, some commits are on multiple branches and the difference is the amount of
duplication. That difference is not noise — it is a map of which branches were *stacked* rather than
forked, and in this round it is the direct fingerprint of the roster's own "do not duplicate"
instructions. **The duplicate count is the evidence that the anti-duplication instructions worked.**

And the corollary that saves the next census from over-reporting: one of the 177 is `05da846`, whose
content is already on `main` as squash `45445f48` (§3). So the honest at-risk figure is **168 distinct
commits on 51 branches, of which at least one is a squash twin of landed work** — and the exact number
of remaining genuine risk requires a blob comparison per squash-merged branch, which this document has
not performed for all 51 and therefore does not claim.

### 6.1 The decimator that hit its triangle count and destroyed the shape

The most instructive sequence in the corpus is not a single entry but five, spread across three days,
all concerning one op: `decimate_mesh`.

**First attempt — quadric error metrics.** Three defects, and the corpus is precise about the order in
which they were found:

1. The flip guard compared `cross(b-a, p-a)` against `cross(b-a, c-a)`. The actual post-collapse
   normal is `cross(p-a, c-a)`. With the operands in the wrong order, **every interior quadric
   minimiser looked like a flip, so all 552 candidates were rejected and the mesh never changed** —
   the op reported success while doing nothing.
2. Fixed, it then segfaulted: collapsing deleted degenerate faces and swapped in a compacted vector,
   which renumbered faces while the vertex→face index still held the old numbers.
3. Fixed again, it hit its triangle targets and lost **20% of signed volume at ratio 0.5 and 79% at
   0.1**; once hole-filling was added it stopped reaching its target at all, reaching a fixed point at
   297 faces.

The cause, as recorded: the link condition was being applied to n-gon faces, where "the vertex
opposite the edge" is not well defined, and the boundary case was never handled.

**The decision** was to replace it with vertex clustering — "which has no topological failure mode" —
measured at 4% area drift at ratio 0.75 and 6.7% at 0.5, with zero degenerate, zero non-finite and
zero non-manifold geometry, measured by `tests/mesh_metrics.py`. QEM was recorded as the planned
replacement, "not silently dropped".

**Second attempt — refused rather than shipped broken.** The 2026-09-27 entry fixes all three of the
above and then measures six variants against a watertight 528-triangle sphere. The table is the best
thing in the corpus:

| attempt | result |
| --- | --- |
| boundary quadrics computed once | 100-140 boundary edges, −93% volume at ratio 0.1 |
| boundary quadrics refreshed per collapse | 140 boundary edges, no better |
| link condition checked after collapsing | 564 triangles out of 528 in, +3% area, still holed |
| link condition checked before collapsing | 564 triangles out, unchanged |
| triangulate first, then collapse | **1,470 triangles out of 528, +2457% area** |

That last row is arithmetically 278.4% of the input triangle count (`1470/528 = 2.784`). The recorded
cause: "the hole left by a collapse must be retriangulated from the *hole boundary*, and the loop was
being built from every neighbour of the surviving vertex. That adds more faces than the collapse
removed, so the mesh grows."

The decision line is the one to keep verbatim:

> `decimate` defaults to `cluster`, the only method measured to preserve the surface … `method:
> "qem"` refuses with that reason rather than returning a larger mesh. A decimator that hits its
> triangle count while destroying the shape is worse than a simpler one that preserves it, and one
> that returns 278% of the input is not a decimator at all.

**Third attempt — the fix, and what it was.** The next entry names the actual mistake in its title:
"the hole boundary needed an *order*, not a set". The loop was a *set* of neighbours; a set has no
order, and a fan over an unordered loop produces overlapping triangles. It was rewritten to walk the
1-ring in cyclic order through the face fan. The measured outcome, on the same sphere:

| method | ratio | triangles | hit | area drift | volume drift | boundary | degenerate | watertight |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| qem | 0.75 | 396 | 75% | +3.10% | **−1.32%** | 0 | 0 | yes |
| cluster | 0.75 | 172 | 33% | −4.02% | −8.20% | 0 | 0 | yes |
| qem | 0.50 | 264 | 50% | +7.92% | **−0.60%** | 0 | 0 | yes |
| cluster | 0.50 | 122 | 23% | −6.65% | −13.19% | 0 | 0 | yes |
| qem | 0.25 | 132 | 25% | +60.01% | −8.80% | 0 | 0 | yes |
| qem | 0.10 | 52 | 10% | +13.97% | −56.42% | 0 | 0 | yes |

`qem` became the default. And then the entry adds a guard that is really the lesson in executable
form:

> decimation refuses a mesh that is not a closed surface, with the actual boundary and non-manifold
> edge counts. A decimator run on a holed or non-manifold input returns confident nonsense, so it says
> no instead.

**What we learned**, in the corpus's own words: *"Count targets are not quality."* The generalised form
for a program of this kind: **a quality metric that can be satisfied while the artifact degrades is
worse than no metric, because it converts a broken result into a green one.** The decimator is the
cleanest example in the repository of a component that refuses instead of lying, and refusals of this
kind are among the most important entries in the story — which is why this section spends its length
on them rather than on the features that worked.

### 6.2 The exporter that wrote every face index one too high

> **Attempt:** round-trip a scene through OBJ.
> **Actual error:** my own importer rejected kiln's export with "face references vertex 275 but only
> 274 vertices exist". Blender accepted the file anyway.
> **Cause:** `int base = 1;` combined with writing `base + v + 1`, so the first mesh's indices started
> at 2 instead of 1.
> **Why it survived:** nothing round-tripped OBJ through kiln before, and Blender is lenient about a
> trailing out-of-range index.

Three sentences of cause, and one of them is a fact about the *ecosystem* rather than the code. The
defect was invisible for as long as it existed because the only consumer anyone had tried was a
tolerant one. Blender's leniency was not a courtesy; it was a missing test.

The corpus draws the conclusion the project needed: "The importer caught it; that is the argument for
having an importer at all." A writer with no reader is untested. This is the same structural insight
as the non-diff-scoped gate, one level down: **a component that is only ever exercised by its own
output, or by a consumer known to be forgiving, has not been exercised.**

### 6.3 "Never publish a hand-summed count. Publish the grep."

The 2026-09-25 entry titled *"Proposal claimed 263 AI-native features; real count was 212"* is the
origin of this serial's governing rule, and it is worth reproducing entire because the error's cause
is not arithmetic:

> **Actual error:** the per-family subtotals in the same paragraph summed to 212. The 263 was not
> derived from anything; it was wrong.
> **Cause:** hand-summed headline figure never reconciled against the item list. The subtotals were
> correct, which is exactly why it survived a read-through.
> **Next action:** recounted mechanically with `grep -cE '^- [A-L][0-9][0-9] '`, then added family L
> (43 genuine generative-pipeline capabilities) to clear 250 honestly rather than padding. Now 255,
> verified. The document carries the verification command and the correction note.
> **Rule learned:** never publish a hand-summed count. Publish the grep.

The subtotals were right. That is the whole mechanism: a wrong total sitting beside correct components
survives review, because a reader's checking instinct is satisfied by the parts. And the repair was not
to adjust the headline to 212 — it was to *do the missing work* (43 capabilities) and then report 255
with the command that produces it.

The neighbouring entry in the same corpus applies the same discipline to a *scan* rather than a sum:
sixteen engine functions were declared and never implemented, but the first report said nine, because
"I grepped nine names I had picked by hand". Two of the seven missed were `apply_frame` and
`ik_two_bone` — the engine's frame evaluation and two-bone IK. A hand-picked sample under-reported by
44% and hid the two functions whose absence mattered most.

**What we learned.** The failure mode is not "I cannot count". It is "I counted the part I could see and
reported it as the whole". The countermeasure is mechanical and cheap: publish the command, not the
number, and let the reader re-derive. §5 of this document is that rule applied to itself, and §5 is
also where the rule caught this document's own brief.

### 6.4 The transform chain that was mathematically wrong

A glTF node transform is `T*R*S`, and composing two gives `T*R*S*T*R*S` — which is **not expressible
as a single translation/quaternion/scale triple**, because the inner translation has nowhere to go.
The code collapsed the chain into one triple, "which is only correct when rotations are absent".

The evidence is a single distinguishing case: a parent with a 90° rotation and a 2× non-uniform scale,
a child with its own 90° rotation and an offset. The true chain gives `(0, 2, 0)`; the collapsed triple
gives `(0, −2, 0)`. Both are plausible numbers. Only one puts the point on the right side of the
origin.

And then the entry records something rarer, about its own investigation:

> **Note on the investigation:** my first hand-computed "expected" value was also wrong (2.0 instead
> of 3.0) because I forgot that the child's own translation moves the point. The code was right; the
> expectation was not. Recorded because the same trap would mislead the next reader.

A ledger that records its author's own wrong working is doing something no changelog can. The rule that
falls out: **a test whose expected value was hand-derived is itself a suspect**, and the first
disagreement between code and expectation is not evidence about the code.

### 6.5 The manifest that described the blockout

> **Actual error:** the replay produced 1,720 bytes with 24 vertices where the original was 161,772
> bytes with 5,952. Diffs were confined to the accessor counts, so the geometry itself differed, not
> just the encoding.
> **Cause:** the journal was read immediately after the brief, before the refine stage ran.

The manifest recorded the operations that produced the *blockout* while the file on disk was the
refined asset. Replaying it faithfully rebuilt the wrong thing — "faithfully, and wrongly". The
corpus's assessment is exact:

> this is worse than having no journal. A manifest that looks complete and replays cleanly is trusted;
> one that is quietly truncated is not.

**What we learned.** Provenance has to be sampled at the same moment as the artifact, and a provenance
record that *replays successfully* is a stronger claim than one that merely lists steps — which is why
its failure is more dangerous, not less.

### 6.6 The refusals and the deletions

The corpus keeps three things a tidier ledger would have dropped.

**An experiment deleted rather than half-kept.** Classifying each voxel shell cell by its own nearest
triangle normal gave **2.1% volume error** on a remeshed sphere against 11% for the binary field — a
five-fold improvement — but left **2,829 non-manifold edges**, because neighbouring cells disagreed
about which side of the surface they were on. A majority filter restored manifoldness and pushed the
error straight back to **10.9%**. The recorded conclusion: "the raggedness it removed was not noise, it
was the accurate boundary. Both were deleted rather than left in as a partial feature."

That is a capability with a genuinely better headline number, removed because the number was the only
thing better about it. It is the same judgment as the decimator, made earlier and without a shipped
alternative.

**A source file preserved against a destructive edit.** A brace-counting script written to replace one
C++ function body did not skip string literals, so "its match ran past the intended function and
deleted everything up to the next coincidental brace balance" — `apply_and_reply` was gone, and
`dsl_command` with it. The compiler caught it because the project builds with warnings-as-errors on
unused symbols; the fix was `git checkout` on the one file and redoing the edit by hand by exact match.
The recorded rule: "`git diff` reviewed for deletions before rebuilding."

**A probe that states what it cannot measure.** OBJ geometry: "`probe` states `geometry not measured by
this probe` in `reason` rather than presenting 0 as a measurement." One line, and it is the same
principle as `not_measured` in the `family_otherstack` fix. The program has a house style for not
knowing, and it appears independently in two components.

### 6.7 The defect classes the corpus names

Reading all forty entries together, the failures cluster into a small number of repeatable classes, and
naming them is more useful than any single entry:

1. **Plausible output that is wrong** — the colourless description that measured in local space, the
   animation curve shifted by one key, the transform chain, the surface-nets winding. The corpus says
   of the animation case: "every individual check passed. The file was valid glTF, the accessor counts
   were right, the times increased, and the import reported no error. Only comparing the sampled curve
   before and after a save caught it."
2. **Success reported for work not done** — 552 candidates all rejected while the op reported success;
   `skin` reporting `skinned=True` while the exporter wrote no skin data; `translate` reporting
   "translated <name>" having moved nothing. The corpus's verdict: "A false success is worse than a
   crash, because the caller believes it."
3. **Unit-of-count errors** — the 263/212 hand sum, the nine-versus-sixteen sampler, the advisory op
   table drifting to `ops: 79` against 87 dispatched. The fix for the last one was a checker,
   `tests/check_op_sync.py`, that "reads `apply_op`'s dispatch, the advisory table, the live `ping`
   count and the live `initialize` list, and fails on any mismatch in either direction."
4. **Environment and path assumptions** — a relative output path resolved against the engine's own
   directory, a `sys.path[0]` insertion that shadowed an installed package with a namespace directory,
   a `cwd` documented but never applied.
5. **Tests that assert the wrong thing** — three assertion failures that "looked like defects" and were
   the author's expectations; a test writing `broken.glb` into the repository root because it used a
   relative path instead of `tmp_path`; a green suite read as evidence of clean lint, followed by an
   `F401` committed anyway.

Class 5 is the one the corpus treats most seriously, because it corrupts the instrument. The entry on
the debris test ends with a process rule rather than a code fix: "the post-commit verification now
lints and tests as separate steps, after the final edit, and the result is read rather than assumed."

Class 3 is the one this document committed, in §5, and the corpus's own countermeasure — publish the
grep — is what caught it.

### 6.8 The gate that had never passed once

The corpus's lessons are about components. The audit tree holds a lesson about *infrastructure*, and it
is the sharpest single document in the repository: `docs/audit/2026-10-pages-build-failure.md`, dated
2026-10-18, 110 lines, concerning issue #54. Its opening measurement is the whole argument:

> Every GitHub Pages run fails. At the time of diagnosis the workflow had **23 runs, 0 successes**.

Twenty-three runs and zero successes. A gate with zero successes has told you nothing about its subject
and a great deal about itself, and the audit knows which is which. The failure was not in the build:

```
##[error]fatal: No url found for submodule path 'kanban-mcp' in .gitmodules
##[error]The process '/usr/bin/git' failed with exit code 128
```

Step outcomes: `Set up job` success → **`Checkout` failure** → `Upload artifact` skipped → `deploy` job
skipped. Nothing after checkout ever ran, which means every hypothesis about the deploy configuration
was a hypothesis about a step that was never reached. The audit says so in a table of ruled-out
causes — missing `pages: write` permissions, a missing concurrency group, a wrong artifact path, Jekyll
processing a non-Jekyll site, a missing `index.html`, base-path 404s, a Node version mismatch — and each
row's verdict is a reason the step was skipped, not a reason it failed.

The cause: the repository contained three entries with git mode `160000` (gitlinks), added by a plain
`git add` of nested working trees rather than `git submodule add`. **A gitlink records a commit pointer
but writes no URL**; the URL comes only from `.gitmodules`, which did not exist — not at `HEAD`, and not
anywhere in history. All three pointed at repositories that return 404.

And here is the part worth the chapter. CI was green throughout:

> `.github/workflows/ci.yml` uses `actions/checkout@v4` with no `submodules:` input (default `false`),
> so CI never recursed and never surfaced the problem — CI green, Pages red.

Two workflows, one checkout step each, different defaults, and the difference between them was invisible
because only one of them recursed. The defect was not in either workflow. It was in the *absence of a
workflow that exercised the other's assumption*.

**What broke.** Every Pages deployment for at least five days (the audit's table runs from 2026-10-14
17:18 to 2026-10-17 03:04) failed at checkout, and no test, gate or human noticed, because the only
check anyone was reading (`ci.yml`) had disabled the exact mechanism that would have failed.

**What we learned.** The audit's own record of the fix is a refusal to over-correct: the gitlinks were
removed with `git rm --cached`, and the document is explicit that this is not a feature removal —
"These pointers reference repositories that do not exist, so they carry no content and no functionality;
nothing can ever check them out. This is a broken pointer being repaired, not a feature being removed.
The SHAs above are kept in the commit message so the original intent is recoverable." It also preserves
the thing that could have been quietly lost: `mem20kilnz/` keeps all 43 of its real files.

The generalisable rule: **when two paths through the same tool use different defaults, the untested path
is the one that will break, and it will break silently.** The corollary is an operational one — a
workflow with zero successes is not a flaky workflow, it is a workflow that has never run, and the
difference between those two readings is one query on the run history.

`2.0_roadmap/tech_debt_register.md` is 29 lines and eight rows, and it is the only place in the tree
where the project states its own architectural risks in a scored form. Severity and effort are 1–5.

Two of these read differently on 27 October than they did when written, and the difference is the

**TD-01 and TD-02 are the rows that matter, and neither is discussed anywhere in this round's
twenty-two assignments.** TD-02 — the vector index is in-process FAISS and is not shared across MCP
processes — is recorded at severity 3, the highest in the file, with the mitigation "Document
single-writer constraint; for 2.0 consider external vector store (ADR pending)". TD-01 — metrics are

to assign meaningful work to every agent.

together, and the gap between them is the most expensive gap in a planning cycle. The check is one line
long: for each row in the register above severity 2, name the assignment that addresses it. If the
answer is "none," the round is optimising something other than its stated risk. This document makes no
claim that TD-02 should have been prioritised over, say, the Tauri shell — only that the choice was
never made explicitly anywhere in the tree, and an unrecorded choice is indistinguishable from an
oversight.

## 7. The three checks that are not seven

The prior round left a document that does more work than any commit in this hour: PR #111,
`docs(ops): publish the one working GitHub access path + evidence register`, head
`bef79279c2b99f44b14f3d60b11bacd865f537d0`, opened 07:43:16Z.

Its central finding is a de-duplication of failure. Every open PR — #103 through #110 — and `main`
itself were failing **the same three** checks, so a reviewer seeing seven red checks on one branch was
seeing one defect seven times:

| Check | Real cause, per #111 |
|---|---|
| `Syntax gate` | Whole-tree, not diff-scoped. Trips on two `core.py` files violating the shim rule (#17), plus a policy document that quoted the banned path while documenting the ban (#80). |
| `Tests` | Same whole-tree job, inheriting the above. |
| `Rust braid` | The hosted runner image moved to a new Ubuntu release; the toolchain assumptions no longer hold. |
| `Ruby 3.1/3.2/3.3` (#107 only) | Runner image, not the SDK: the image does not carry the requested Ruby patch release. |

Note what this does to a project's sense of its own health. If you read the check list per PR you
conclude that eight pieces of work are broken. If you read #111 you conclude that **one gate is
mis-scoped and two runner images moved**, and that no individual author can fix any of it inside
their own diff. #112 then proved the first half of that by fixing the `core.py` half and pushing the
gate to diff-scoping in `4abd005` (`fix(ci): diff-scope the Syntax gate like hygiene + rebuild lost
pipeline-1 concept.py (#114)`).

**What broke.** For an unknown number of days, every branch in the repository was scored against
pre-existing debt on `main`. The mechanism was a workflow file that used `git grep` over the whole ref
where the sibling workflow used a diff. Nothing was misconfigured loudly; the gate did exactly what it
was written to do. It was simply written to ask a question about the tree when the useful question was
about the change.

**What we learned.** A gate that is not diff-scoped converts every historical defect into a permanent
veto on new work, and it does so silently, because a red check looks like a finding about the branch.
The diagnostic is cheap: when several unrelated branches fail the *same* check, ask whether the check
reads the diff or the tree. #111 also supplies the corollary, in its own list of things it cannot
claim:

> So "get all 7 checks green on #103" cannot be done inside #103. It needs two decisions outside any
> agent's diff.

That sentence is the most useful thing in the document, because it tells an agent where its authority
ends. Two of the four causes were runnable-image decisions and one was a policy decision; none was a
code change in the branch under review.

### The access path, and the claims it corrected

PR #111 also landed `docs/ops/GITHUB_ACCESS.md` and `docs/ops/agent-worklog.md`, and its body
corrects three claims that were circulating. Reproducing the *shape* of those corrections matters more
than their content:

1. A branch reported as "never pushed because the disk filled" had in fact been at
   `44c687d564fdda2fb56326954bd1d16038b32732` since **2026-10-24**, with an open PR and eight changed

2. A credentials story about a key on the publish host was not an access path at all: the host was

3. "The `gh` CLI is installed" was untrue in the agent sandbox, and the token environment variables

The third is the one to keep. The failure mode is not believing something false; it is *writing the

The worklog on that branch is the closest existing precedent for this document, and it contains the

## 8. What this document got wrong, and what the round's own documents got wrong

A chronicle that only audits other people's work is a press release. This section is the correction
log, and it opens with this document's own error because that error is the largest one available.

### 8.1 The census that was right and the verdict that was wrong

The earlier version of this file, at `c5b54596ddfc123d2d91fd61ead7daf0803bc0cb`, published this:

> **Score at ~08:55Z: 0 delivered, 21 not delivered, 0 unknown.**

and built its thesis on it:

> **at the moment of measurement, none of the twenty-one branch deliverable assignments existed on the
> remote.** Not one.

Both sentences were true when written. Both are now false, and the second was always a misreading of
its own evidence. The measurement was taken at roughly 08:55Z; the deadline was 09:44Z. The earliest
branch tip in the round is 08:53:12Z — **two minutes before the census** — and the census missed it.

Why it missed it is the interesting part, and the earlier draft recorded the mechanism without
recognising that it was the cause of the empty table rather than a footnote to it. The first census
compared ISO timestamps as strings:

```
awk -F'|' '$1>="2026-10-27T08:44"'
```

Some tips carry `+00:00` and some carry `−06:00`. A lexicographic comparison of
`2026-10-27T02:48:09-06:00` against `2026-10-27T08:44` puts the 02:48 commit *first*, so a commit that
is in fact **after** the cutoff sorts before it. The earlier draft caught this, fixed it, and reported
that the corrected answer was "two branches". It then ran a *second* query — `git ls-remote --exit-code
--heads origin <branch>` — to test whether each of the twenty-one named branches existed, and that
query returned absent for all twenty-one.

The two results were not in conflict at the time: at 08:55Z, most of the twenty-one branches genuinely
did not exist yet. The earliest tips cluster at 08:53–08:57, and a `ls-remote` run a minute or two
before them would legitimately return nothing. So the census was accurate and the *verdict* — "the
scoreboard was empty" — was a statement about minute eleven of sixty presented as a statement about the
round.

**What broke.** A point-in-time census was published as a verdict on a round that had not finished. The
document even said so in its own prose ("forty-five minutes into a sixty-minute window") and then
titled its conclusion "the scoreboard was empty" anyway. The hedge and the headline disagreed, and the
headline is what a reader takes.

**What we learned.** A census has a timestamp and a verdict has a deadline, and they are not
interchangeable. The rule this document now applies: **if the measurement precedes the deadline, the
only publishable sentence is "at HH:MMZ, N of M rows had landed" — never "N of M delivered".** The
second sentence requires the deadline to have passed. The earlier draft's own discipline about
"nobody delivered" versus "nothing has landed yet" was correct in principle and was violated in its
own conclusion, which is the most common way a good rule fails.

The correction, in the log's terms, is a **Corrected** row: old claim "0 of 21 delivered", new claim
"21 of 21 delivered, tips 08:53:12Z–09:22:25Z", settling source the table in §3 and
`git rev-parse origin/<branch>` for each.

### 8.2 The brief's own unit error

The brief supplied "177 at-risk commits". §5 shows that 177 is the sum of per-branch ahead-counts and
that the distinct-commit figure is 168. The brief's number is not wrong; its unit is unstated. This is
logged as a **Re-labelled** row rather than a correction, because the arithmetic reproduces exactly and
only the noun changes.

### 8.3 Three deadlines in three documents

Here is a defect that no commit's subject announces and that only a side-by-side read finds. The
roster states its deadline three times, consistently:

> **Hard deadline:** **2026-10-27 09:44 UTC / 03:44 MDT** (one hour)

The worklog that PR #111 landed — the register agents are told to write their evidence into — states a
different one. It is on `main` now, at `docs/ops/agent-worklog.md` line 3:

> **Round:** 2026-10-27 · **Deadline:** 21:34 MDT (01:34 UTC+1) · **Auditor:** Mem20-admin

And the previous round's checkpoint ledger, committed at `83b488783fd177b6795c5c062f6957729cc22def`,
states a third:

> Deadline **2026-10-27T02:47:00Z** (2026-10-27 20:47 MDT)

Three documents, three deadlines, in the same repository, within fourteen hours. The arithmetic in the
last one does not close either: 02:47Z on 27 October is 20:47 MDT on **26** October, not 20:47 MDT on
the 27th.

None of these is a typo worth a chapter on its own. Together they are a finding about dispatch
hygiene, and it is the specific finding this round produces: **an agent working from the worklog would
have believed it had until 21:34 MDT, twelve hours after the roster's whistle.** A deadline that

suggestion with a timestamp on it.

**What broke.** The round's own instruction set contained at least three mutually inconsistent
cut-offs, and at least one internally inconsistent timezone conversion.

**What we learned.** A deadline is a datum and belongs in exactly one place, referenced by ID from
everywhere else. The project already has this instinct for tool counts — `docs/finance/inputs.json`
carries `"authority": "verify_mcp.py MEM20_EXPECTED_TOOLS default = 270 ..."` precisely so the number
is not restated in six documents and stale in four. The same pattern applied to the round's clock
would have made this paragraph impossible to write. It is a one-line fix with a measurable payoff, and
it is the kind of fix that only looks obvious after someone diffs two files nobody thought to compare.

### 8.4 The scoreboard's definitional inconsistency

The roster's row 22 claims "22 assignments to 22 agents" while also saying "21 of them produce a new
branch". Both statements are correct and the apparent tension is real: Mem20-admin's slice is the
verification, not a branch. But the roster's table then lists row 22's evidence as "this file", which
is a committed artifact rather than a branch, and the census in §3 therefore scores it differently from
the other twenty-one.

That is a definitional inconsistency in the scoreboard, not a delivery failure, and it is the kind of
thing that produces arguments at a checkpoint. The fix is one sentence in the roster: a row's evidence
form is either `branch` or `path`, declared per row. As it stands, a strict reading of "a live branch
head SHA or a committed URL" scores row 22 as `DELIVERED` on the URL clause and the other twenty-one on
the SHA clause, and a reader who applies only the SHA clause will report 21 of 22.

### 8.5 The dispatch document that was invisible for six hours

## 9. Attributing work when the author field is credentials

The single most misleading column in any git-based account of this program is `%an`.

Measured across the 299 commits reachable from `main`:

```

      2 UX Researcher
```

And across all 482 commits in the clone:

```
$ git log --all --format='%an' | sort | uniq -c | sort -rn | head -12
    336 bythewayz66-glitch
     30 Mem20 Content
     29 spacebunny
     29 JaysonAIOnline
      8 Slides Assistant
      7 mem20 GTM Team Lead
      6 mem20 perl sdk
      5 dependabot[bot]
      3 mem20 agent
      3 Webpage Developer
      3 Server Builder
      3 GitHub Repo Assistant
```

Two things follow, and they point in opposite directions.

**First: the author field is not useless.** 123 of 299 commits on `main` carry an identity other than
the owner, and some of those identities are agent roles outright — `Mem20 Content`, `mem20 GTM Team
Lead`, `Slides Assistant`, `Server Builder`, `UX Researcher`. So a chronicle may report that agent
identities appear in the history, and it may count them.

**Second: the author field is not authorship.** The roster at `05da846` was dispatched in the name of
"Mem20-admin" and is authored by `bythewayz66-glitch`. Every one of the twenty-one branch tips in §3
was read back with `git rev-parse`, and the author field on those tips is not a reliable guide to which
agent produced the diff — the round's landing path is a single authenticated integration, so the
credential is shared. Both are true statements about *which credentials were used to commit*, and
neither identifies which agent did the thinking.

So the honest rule for this serial, and the one it applies throughout: **attribute by path, SHA and
diff; use the author field only as a fact about configuration.** When an agent's report and the
repository agree, say so and cite both. When they disagree, publish both rather than picking the
flattering one.

There is a third case, and the earlier draft of this document was it: the agent reports work, the
repository shows nothing *yet*, and the correct sentence is neither "delivered" nor "lied" but "no SHA
existed at the time of measurement". §8.1 is that sentence, corrected.

## 11. The verifier, and what it does not verify
