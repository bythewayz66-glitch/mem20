### Method

Everything below was gathered in this run, from a full clone. The clone is not shallow, and that check
comes first because a shallow clone returns a plausible wrong count with no warning anywhere in its
output:

```
$ git rev-list --count --all

```

Two numbers, two questions. **470** is how much history `main` has. **695** is how many commits exist
in this clone across every ref. Neither is wrong and quoting one for the other is.

## 1. The window, counted on two clocks

The window is `e7758bd1..2ea44922`. On `main`:

```
$ git log --oneline e7758bd178d38da63c5359dded0aada8bfc0eea5..HEAD | wc -l
166
$ git log --all --oneline e7758bd178d38da63c5359dded0aada8bfc0eea5.. | wc -l
391
```

Both queries, side by side, every time. The difference — 225 commits — is not noise. It is the
archive tags and the open branches, and §4 is about exactly that population.

The per-day distribution, taken from `%aI` so the offset travels with the value:

```
$ git log --format='%aI' e7758bd..HEAD | cut -c1-10 | sort | uniq -c
     13 2026-10-27
      4 2026-10-28
     71 2026-10-29
     10 2026-10-30
     56 2026-10-31
     12 2026-11-01
```

Those are **author-local** dates, and the label matters. `--date=format-local` and plain
`--date=format` both format in the process `TZ`, which in a container is frequently UTC even when the
commits carry a `-06:00` offset — so a "local" count written from either can come back identical to
the UTC one and look perfectly correct. Only formats that carry the offset in the value are safe:
`%aI`, `%ai`, `%ad --date=iso-strict`.

The shape of the window is a spike, not a slope. **71 commits on 29 October** is 43% of the window in
one day, and it is not a day of 71 separate decisions. It is a day of scripted work — the
`feat: make N modules first-class` series that the v3.1.0 release notes describe, plus its variants.
The impression a subject-line scan gives is that roughly sixty commits of that kind landed. Counting
is one command and the impression is never right:

```
$ git log --format='%s' e7758bd..HEAD | grep -c 'make .* modules first-class'
```

The number that command returns is smaller than the impression, and the gap between them is the first
lesson of this window: **a category's size is not the density of its subjects.** Ten near-identical
subject lines read as sixty commits of work and are twenty-three.

### The clock that moved inside the window

The window opens at `-06:00` and closes at `-07:00`. That is a daylight-saving transition, and it
means a fixed conversion applied to the whole window is wrong for part of it. The check is per
commit, never per window:

```
$ git log --format='%aI' e7758bd..HEAD | sed 's/.*\([-+][0-9][0-9]:[0-9][0-9]\)$/\1/' | sort | uniq -c
```

Two offsets in that output is the finding, and it belongs in the post rather than in a footnote. It
also means elapsed time must be derived from parsed instants, not from subtracting printed clock
values — a span computed by subtracting two fixed-offset timestamps is wrong by the transition hour.

The frontier's own offset is `-07:00`. The window's opening commit is `-06:00`. Any sentence in this
post that says "five days" is rounding; the exact span is derived in §11's verification script from
`datetime.fromisoformat` on both ends.

### What the window is not

It is not a quiet window, and it is not a clean one. Twenty-one merges landed in it:

```
$ git log --merges --oneline e7758bd..HEAD | wc -l
21
```

Twenty-one merges, 166 commits, and — as §7 shows — a `Tests` check that has been red on the frontier
the whole time. The repository moved a great deal and one of its gates did not move at all.

## 2. The commit that says 162 and landed 155

On 27 October, at 09:39:57 local, a commit landed on `main` with this subject:

```
78d28ad8 Land 162 files from the verified working tree (docs, SDKs, MCP tools, controlz, benchmarks)
```

A subject like that is a claim about a diff, and the first rule of reading this repository is that a
commit's message is not evidence of its diff. So:

```
$ git log -1 --format='%h parents=%p' 78d28ad8
78d28ad8 parents=b44eff6f

$ git show 78d28ad8 --shortstat --format=''
 155 files changed, 16728 insertions(+), 2021 deletions(-)

$ git show 78d28ad8 --name-only --format='' | wc -l
155
```

Three numbers, and they do not agree with the subject. The subject says 162. The diffstat says 155
files changed. The name-only listing says 155 paths. The two measurements agree with each other and
disagree with the prose.

This is not a rounding error and it is not a mystery. It is the difference between a count taken while
the work was being assembled and a count taken from the tree that resulted. Seven files that were
expected to be in the commit were not in it. Whether they were already present, or excluded, or simply
never staged, the commit does not say — and that is the finding, because a commit whose subject
advertises a file count is a commit that invites a reader to trust the count instead of running the
command.

### The parentage is the more important number

`parents=b44eff6f` — one parent. Not a merge.

This matters more than the file count. A single-parent commit that lands 155 files records no merge,
no per-branch decision and no provenance. It records a diff between two trees. The subject describes a
campaign — "the verified working tree" — and the object is a working-tree copy. There is no record in
the commit of which branches contributed, which files came from where, or what was deliberately left
out.

The same shape appears twice more in the same morning:

```
$ git log -1 --format='%h parents=%p %s' 0d9d3a38
0d9d3a38 parents=3f3e470c converge: land the residue from the 9 branches that still held unique files

$ git show 0d9d3a38 --shortstat --format=''
 39 files changed, 3389 insertions(+), 483 deletions(-)
```

"the residue from the 9 branches" — nine branches, one parent, 39 files. The commit names nine
sources and records none of them. A reader who wants to know which nine branches, and whether all nine
were fully drained, cannot answer from the commit. They can only answer from the branch inventory,
which is a different document written two days later by a different agent.

> **What broke.** A commit subject advertised 162 files; the diff contains 155. The commit that
> "landed the residue from the 9 branches" has one parent and names none of the nine.
>
> **What we learned.** A file count in a subject is a claim about a diff, and the diff is one command
> away. The count was wrong by seven and nobody noticed for five days, because the number was
> plausible and the work was real. The provenance gap is the more expensive defect: the files are
> there, but the record of *how they got there* is not, and that record cannot be reconstructed after
> the fact. **Publish the diffstat, not the subject.** And when a commit drains several branches, make
> it a merge or list the branches in the body — a single-parent commit is a copy, and a copy has no
> history.

### The convergence commits that came before the inventory

The 27 October morning also produced a run of commits whose subjects read like a convergence campaign:

```
cc3525d0 converge: land the desktop collision chain (#35 -> #36 -> #37 -> #40)
1fd2399a Add the 8 files that existed only in the local tree (Ruby SDK core, controlz web + tauri)
3f3e470c Fix a corrupted line in mem20controlz/src-tauri/src/lib.rs
0d9d3a38 converge: land the residue from the 9 branches that still held unique files
a366ff74 fix(ops): repair truncated metrics_collector.py and add --since repo-metrics mode (#135)
```

Read as a sequence, this is a recovery operation: a working tree that had diverged from the repository
was being reconciled into it, file group by file group, with the corrupted and truncated files repaired
as they were found. `a366ff74` is the most specific of them — "repair truncated metrics_collector.py" —
and it is the same defect class that recurs in §8, where a 352-line document was found truncated to a
356-byte stub. Truncation is a recurring failure mode in this repository, and it recurs because the
tooling that writes files can fail partway and report success.

The 27 October work is also where the previous instalment's frontier sits. `e7758bd1` is the commit
this post's window opens after, and the convergence campaign above is the first thing in it.

## 3. The convergence: 10 → 3 → 0, and the 1 that is left

`docs/ops/branch-inventory-2026-10-31.md` is a 291-line report by the Analytics Reporter (H12),
measured at 2026-10-31T23:03Z against `main` = `f1672473cd19d5926e1df0c80042259d3b4b17ca`. Its §196
carries the sentence the directive quoted:

> **Result: zero branches ahead of `main`.** The summed at-risk count goes **10 → 3 → 0**, and the
> deduplicated union goes **10 → 3 → 0** with it.

That sentence is the end of a three-stage argument, and the argument is worth reading in full because
the report is unusually careful about what it has and has not done. §6 of the report is headed:

> **This section is a staged replay, not a landed state.** Repository protocol
> (`docs/handoff/AGENT-OPERATING-PROTOCOL.md:136,140`) is *"Never commit to `main` directly"* and
> *"The human owner merges. Agents open PRs."* No merge was performed by this run, and no branch was
> mutated. The tables below come from replaying the merges on a scratch branch in a local clone, so the
> `ahead = 0` result is **proven reachable, not proven achieved**.

So the 10 → 3 → 0 is a *simulation*. Stage A is a pre-flight `git merge-tree` over unmodified trees.
Stage B merges the six mechanically-clean branches onto a scratch commit `65daa741` and measures 3
remaining. Stage C resolves the two conflicts in favour of the branch and measures 0.

The report is explicit that this is not a landed state, and it is explicit about the two conflicts:

> Both conflicts are **expected and mechanical**: PR #145 already landed the same purge on `main`, so
> these two branches now edit lines `main` has rewritten. Neither is a real disagreement about content.

That is the honest form of the claim, and it is the form the directive then compressed into
"10 → 3 → 0". Compression is where the qualifier gets lost. A reader who meets the arrow without the
paragraph above it will believe the branches were merged. They were not — not by that run.

### The one that is left

`docs/ws1-owner-directive-2026-11-01` is one commit ahead of `main` and zero behind. That commit is
`06fa1220` — the owner directive itself, the document that commissioned this post.

So the convergence is not 0. It is **1**, and the 1 is the directive. The inventory's `TOTAL_AHEAD=0`
was true of its own eight branches on its own day; it is not true of the repository on 1 November, and
the difference is a document that was written after the inventory and never merged.

This is worth stating plainly because it is the kind of fact a summary loses. A post that reported
"convergence achieved, 0 at-risk" would be quoting a document correctly and describing the repository
falsely. The repository has one at-risk commit, it is the commission, and it is one `git merge` from
being safe.

> **What broke.** A staged replay was compressed into a result. The inventory said "proven reachable,
> not proven achieved" in §6 and "zero branches ahead" in §196, and the second sentence travelled
> further than the first.
>
> **What we learned.** A simulation and a measurement produce the same table and mean different
> things. When a report contains both, the qualifier has to travel with the number or the number
> becomes a claim about a state that was never reached. The repair is not to delete the arrow — the
> replay was correct and useful — but to keep the sentence that says which kind of zero it is.
> **A zero is only a measurement if something was measured.**

### The branch that was rewritten out of existence

The inventory's §5 records a finding that belongs in this post's failure thread because it is a
data-integrity issue rather than a bookkeeping one:

> **`-5` — the branch was rewritten, not extended.** The stated head `1df637d6…` **does not exist in
> the repository**. `git cat-file -t 1df637d6` returns nothing; the branch head is now
> `de37968ac72cb89e9dd555bb67923220e959a260`. Those 5 commits are not "still unmerged" — they were
> force-pushed away and replaced by a single squashed commit. **The assignment's count could not be
> reproduced because the history it measured no longer exists.**

Five commits were force-pushed away. They are not recoverable from the repository, and the report says
so rather than reporting the new number as if it were the old one. That distinction — "unreproducible"
versus "outdated" — is the difference between a measurement and a guess, and the report draws it
explicitly.

The same section records the opposite error in the other direction:

> **`+1` — the rebuild branch gained a commit.** `faf9cef3` (FAQ source fix) was pushed on top of

> **conflicting intent**: `faf9cef3`'s own message says the regenerated bundle is *not* in the commit,

Two commits on one branch, each asserting the opposite about whether a build artifact is included. The
report's finding 5 says what to do about it — "Verify which bundle ends up in `docs/app/assets/` before
the site rebuilds — a wrong answer here 404s the live app" — and that is the correct instruction,
because the commit messages cannot settle it. Only the tree can.

### 27 is not a property of the code

`docs/ops/surface-measurement-2026-10-31.md` is an independent measurement taken at
`8f0a310d5dbcb77e92188dd2312516d47ea0bffd`, and its verdict table is blunt:

| Claim under test | Result | Status |
|---|---|---|
| 270 unique tools | **270** | **CONFIRMED** by two independent methods |
| 28 `register_*_tools` groups | **28** | **CONFIRMED** |
| 27 domains | **not reproducible from the code** | **REFUTED as a code-derived number** |
| Which group is "not a domain" | **`register_a2a_tools`** | named below, with evidence |

> **The repo ships 270 tools across 28 registration groups.** "27 domains" is an editorial subtraction
> performed by `docs/TOOL-DOMAINS.md`, not a property the code exposes.

That is the finding, and it is a good one, because it separates two numbers that had been travelling
together. 270 is measured. 27 is a decision — someone looked at 28 registrars, decided that
`register_a2a_tools` is an inter-agent transport rather than a tool domain, and subtracted it. The
subtraction is defensible. It is not a measurement, and `docs/TOOL-DOMAINS.md` presents it as one:

> **270 tools across 27 domains.** This file is the ground truth for both numbers. It is generated from
> the registry itself, not hand-counted, so it cannot drift silently.

"Generated from the registry itself" is true of 270 and false of 27. The 27 comes from a table row
that reads `minus the A2A Hermes layer | −1 | register_a2a_tools — an inter-agent transport, not a tool
domain`. That is an editorial judgement written in the grammar of a derivation.

different kinds rather than two greps.

### The duplicate that is not a duplicate

`docs/ops/tool-count-270-27.md` explains the 271 → 270 gap:

> `lie_status` is assigned twice — `mcp/tools/lie_tools.py:69` and `:77`. The second assignment
> overwrites the first, so the server exposes 270 tools while the source contains 271 assignments.

The line numbers are right. The mechanism is wrong. Here is the code:

```python
    def register_lie_tools(self):
        if not LIEZ_AVAILABLE:
            # Still register a status tool so the absence is visible
            self.tools["lie_status"] = mt.Tool(
                name="lie_status",
                title="Lie / Behavioural Signal Status",
                description="Report whether mem20liez is available",
                inputSchema={"type": "object", "properties": {}},
            )
            return

        self.tools["lie_status"] = mt.Tool(
            name="lie_status",
            title="Lie / Behavioural Signal Status",
            description="Report mem20liez availability and active sessions",
            inputSchema={"type": "object", "properties": {}},
        )
```

The first assignment is followed by `return`. The two assignments are **mutually exclusive branches**,
not an overwrite. Exactly one executes, always. There is no defect here at all — the pattern is
deliberate and correct: register a status tool either way, so that a missing optional dependency is
visible to a client rather than silently absent.

So the arithmetic reconciles (271 sites, 270 distinct, 270 at runtime) and the stated cause does not.
The document says "the second assignment overwrites the first", which would be a bug worth fixing. The
code says "one branch or the other", which is a design worth keeping. A reader who trusted the ops note
would go looking for a defect that is not there, and might "fix" a correct pattern.

> **What broke.** An ops note explained a real 271-vs-270 gap with a mechanism that is not in the code.
> The numbers were right; the cause was invented by reading two line numbers and not the control flow
> between them.
>
> **What we learned.** A count discrepancy has a cause, and the cause is a claim like any other. Two
> assignments to the same key look like an overwrite until you read the `return` between them. The
> note's own conclusion — "This run did **not** fix it: removing a tool registration changes the
> exposed schema, which is a behaviour change and belongs with the tests" — was the right call for the
> wrong reason, and it is the reason the wrong explanation survived: nobody was going to touch the code
> to check. **Read the control flow, not the line numbers.**

### What the 27 actually costs

None of this makes the launch page wrong to say 27 domains. It makes the word "domain" a product
decision rather than a code fact, and the cost of blurring that is specific: when the next registrar is
added, 270 will move by measurement and 27 will move by whoever remembers to edit the table. One of
those two numbers is self-maintaining and the other is not, and the document that presents both as
"generated from the registry itself" has removed the reader's ability to tell which is which.

The honest sentence is: **270 tools across 28 registration groups, presented as 27 domains because the
A2A transport layer is not counted as a domain.** That sentence is longer and it is checkable.
