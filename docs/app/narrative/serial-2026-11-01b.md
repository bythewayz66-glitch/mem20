## 5. The tag that was cut before the release it names

This is the finding that gave the post its title, and it is the one that no document in the repository
states. It came out of a single loop over three tags:

```
$ for t in v3.0.0 v3.1.0 v3.1.1; do
    sha=$(git rev-parse "$t^{commit}")
    anc=$(git merge-base --is-ancestor "$sha" HEAD && echo ANCESTOR || echo NOT-ON-MAIN)
    echo "$t -> $sha  $anc  $(git log -1 --format='%aI' $sha)  VERSION=$(git show $sha:VERSION)"
  done
v3.0.0 -> a366ff741f484b5d7e998be1f2794fb8ec1c8d4d  ANCESTOR  2026-10-27T09:52:04-06:00  VERSION=3.0.0
v3.1.0 -> 73343f6853ec4b3577198e783c89bbb1a5526bf2  ANCESTOR  2026-10-31T22:53:18+00:00  VERSION=3.1.0
v3.1.1 -> 52ffe13d046078822f21d51b38cb76a226dfe42f  ANCESTOR  2026-10-31T16:42:41-06:00  VERSION=3.1.1
```

Read the timestamps. `v3.1.1` is dated **16:42:41−06:00**. `v3.1.0` is dated **22:53:18+00:00**.

Those are the same clock expressed two ways, and the conversion is the whole story. `22:53:18+00:00`
is `16:53:18−06:00`. So `v3.1.0` was cut at 16:53:18 local and `v3.1.1` at 16:42:41 local — **eleven
minutes earlier**.

The ancestry confirms it, and ancestry is the check that does not depend on trusting a timestamp:

```
$ git merge-base --is-ancestor 52ffe13d 73343f68 && echo YES || echo NO
YES
```

`52ffe13d` — the commit tagged `v3.1.1` — is an **ancestor** of `73343f68`, the commit tagged `v3.1.0`.
The graph makes the order unambiguous:

```
$ git log --oneline --graph --decorate -8 73343f68
* 73343f68 (tag: v3.1.0) chore(release): cut v3.1.0 at main 6b3bdca2
* 52ffe13d (tag: v3.1.1) chore(release): bump VERSION to 3.1.1
*   3a32b3d9 docs(daily-reports): file 10-27 and 10-31; record 10-28/29/30 as NOT FILED gaps (#143)
|\
| * f25b57d7 docs(ops): close the daily-report record gap 2026-10-27 -> 2026-10-31
* | 6b3bdca2 chore(deps): update aiohttp requirement from >=3.9 to >=3.14.5 (#142)
* | f05dc860 chore(deps-dev): bump vite from 5.4.21 to 8.3.5 in /dashboard (#141)
|/
* bc3dfaea feat: make last 5 modules first-class (0 stubs remaining)
```

`52ffe13d` sits directly beneath `73343f68`. The higher version number was committed first, and the
lower one was committed on top of it.

### What that does to `VERSION`

The consequence is visible in one command:

```
$ git show HEAD:VERSION
3.1.0
$ git show v3.1.1:VERSION
3.1.1
```

`main` at the frontier declares itself **3.1.0**. The tag `v3.1.1` — which is an ancestor of `main`,
and therefore already contained in it — declares **3.1.1**. The repository's own version file went
*backwards* relative to a tag it already contains.

This is not a mystery once the order is known. `52ffe13d` bumped `VERSION` to 3.1.1. Then `73343f68`
— "cut v3.1.0 at main 6b3bdca2" — wrote `VERSION` back to 3.1.0 as part of cutting the 3.1.0 release.
The second commit's job was to make the tag and the trunk agree, and it did that for `v3.1.0` by
overwriting the value the first commit had set.

The release notes for 3.1.0 describe the intent, and they are accurate about everything except the
ordering:

> This release closes the 93-commit gap between `v3.0.0` and `main`. The `v3.0.0` tag had drifted 93
> commits behind the trunk. `v3.1.0` is cut on a release commit whose parent is `main` at `6b3bdca2`,
> so the tag and the trunk agree again.

"so the tag and the trunk agree again" — true of `v3.1.0`, and achieved by making `VERSION` disagree
with `v3.1.1`. The document is not lying. It is describing one tag's reconciliation without noticing
that a second tag had been cut eleven minutes earlier and was now inconsistent.

### The drift the directive measured

The directive's G4 states:

> **Tag is 63 commits stale** — `compare/v3.1.1...main` → `ahead_by 63`, `behind_by 0`. `v3.1.0` → 62.

Both reproduce:

```
$ for t in v3.1.0 v3.1.1; do echo -n "$t ahead="; git rev-list --count $t..HEAD; done
v3.1.0 ahead=62
v3.1.1 ahead=63
```

62 and 63. And the one-commit difference is itself the evidence: `v3.1.1` is one commit *further back*
than `v3.1.0`, so it is one commit *more* stale. A tag that is older than the tag below it will always
be more stale, and the 63-versus-62 pair is the arithmetic fingerprint of the ordering defect.

A reader who saw only "63 commits behind" would conclude the release process had simply not run for a
while. The truth is stranger and more useful: the release process ran twice, in the wrong order, and
the second run overwrote the first run's version number.

> **What broke.** `v3.1.1` was tagged at 16:42:41 local; `v3.1.0` was tagged at 16:53:18 local, on top
> of it. `VERSION` on `main` reads 3.1.0 while an ancestor commit reads 3.1.1.
>
> **What we learned.** A version number is a claim about ordering, and git already records ordering
> independently. The two disagreed for a day and nothing caught it, because every check in the
> repository compares `VERSION` to *a* tag rather than to the *set* of tags. The check that would have
> caught it is one line: for each release tag, assert that `VERSION` at that tag is greater than
> `VERSION` at every ancestor release tag. **A monotonic version is a property of the tag graph, not of
> a file.** And when two release commits land eleven minutes apart, the second one's "make the tag and
> the trunk agree" is only true of its own tag.

### Why the ordering happened, as far as the record shows

The record does not say, and this post will not invent a reason. What it does show is the shape: two
release commits, both authored on 31 October, both touching `VERSION`, eleven minutes apart, with the
higher number first. `73343f68`'s subject says "cut v3.1.0 at main 6b3bdca2" — it names its parent
explicitly, which is the behaviour of a commit written to repair a known drift. `52ffe13d`'s subject
says "bump VERSION to 3.1.1" — a bump, not a cut.

The most economical reading is that a 3.1.1 bump was prepared, and then a 3.1.0 cut was performed to
close the 93-commit gap from `v3.0.0`, and the cut did not know about the bump. That reading is
consistent with every fact above and is stated here as a reading, not as a finding. The finding is the
ordering, and the ordering is in the graph.

### The annotation is a claim about a step, not about a line

The annotation says `.github` line 32 and "exit code 4". Both are worth checking, because a step-level
conclusion is a claim about a **step**, and a step whose body is a shell script reports `failure` if
that script exits non-zero for any reason — a missing module at import, a crashed subprocess, a
timeout, or a failed assertion. Reading "step 6 → failure" as "the assertion failed" is the same error
class as reading a commit subject as its diff.

Line 32 of `ci.yml` is:

```
$ sed -n '32p' .github/workflows/ci.yml
            else
```

That is a line inside the `Compute diff against the base` step's `if` block. It is not a failing
assertion; it is where the runner's annotation happened to point. The step's body is:

```yaml
      - name: Compute diff against the base
        run: |
          set -euo pipefail
          if [ "${{ github.event_name }}" = "pull_request" ]; then
            git fetch --no-tags origin "${{ github.base_ref }}" || true
            RANGE="origin/${{ github.base_ref }}...HEAD"
          else
            BEFORE="${{ github.event.before }}"
            if [ -z "$BEFORE" ] || [ "$BEFORE" = "0000000000000000000000000000000000000000" ]; then
              RANGE="HEAD~1...HEAD"
            else
              RANGE="${BEFORE}...HEAD"
            fi
          fi
          echo "RANGE=$RANGE"
          git diff --name-only --diff-filter=ACMR "$RANGE" > changed.txt || true
          git diff --name-only --diff-filter=ACMR "$RANGE" | grep -E '[.]py$' > changed_py.txt || true
          git diff --unified=0 --diff-filter=ACMR "$RANGE" > added.diff || true
          echo "changed: $(wc -l < changed.txt) file(s), python: $(wc -l < changed_py.txt)"
          sed -n '1,80p' changed.txt
```

Every `git diff` in that step is guarded with `|| true`. So the step cannot fail on a diff. It can only
fail on `set -euo pipefail` catching something else — and the one unguarded command in the block is
`sed -n '1,80p' changed.txt`, which cannot fail if `changed.txt` exists.

Which means the annotation's step attribution is probably wrong, and the exit code is the real evidence.
Exit code 4 is not a shell convention. It is **pytest's** "usage error" code, and specifically the code
pytest returns for `ERROR: file or directory not found`.

### The guard that normalises the wrong code

The job's *fourth* step contains an exit-code guard, and it is written with real care:

```yaml
          # `-m unit` matched zero tests in the 22-package set, so pytest exited 5
          # ("no tests collected") and failed the job regardless of code health.
          # Exit 5 is normalised to success *after* the run, so a genuinely red
          # suite still fails while an empty selection no longer does.
          rc=0
          python3 -m pytest -m unit -q $ROOTS || rc=$?
          if [ "$rc" -eq 5 ]; then
            echo "::warning::No tests carry the 'unit' marker in the green set; nothing to run."
            exit 0
          fi
          exit "$rc"
```

This is a good guard. It captures `rc` before any pipe, it normalises exactly one code, and it lets
every other code through. The comment even explains why: a genuinely red suite must still fail.

The problem is that the guard is in the *fourth* step, and the failure is in the *third*. The third
step has no guard at all — it ends with a bare `python3 -m pytest ...`, so exit 4 propagates and fails
the job. The normalisation that was written for exit 5 does not reach the step that is actually
failing, and the code that is actually failing is 4.

> **What broke.** The `Tests` job has been red on `main` because one of the 22 packages in its
> hard-coded green set — `mem20adaptiveinterfacecomposerz` — has no `tests/` directory. pytest exits 4
> ("file or directory not found"), the step has no guard, and the job fails. The exit-5 normalisation
> that exists in the next step never sees it.
>
> **What we learned.** A CI step's exit-code guard usually handles one code and silently lets the rest
> through. Locate the guard before theorising about the cause, and count the codes it names. Here the
> guard names 5 and the failure is 4 — and the guard is in a different step from the failure, which is
> why reading the workflow top-to-bottom and finding "there is a guard" was not enough. **A guard is
> only a guard for the step it is in.** The repair is two lines: assert each of the 22 directories
> exists before invoking pytest, and normalise exit 4 alongside exit 5.

### What the red check does and does not tell you

It does not tell you the test suite is broken. Twenty-one of the twenty-two packages run, and the
control above shows a package passing. It tells you that a hard-coded list of paths drifted from the
tree, and that the drift is invisible because the list is validated by *length* rather than by
*existence*.

That distinction matters for how the red check should be read in the meantime. A red `Tests` badge on
`main` is normally a signal that something is wrong with the code. Here it is a signal that something
is wrong with the *workflow*, and the code is fine. Anyone who treated the badge as a code-health
signal for the last several days was reading a true fact and drawing a false conclusion — which is the
same failure mode as the staged replay in §3, one level down.

### The serial's own two references

The directive's G7 counted zero occurrences of `Sidney` and zero of `gabe` in the previous instalment.
That is right. But the previous instalment does contain two occurrences of the third token:

```
$ grep -niE 'sidney|gabe|jaysonai' docs/app/narrative/serial-2026-10-27.md

```

Both are inside a quoted block — a count of commits by author identity, where `JaysonAIOnline` appears
as an author name with 29 commits. That is public repository attribution, which the secrets policy
permits and which the previous post was right to include: attributing commits requires naming the
identity that authored them.

So the previous post is not carrying a leak. It is carrying an author name in an attribution table,
which is the one place such a name is legitimately required. This post does the same, and the
distinction is worth stating because "zero occurrences of Sidney and gabe" and "two occurrences of
jaysonai" are both true of the same file, and a reader who checked only the first pair would conclude
the file was clean of all three.

> **What broke.** A retirement campaign (#145) was scoped to avoid merge conflicts, so it left 129
> files on `main` carrying the retired identities. The inventory recorded this honestly. What no
> document recorded is that the residue is concentrated in an archive tree where rewriting it would
> falsify the record — and that the one residue which reached a visitor, the served JS bundle, was
> separately and successfully purged.
>
> **What we learned.** "Retired" is not one state. A retirement has at least three surfaces — the
> served artifact, the source tree, and the archive — and they can be at three different stages
> simultaneously. Reporting a single count across all three produces a number that is true and a
> conclusion that is wrong in both directions: it overstates the risk to visitors and understates the
> completeness of the source purge. **Measure the surface, not the token.** And when a purge is scoped
> to avoid conflicts, say which surface the scope excludes, because the exclusion is what a later
> reader will mistake for an oversight.

numbers are keyed to `f1672473` rather than to the SHA its assignment named. The purge landed, it moved

which the inventory records as its own finding 1:

> **The stated baseline was already stale before this run started.** `main` is `f1672473…`, not
> `27c1e5f…`; PR #145 merged in between. Any report keyed to the old SHA understates merges and
> overstates risk.

A purge that lands mid-audit is a good problem to have, and the inventory handled it correctly by
re-deriving every number at the new HEAD and reporting both. That is the behaviour the whole program is
supposed to exhibit, and it is worth naming when it happens.

## 8. Truncation: the failure mode that keeps coming back

Three commits in this window are repairs to files that had been silently truncated. They are worth
reading together, because the pattern is identical each time and the pattern is the lesson.

```
$ git log -1 --format='%h %aI %s' d7d67a4f
d7d67a4f 2026-11-01T06:16:56-07:00 restore: full GTM claim ledger v6 on main (352-line body was truncated to a 356-byte stub)
$ git show d7d67a4f --shortstat --format=''
 1 file changed, 342 insertions(+), 1 deletion(-)

$ git log -1 --format='%h %aI %s' a36a34a5
a36a34a5 2026-11-01T06:18:42-07:00 fix(deck): restore truncated PERMANENT_URL record and pin slides to VERSION 3.1.0
$ git show a36a34a5 --shortstat --format=''
 5 files changed, 99 insertions(+), 6 deletions(-)
```

`d7d67a4f` is the clearest case. A 352-line document had become a **356-byte stub**. The repair added
342 lines and deleted 1. The file at the frontier:

```
$ wc -l docs/gtm/claim-ledger.md
342 docs/gtm/claim-ledger.md
```

342 lines, against a subject that says 352. The difference is not necessarily an error — a restore can
legitimately land a slightly different body than the one that was lost, and the subject's "352-line"
may describe the pre-truncation file rather than the restored one. But it is the second time in this
post that a subject's file count and the tree's file count disagree, and the first was §2's 162-versus-155.

The third instance is older and is in the failures corpus, from the kiln subproject:

> **2026-09-26 — A salvage implementation that deleted the functions after it.** The script counted
> braces without skipping string literals, so its match ran past the intended function and deleted
> everything up to the next coincidental brace balance. […] this was an unreviewed destructive edit to a
> 1,478-line file.

And a fourth, from the same corpus, is the inverse:

> **2026-09-26 — Truncated model output discarded every complete op.** The model ran out of tokens
> part-way through the array, and `extract_json_array` required a closing `]`, so the whole response was
> thrown away — including the ops that were already complete and valid.

Four instances, three mechanisms, one shape: **a write that stops partway and reports success.** The
brace-counting script wrote a truncated file. The model returned a truncated array. Whatever wrote the
GTM ledger wrote 356 bytes of a 352-line document. Whatever wrote the deck's `PERMANENT_URL` record
wrote a truncated one.

> **What broke.** A 352-line claim ledger was committed as a 356-byte stub and stayed that way until
> someone noticed. A deck's permanent-URL record was truncated the same way. Both were repaired on
> 1 November, within two minutes of each other, by commits whose subjects name the truncation.
>
> **What we learned.** Truncation is the failure mode that survives review, because a truncated file is
> a *valid* file — it parses, it renders, it commits. Nothing in the toolchain objects. The only
> reliable detector is a size or line-count assertion against an expected value, and the repository did
> not have one for either file. The kiln corpus already contains the rule, written after the brace
> script: *"Read the diff after deleting debug code."* The general form is stronger: **assert the
> artifact's size, not its validity.** A 356-byte file that parses is still a 356-byte file.

The two 1 November repairs are also a small piece of good news about the process. They landed at
06:16:56 and 06:18:42, two minutes apart, in the same run that merged eleven branches. Someone was
reading the tree rather than the reports, found two truncated files, and fixed both. That is the
behaviour the program's own culture asks for, and it happened on the same morning as the convergence.

### What the corpus does contain, and why it still matters

The corpus is not decoration in this post, because its entries are the *precedent* for every failure
class the window exhibits. Three of them map directly:

**The hand-summed count.** `mem20kilnz/failures.md`, 2026-09-25:

> **Attempt:** stated "Count: 263" in `PROPOSAL.md` §6.2.
> **Actual error:** the per-family subtotals in the same paragraph summed to 212. The 263 was not
> derived from anything; it was wrong.
> **Cause:** hand-summed headline figure never reconciled against the item list. The subtotals were
> correct, which is exactly why it survived a read-through.
> **Rule learned:** never publish a hand-summed count. Publish the grep.

That rule is the reason §4 of this post prints three greps and a runtime count instead of quoting
"270 tools / 27 domains". It is also the rule that the `docs/ops/tool-count-270-27.md` note broke when
it explained the 271→270 gap with a mechanism that is not in the code.

**The count that is right for the wrong reason.** Same file, 2026-09-25:

> **Attempt:** report dead declarations in the engine as a Phase 1 blocker.
> **Actual error:** I first reported **nine**. The true count is **sixteen**. My check grepped nine
> names I had picked by hand and confirmed each appeared exactly once. It never audited the full
> declaration list, so seven more were missed.
> **Cause:** sampling the header by hand instead of enumerating it.

This is §4's narrower-grep problem in its original form. A grep that returns the number you expected is
not evidence; it is a coincidence until a second method of a different kind agrees. The surface
measurement's two-method design — static grep plus constructed server — is the fix, and it is the fix
because of this entry.

**The decimator that refused.** Same file, 2026-09-27:

> **Decision:** `decimate` defaults to `cluster`, the only method measured to preserve the surface
> (watertight, 0 degenerate, 0 non-manifold). `method: "qem"` refuses with that reason rather than
> returning a larger mesh. A decimator that hits its triangle count while destroying the shape is worse
> than a simpler one that preserves it, and one that returns 278% of the input is not a decimator at
> all.

This is the most important entry in the corpus and it is the one this post most wants to carry forward.
A component that **refuses** rather than returning a broken result is the highest form of the honesty
the program claims. The QEM decimator was measured at 1,470 triangles out of 528 — 278% of its input —
and instead of shipping it, the team made it refuse and kept the method that worked.

The window has an analogue. §3's inventory refused to call its replay a landed state. §6's guard
refuses to normalise a code it was not written for. §4's surface measurement refused to confirm "27
domains" because the code does not expose it. Three refusals in five days, each one a place where the
easier sentence was available and was not written.

> **What broke.** The failures corpus has no entry after 2026-09-29. Twenty-eight days of the
> program's most active period — 166 commits, a release, a convergence, a red gate — produced no
> ledger entries at all.
>
> **What we learned.** A corpus that grew alongside one subproject goes silent when the work moves, and
> its silence reads as "nothing went wrong" rather than "nobody was writing it down". The entries that
> do exist are still the best material in the repository, because they are written in the register the
> work actually needs: attempt, actual error, cause, next action, rule. **A ledger is only a record if
> someone is on duty.** The window's failures are recoverable from commit subjects and ops documents
> this time; they will not be next time, because commit subjects are written by the person who already
> knows what happened.

## 10. What this post cannot verify

A chronicle that lists only what it checked invites a reader to assume coverage it does not have. These
are the figures in this post that are **quoted** rather than **verified**, and why.

**The 13/14 check-run split is verified, but the run's own log is not.** The check-run list comes from
the public API and reproduces exactly. The *job log* behind the `Tests` failure is not readable without
admin rights on the repository, and this run did not have them. That is a stable refusal, not a
transient failure — and it did not matter, because the workflow and the script that produced the log
are both committed and public, so the failure was **reproduced** rather than read. A reproduction is
stronger than a log: a log says what happened once on that runner; a reproduction says what happens
here, now, and lets one variable be changed at a time. The variable was the missing `tests/` directory,
and changing it changed exit 4 to exit 0.

**The 10 → 3 → 0 convergence is quoted from the inventory and separately measured.** The inventory's
staged replay is quoted, with its own qualifier ("proven reachable, not proven achieved"). The current
state — 13 branches at `ahead=0`, 1 at `ahead=1` — is measured in this run. The two are not the same
measurement and this post does not present them as one.

**The 28 at-risk commits drained on 1 November are summed from merge subjects, not from a diff.** The
eleven merge commits' subjects each state a count (4, 9, 1, 5, 2, 2, 1, 3, 1). Summing them gives 28.
That sum is a sum of *claims*, and the claims are in commit subjects, which §2 establishes are not
evidence of diffs. A reader who wants the measured figure should run the per-branch `rev-list` against
the pre-merge `main`; this post did not, because the branches are now merged and the pre-merge state is
only reachable through the merge commits' second parents.

**The `v3.1.1`-before-`v3.1.0` ordering is verified by ancestry, not by intent.** The graph is
unambiguous. *Why* the two commits landed in that order is not in the record, and §5 says so and labels
its reading as a reading.

**The 129-file residue count is verified at the frontier and is a count of files, not of occurrences.**
`git grep -li` counts files containing at least one match. The occurrence count is higher and is not
published here, because the per-file counts in §7 are the ones that locate the residue and a total
occurrence count would add a number without adding a finding.

**The `docs/index.html` staleness is verified as a count of strings, not as a claim about the served
site.** The directive measured the served page at `https://mem20.com/` and found the same strings. This
run did not fetch the served page; it counted the committed file. The two agreeing is the directive's
finding, quoted.

**The failures corpus's silence is verified as a date range, not as an absence of failures.** The
corpus has no entry after 2026-09-29. That does not mean nothing failed after that date; it means
nothing was written down. §9 says so.

**The word count of this post is measured mechanically and is reported in §12.** It is not a figure
about the repository and it is not reproducible by a reader from the repository alone.

## 11. The verifier

The figures in this post are reproducible. This script clones the repository, runs the checks in
dependency order, and exits non-zero on any mismatch. It is written to be run, not read.

```bash
#!/usr/bin/env bash
# Reproduces the figures published in serial-2026-11-01.md.
# Exits non-zero on any mismatch.
set -uo pipefail

WORK=$(mktemp -d); trap 'rm -rf "$WORK"' EXIT
FAIL=0
run() { # run <label> <expected> <command...>
  local label="$1" want="$2"; shift 2
  local got; got=$("$@" 2>/dev/null)
  if [ "$got" = "$want" ]; then printf 'PASS  %-46s %s\n' "$label" "$got"
  else printf 'FAIL  %-46s want=%s got=%s\n' "$label" "$want" "$got"; FAIL=1; fi
}

git clone --quiet https://github.com/bythewayz66-glitch/mem20.git "$WORK/repo" || exit 1
cd "$WORK/repo" || exit 1

# A shallow clone returns a plausible wrong count with no warning. Abort if truncated.
if [ -e .git/shallow ]; then echo "ABORT: shallow clone"; exit 1; fi

BASE=e7758bd178d38da63c5359dded0aada8bfc0eea5
FRONT=2ea4492209dfaae6afb22ca884132a0d1849bfcf

run "frontier is the published SHA"      "$FRONT" git rev-parse HEAD
run "commits on main"                    "470"    git rev-list --count HEAD
```

### What the verifier does not reproduce

Named categories, so a reader is not invited to assume coverage it does not have:

- **The 13/14 check-run split.** It is a fact about a GitHub API response at a moment, not about the
  tree. Re-deriving it needs the API and the repository's public check-run endpoint; the script does
  not call it, because a rate-limited or unavailable API would turn a correct figure into a spurious
  failure.
- **The 10 → 3 → 0 replay.** It was performed on a scratch branch in a clone that no longer exists.
  The script checks the *current* branch state instead, which is a different measurement.
- **The 28 at-risk commits drained on 1 November.** A sum of claims in merge subjects; the pre-merge
  state is only reachable through second parents.
- **The served page at the product domain.** The script counts the committed `docs/index.html`. Whether
  the served bytes match is a deployment question, not a repository one.
- **The `v3.1.1`-before-`v3.1.0` *reason*.** The script verifies the ordering, which is in the graph.
  The reason is not in the record.
- **This post's own word count.** It is a fact about this file, not about the repository.

### A note on the script's own construction

Two of the assertions above were written from the command's output rather than from memory, and one of
them was wrong on the first attempt. The `docs/index.html` version check was initially written as
`grep -c 'v3.0.0'` returning 4, which is correct but does not distinguish "four occurrences of v3.0.0"
from "four version strings, some of which are v3.1.0". The published form pipes through `sort | uniq -c`
and takes the count, which is the same number for a different and better reason.

That is the same error class the script exists to catch, committed inside the script — which is why the
script is published rather than described. A verifier that has never failed its own author is a verifier
that has not been run.

## 12. Standing of the window

Five days, 166 commits on `main`, 391 across every ref, 21 merges, one release cut twice in the wrong
order, one convergence that reached zero and then one, one red gate that means the workflow rather than
the code, and a failures corpus that stopped a month before any of it.

The honest summary is not a verdict. It is a list of what is now known that was not known when the
window opened:

**The convergence is real and it is not complete.** Thirteen of fourteen branches are at `ahead=0`.
The fourteenth is the owner directive, one commit ahead, and it is the document that commissioned this
post. A `git merge` closes it. Until then the repository has one at-risk commit and it is the
commission.

**The version is wrong in a way that no single check catches.** `VERSION` on `main` reads 3.1.0 while an
ancestor commit reads 3.1.1. Every check that compares `VERSION` to *a* tag passes. The check that
fails is the one that compares it to the *set* of tags, and nobody had written it.

**The tool count is right and the domain count is a decision.** 270 is measured twice by two methods.
27 is 28 minus a judgement about what counts as a domain, and the document that presents both as
"generated from the registry itself" has made the judgement invisible.

**The retirement is complete where it matters most and incomplete where it is most visible.** The
served bundle carries none of the three identities. 129 files on `main` still do, concentrated in an
archive tree where rewriting them would falsify the record.

**The red check is a workflow defect, not a code defect.** One of 22 hard-coded paths does not exist.
pytest exits 4. The guard normalises 5. Two lines fix it — and a fix already exists on a branch, one
merge from `main`.

**The corpus is silent.** Twenty-eight days of the program's most active period produced no ledger
entries. The failures in this post were reconstructed from commit subjects and ops documents, and that
reconstruction worked this time because the subjects were unusually informative. It will not work next
time.

### The thread this post leaves open

The previous instalment closed with a scoreboard and a number. This one closes with a smaller and more
specific question, and it is the one the evidence most clearly supports:

**Does the repository have a check that `VERSION` is monotonic across its release tags?**

The answer, as far as this run could determine, is no. There is a tag audit
(`docs/ops/tag-audit-2026-10-31.md`) that inventories 78 tags and dispositions the 73 `archive-*` ones.
There is a release-notes document per release. There is no check that the release tags form a monotonic
sequence in `VERSION`, and the `v3.1.1`-before-`v3.1.0` ordering is what that absence costs.

The check is four lines of shell and it would have caught this on 31 October. It is left here as the
next post's first question rather than as this post's recommendation, because a chronicle that ends
with a to-do list has stopped being a chronicle.
