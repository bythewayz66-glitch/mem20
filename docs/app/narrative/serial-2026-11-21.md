# The Archive That Was Rewritten

**Serial — 2026-11-21** · window: 2026-11-01T13:21Z → 2026-11-21T16:11Z · baseline `2ea4492209dfaae6afb22ca884132a0d1849bfcf` · frontier at publication `105b960213b0e8b0e9f02851bd0e7163eaedf447`

This is the third instalment of the mem20 chronicle. Part one (`serial-2026-11-01.md`) established the
frontier and the convergence from ten at-risk branches to zero. Part two (`serial-2026-11-01b.md`)
took the five findings that needed their own room: the release tag cut before the release it names,
the red `Tests` check, the retired identities still on `main`, the truncation repairs, and a failures
corpus that stopped a month before the window. A publication note
(`serial-2026-11-01-publication-note.md`) recorded that `main` had moved while those two parts were
being written.

This instalment covers the twenty days that followed. It is the largest window the serial has
attempted: **815 commits on `main`**, **151 merge commits**, and a repository that grew from 8,536
tracked files to 11,656. It is also the window in which the project's headline number — the count of
tools the MCP server serves — moved nine times, in which a conformance sweep closed seventy-nine
issues, in which 177 subsystems were absorbed into 56 short runtimes, and in which **the chronicle's
own delivered archive was rewritten by a repository-wide find-and-replace.**

That last fact is the reason this post has the title it has, and it is the first thing to establish,
because it changes how every other figure in this post has to be read.

Every figure below carries the command that produced it, run in this session against a full clone of
`github.com/bythewayz66-glitch/mem20`. Where a figure could not be re-derived, it is labelled
**quoted** rather than **verified**. Where an earlier instalment was wrong, the correction is stated
in place, in the section where the wrong figure appeared, and again in the corrections block at the
end.

## 1. The archive was rewritten, and the serial has to say so first

The previous instalment's publication note is a 500-word document whose entire purpose is to be the
honest record of a moving baseline. It was written on 1 November, after both parts of the instalment
were committed, and it exists because `main` advanced from `2ea44922` to `48c241a1` while the two
parts were being drafted.

It printed this transcript:

```
$ git log -1 --format='%h %aI %s' origin/main
48c241a1 2026-11-01T10:33:30-07:00 chore(release): cut 4.0.0 and land the owner directive

$ git show origin/main:VERSION
4.0.0
```

Both lines are wrong. The commit exists, the timestamp is right, and the subject and version are not.

```
$ git log -1 --format='%h|%aI|%s' 48c241a1
48c241a1|2026-11-01T10:33:30-07:00|chore(release): cut 3.1.2 and land the owner directive

$ git show 48c241a1:VERSION
3.1.2
```

The commit cut **3.1.2**, not 4.0.0. Its own body says so in its first line:

> G1 (red Tests) is already fixed on main by 39554320 / f295e74c — the green set names mem20adaptz
> and Tests is green on that SHA. This commit carries the remaining release work:
> - VERSION 3.1.0 -> 3.1.2 so the tree agrees with the tag being cut
> - CHANGELOG section for 3.1.2 covering the commits since v3.1.1
> - docs/ops/owner-directive-2026-11-01.md landed from docs/ws1-owner-directive-2026-11-01 (06fa1220)
>   so the register is on main

So the note's central exhibit is wrong. The obvious reading — and the one this post was going to
publish before the diff was run — is that the note's author misquoted the commit. That reading is
false, and the way it is false is the story.

### 1.1 The note was right when it was written

The note was committed as `1376fb47`, dated 2026-11-01T10:36:33-07:00, subject *"docs(narrative):
publication note for serial 2026-11-01 — main moved to 3.1.2 mid-run; posts stay pinned to
2ea44922."*

Read the subject. **"main moved to 3.1.2."** The note's author knew the version. The note was
correct.

Then, seventeen days later, commit `0cd80344` — dated 2026-11-18T01:04:50Z, subject *"Replace 3.1.2
with 4.0.0 across repository and include pending workspace changes"* — rewrote it. The diff is five
lines:

```
$ git show 0cd80344 -- docs/app/narrative/serial-2026-11-01-publication-note.md
-48c241a1 2026-11-01T10:33:30-07:00 chore(release): cut 3.1.2 and land the owner directive
+48c241a1 2026-11-01T10:33:30-07:00 chore(release): cut 4.0.0 and land the owner directive
-3.1.2
+4.0.0
-So `VERSION` on `main` is now **3.1.2**, not 3.1.0. The posts say 3.1.0, and they are right to: every
+So `VERSION` on `main` is now **4.0.0**, not 3.1.0. The posts say 3.1.0, and they are right to: every
-of `73343f68` (tag `v3.1.0`). Cutting 3.1.2 on top of both does not reorder them.
+of `73343f68` (tag `v3.1.0`). Cutting 4.0.0 on top of both does not reorder them.
-that `VERSION` is monotonic across its release tags. `48c241a1` cuts 3.1.2, which is higher than both
+that `VERSION` is monotonic across its release tags. `48c241a1` cuts 4.0.0, which is higher than both
```

Five substitutions. Every one of them replaced a true statement with a false one. The note now claims
that a commit dated 1 November cut 4.0.0, which did not exist until 16 November, and it claims this
in a document whose stated purpose is to be the record of what was true on 1 November.

This is not a correction. A correction would have added a line saying the figure had changed. This is
a **retroactive falsification of a dated record**, performed by a find-and-replace that could not
distinguish a live document from a historical one.

### 1.2 The same sweep hit the second part's verifier

The publication note is not the only delivered artefact that was rewritten. Part two
(`serial-2026-11-01b.md`) contains a reproduction script — §11 of that post, a bash verifier that
re-derives the figures the post publishes. On 9 November, commit `d47c75ac` (*"refactor: consolidate
all pipe subsystems into mem20pipez"*) rewrote it:

```
$ git show d47c75ac -- docs/app/narrative/serial-2026-11-01b.md
-                 mem20boxz mem20enginez mem20executablegameconceptandscopepipelinez
+                 mem20boxz mem20enginez mem20pipez
-                 mem20orcaz mem20pipelinez mem20selfz mem20sensorz mem20simz
+                 mem20orcaz mem20pipez mem20selfz mem20sensorz mem20simz
-OK   mem20executablegameconceptandscopepipelinez
+OK   mem20pipez
-OK   mem20pipelinez
+OK   mem20pipez
```

The post's verifier asserted that the green-set package list contained
`mem20executablegameconceptandscopepipelinez` and `mem20pipelinez`. Those packages existed on 1
November. They were consolidated into `mem20pipez` on 9 November. The sweep replaced the names inside
a **published post's reproduction script**, so the script now asserts something about a tree that
never existed: a 1 November tree containing `mem20pipez`.

The consequence is precise and worth stating carefully. Part two's verifier no longer reproduces part
two's figures. It reproduces a hybrid — the 1 November commit graph with the 9 November package
names. Anyone who runs it today gets a result that is neither the post's claim nor the current state.

> **What broke.** Two delivered, dated, pinned instalments of this chronicle were mutated by
> repository-wide sweeps that could not tell a historical record from a live document. The
> publication note was made to state a false version for a commit it correctly identified; part two's
> verifier was made to assert a package list that never coexisted with the tree it checks out.
>
> **What we learned.** The project already knows this failure mode and already wrote the rule. On 8
> November, commit `0eab51ad` is titled *"fix(sweep): stop rewriting the immutable archive and dated
> records."* That commit exists because a sweep had already rewritten dated records once. Six days
> later the sweep ran again, at repository scale, and the only thing standing between it and the
> archive was whatever the operator remembered. **A rule in a commit message is not a control.** The
> control is a path exclusion in the sweep script, and the sweep script did not have one. The
> chronicle's own archive is now the evidence for why the exclusion is needed — which is a poor way
> to acquire evidence, and the only way this one was acquired.

### 1.3 What this does to the rest of the post

It means every figure in this post has to be read as a measurement with a date, and it means the
serial cannot treat its own earlier output as a source. Part one and part two are still the best
record of 1 November that exists, but they are no longer a *pristine* record: two of their passages
have been edited by later commits, and the edits are wrong.

The serial's response is the one it applies to the project: state the frontier, measure at the
frontier, and record the movement separately. This post does that. It also does one thing the
project's own documents do not: it prints the diff that corrupted the archive, so a reader can see
exactly what was changed and by which commit.

## 2. The version that was cut twice, and then rewritten

The window contains two release cuts and one repository-wide rewrite of the version string. They
disagree with each other in a way that is instructive, and the disagreement is the same one that
corrupted the archive in §1.

### 2.1 3.1.2, on 1 November

`48c241a1` is a small commit doing three things: it moved `VERSION` from 3.1.0 to 3.1.2, it added a
`CHANGELOG` section for 3.1.2, and it landed the owner directive from its branch onto `main`.

The interesting part is the first line of its body, quoted in full in §1: *"G1 (red Tests) is
already fixed on main by 39554320 / f295e74c — the green set names mem20adaptz and Tests is green on
that SHA."*

That sentence is the resolution of the red check that part two spent a whole section on. Part two §6
reproduced the failure locally, established that it was a pytest usage error (exit code 4) rather
than a test failure (exit code 1), traced it to a directory named `mem20adaptiveinterfacecomposerz`
that had been deleted in `e9a15295` while `.github/workflows/ci.yml` kept pointing at it, and found
the phantom name in **two** places — line 266 and line 286 — with the second hidden only because the
first failed before it ran.

The fix that landed is the one the second-opinion document recommended, and it is worth recording
that the recommendation was *substitute, not delete*:

> Keep `COUNT -ne 22` intact — `mem20adaptz` replaces the removed entry **one-for-one**, so the
> cardinality contract holds at 22 and the 13 `mem20adaptz` tests join the guarded set (D3).
> **Substitute, do not delete:** deleting drops the count to 21 and trips the cardinality guard at
> `ci.yml:275-279`, failing the job on the next line.

That is a small piece of engineering judgement that deserves its own line in the record. The obvious
fix — remove the name that does not exist — would have turned the check green and *reduced coverage*,
because `mem20adaptz` is the successor package and carries thirteen tests that CI was not running.
The guard that counts names in a string cannot tell the difference between a list of twenty-two real
directories and a list of twenty-two strings, so the cheap fix passes the guard and loses the tests.
Substituting keeps the count and gains the coverage.

> **What broke.** A CI job failed for twenty days with exit code 4, and the failure was read as a
> test failure by everyone who saw the annotation, including the owner directive that assigned it.
> The directive's §2/G1 attributed the failure to the *Compute diff against the base* step. That step
> concluded `success` in CI and replayed clean locally. The real failing step was *Run the green
> package set*.
>
> **What we learned.** Exit code 4 and exit code 1 look identical in a check-run annotation that says
> only "Process completed with exit code 4." The distinction — usage error versus failing assertion —
> is the difference between "the product is broken" and "the invocation is broken," and it changes
> who owns the fix. The second-opinion document earned its place by printing the exit-code table
> before printing any diagnosis. **Publish the exit code's meaning, not just its value.**

### 2.2 4.0.0, on 16 November

The second cut is `7fb3fc32`, dated 2026-11-16T06:37:20Z, subject *"chore(release): bump site to
4.0.0 and apply blocker fixes."* It touches seventeen files with 37,165 insertions and 5,781
deletions, and the bulk of that is the regenerated agent skill catalog:

```
 toolchest/skills/skills.catalog.agent.json |    2 +-
 toolchest/skills/skills.index.agent.json   |    2 +-
 17 files changed, 37165 insertions(+), 5781 deletions(-)
```

Two lines changed in a JSON file and 37,165 insertions in the commit is not a contradiction: the
catalog files are single-line JSON, so a one-line diff to a large document is a large diff. This is
the kind of figure that reads as alarming in a `--stat` and is entirely ordinary once you know the
file format. It is recorded here because a later reader comparing commit sizes will otherwise
conclude that 16 November was a rewrite. It was not. The rewrite was two days later.

### 2.3 The rewrite, on 18 November

The third event is not a release cut. It is `0cd80344`, dated 2026-11-18T01:04:50Z, subject
*"Replace 3.1.2 with 4.0.0 across repository and include pending workspace changes."*

Ninety-seven files, 15,861 insertions, 260 deletions. The subject is doing two jobs at once and the
second one is the one that matters: *"and include pending workspace changes."* A commit that sweeps
unrelated working-tree state into a version bump is the same failure mode the failures corpus records
on 6 November, where a shared working tree meant `git commit` swept another agent's staged files into
`87f4d4e5`:

> **2026-11-06: Shared working tree race** — staging only my files was not enough because another
> agent had already staged its `mem20assistz` files, so `git commit` swept them into 87f4d4e5. NEXT
> ACTION: done — use `git commit --only <paths>` for every commit in a shared tree. The swept files
> were byte-identical to the other agent's staged work, so no content was lost or reverted.

The 18 November commit does not record whether the swept changes were byte-identical to anything. It
records that they were included. That is a weaker statement than the 6 November entry, and the
difference is the point: the 6 November entry could say *no content was lost* because someone
checked. The 18 November entry cannot, and does not claim to.

And this is the commit that rewrote the publication note. The same find-and-replace that moved
`VERSION` from 3.1.2 to 4.0.0 across the repository also moved it across a dated record of what
`VERSION` had been on 1 November. The sweep was correct about the live tree and wrong about the
archive, and it had no way to tell the difference.

> **What broke.** A version-string rewrite landed as a 97-file commit whose subject admits it carried
> unrelated working-tree state, and which retroactively falsified a delivered instalment of this
> chronicle. The commit is not wrong about the live tree — the version string did need replacing —
> but it is unauditable in the way that matters: a reader cannot tell which of the 97 files are the
> rewrite and which are the sweep, and one of them is a historical record that should have been
> excluded.
>
> **What we learned.** The 6 November rule (`git commit --only <paths>`) was written down and then
> not applied twelve days later. A rule in a failures file is not a control. The control is the flag
> in the command, and the only way a rule survives is if the command that violates it is the one that
> feels slower. The same is true of the 8 November rule about not rewriting dated records: it was
> written down, and then a sweep ran without a path exclusion.

### 2.4 What the three events say together

Three version events in twenty days, and the sequence 3.1.0 → 3.1.2 → 4.0.0 is monotonic. The
project's version discipline, judged only by the numbers, improved across the window: the frontier
had a working tree one patch level *behind* its newest tag, and the publication point has a working
tree that agrees with a version higher than every tag before it.

Judged by the mechanism, nothing improved. There is still no check that the release tags form a
monotonic sequence in `VERSION` — the question part two §12 left open, and the answer is still no.
And the 18 November commit shows what happens without one: the version string is corrected by a
repository-wide find-and-replace, which is the correct tool for the job and also the tool that cannot
tell a live document from a historical record.

`VERSION` changed exactly twice in the window:

```
$ git log --format='%h|%aI|%s' 2ea44922..HEAD -- VERSION
7fb3fc32|2026-11-16T06:37:20+00:00|chore(release): bump site to 4.0.0 and apply blocker fixes
48c241a1|2026-11-01T10:33:30-07:00|chore(release): cut 3.1.2 and land the owner directive
```

Two commits, two values, and a third event — the 18 November sweep — that changed no `VERSION` file
because `VERSION` was already 4.0.0. The sweep's job was to make the *rest of the repository* agree
with a file that was already correct. That is the shape of the problem: the authoritative value was
right, and 97 files disagreed with it, and the tool used to reconcile them could not read dates.

## 3. The number that would not hold still

The tool count is the project's headline figure. It appears in the README, the launch page, the
investor deck, the SDK surface guards, the pricing derivation, the finance claims check, and the
positioning line. Across the twenty-day window it took at least nine distinct values, and every one
of them was true when it was measured.

This section is the story of that number, because it is the clearest case in the whole chronicle of a
metric that is real, measured, and useless as a claim.

### 3.1 The values, in order

The frontier value was **270 tools / 27 domains**, established in part one by two independent methods
(271 registration sites, 270 distinct after `sort -u`, and 270 from `len(Mem20MCPServer().tools)`),
with the domain count of 27 marked **quoted** because it was an editorial subtraction rather than a
measurement.

Then, on 1 November, the count moved repeatedly inside a single day. The commit subjects are the
record:

```
5cc304d7|fix(web): count only tools the MCP server actually serves (272, not 282)
d4be3686|ci(mcp): correct stale expected tool count 272 -> 277 (main's actual surface)
b23ba33f|ci(mcp): set expected tool count to 281 (277 on main + 4 from this subsystem)
95495d4d|ci: bump MEM20_EXPECTED_TOOLS 272 -> 290
658b25c0|ci: set MEM20_EXPECTED_TOOLS to measured 294 for this branch
6cc1fcce|ci: set MEM20_EXPECTED_TOOLS to measured 298 for this branch
b4f283d7|ci: set MEM20_EXPECTED_TOOLS to measured 302 for this branch
e8b05216|ci: set MEM20_EXPECTED_TOOLS to measured 306 for this branch
```

Read that list as a sequence of measurements rather than a sequence of corrections. Each line is an
agent measuring the surface on its own branch and finding a different number, because each branch
carried a different set of subsystem additions. `b23ba33f` says it explicitly: *"281 (277 on main + 4
from this subsystem)."* The number is not drifting because anyone is wrong. It is drifting because
the surface is the sum of what is wired, and twenty-two agents were wiring.

There is a second reading of the same list, and it is less flattering. `5cc304d7` says *"count only
tools the MCP server actually serves (272, not 282)"* — which means that at some point before it, the
published figure was 282 and the served figure was 272. Ten tools were being counted that the server
did not serve. That is the same defect that reappears at the end of the window as the 19 unwired
tools in §3.4, and it is worth noticing that it was found and fixed on 1 November and was back by 21
November.

By 2 November the daily ops report records **306 tools / 44 domains**. By 4 November the launch page
and dashboard are updated to **311 / 39**. By 9 November the live surface is **487 / 129**.

### 3.2 The 311/39 plateau

Between 4 and 9 November the number settles at 311 tools and 39 domains, and a great deal of work is
done to make every surface agree with it. The commit subjects from 8 November are almost entirely
convergence:

```
82bca9ba|docs(4.0): converge the renovation plan's house numbers to 311/39
54435ef5|fix(deck): converge deck index, register and record to 311/39
64e23923|fix(deck): converge the tool surface to 311/39 and make slide 04 self-consistent
730271c3|docs(perl-sdk): restore full README with 311/39 on server 3.1.2
376e08c1|docs(cpp-sdk): restore full source-ledger.md (311/39, server 3.1.2)
746f1496|docs(ruby-gem): README states 311 tools / 39 domains on server 3.1.2
```

Six commits, six surfaces, one number. This is what convergence looks like when it is done properly:
not a single edit to a single file, but a sweep across every document that states the figure, each
one carrying the same value and the same server version.

And then, on 9 November, the number is 487 and all of that work is historical.

### 3.3 The jump to 487

The 9 November entry in `DIARY.md` records what happened, and it is not a measurement error:

> **Live surface & stale counts:** verified **487 tools / 129 domains** (`Mem20MCPServer().tools`,
> live). Regenerated `docs/surface.json`, `docs/TOOL-DOMAINS.md`, `web/src/data/tools.json`; aligned
> current-facing docs/SDKs/CI/finance/verify (`verify_mcp.py`, workflows, finance model/inputs
> regenerated, C++/Perl/Ruby surfaces + live tests). `scripts/surface_manifest.py --check-docs` =
> **OK**. Historical records (DIARY/changelogs/dated reports) left as history.

The jump from 311 to 487 is 176 tools, and it is not a bug fix. It is the consolidation described in
§7: subsystems that had been separate packages were absorbed into short runtimes, and each absorbed
member brought its tools with it. The surface grew because the estate was reorganised, not because
anyone had been undercounting.

The last sentence of that diary entry is the one that matters for this section: *"Historical records
(DIARY/changelogs/dated reports) left as history."* That is the correct decision, and it is also the
decision that makes the number impossible to state without a date. A reader who opens a document
dated 8 November and finds 311 is reading a true statement about 8 November. A reader who opens the
same document on 21 November and finds 311 is reading a stale one, and nothing in the document tells
them which.

Note also that this entry is the one place in the window where the archive rule was applied
correctly. The 9 November operator regenerated the live surfaces and explicitly left the dated
records alone. Six days later the 18 November sweep did the opposite. The difference between the two
is not knowledge — both operators knew the rule — it is that one of them was editing a handful of
files by hand and the other was running a find-and-replace.

### 3.4 The number at publication

At the publication point the surface is **487 tools / 129 domains**, with **19 tools unwired**. The
unwired list is in `docs/surface.json` and it is worth printing, because "487 tools" is a claim about
what is registered and the unwired list is a claim about what is not:

```
gateway_admission, gateway_provenance, gateway_translate,
lattice_emit, lattice_recall, lattice_report, lattice_search, lattice_verify,
memory_engine_guard, memory_engine_health, memory_engine_namespace,
memory_engine_recall, memory_engine_subsystem, memory_engine_veto,
stream_publish, stream_recall, stream_report, stream_search, stream_verify
```

Nineteen tools across four families — gateway, lattice, memory_engine, stream — that exist in the
catalog and are not served. The launch-page record from 16 November states the cross-check plainly:

> `docs/surface.json` on main: tools 487, domains 129, unwired_tools 19, cross_check: ast_tools 487,
> ast_domains 129, only_ast empty, only_live empty. Generated from the live JSON-RPC `tools/list`
> response; the AST catalog agrees exactly, with no tool present in one catalog and missing from the
> other.

So the two catalogs agree at 487, and 19 of those 487 are not wired. The number is honest in the
sense that it is measured twice and the measurements match. It is not honest in the sense that a
reader would take "487 tools" to mean 487 tools they can call.

> **What broke.** The project's headline number took nine values in twenty days, and every one was
> correct at the moment it was measured. The consequence is that no document can state the number
> without also stating a date, and almost none of them do. The 8 November convergence — six commits
> making six surfaces agree on 311/39 — was obsolete within twenty-four hours.
>
> **What we learned.** A metric that is the sum of what is currently wired is not a metric; it is a
> snapshot of a build. The project already knows this and already has the tool for it: the doc-count
> drift gate, which scans live docs for a retired tool/domain band and fails if it finds one. That
> gate is the right control, and it is the reason the 16 November launch page could be rebuilt with
> confidence. The lesson is narrower than "keep numbers current": **a number that changes when you
> add a feature must be published with the commit that changed it, or it must not be published at
> all.** The 8 November convergence did the first thing correctly and the second thing not at all —
> it updated six surfaces and left the other eighty-odd documents stating 270.

### 3.5 The house number

There is a fifth value, and it is the one that caused the most trouble: **257 tools / 26 domains**.
This is the "house" figure — the number in the positioning line, the TAM/SAM/SOM model, and the
investor narrative. It was never a measurement of the live surface. It was a number that had been
true at some earlier point and had been carried forward.

The 16 November program status names it as blocker B5:

> B5 | Live surface is **487 tools / 129 domains**, not the house 257 / 26 — positioning line is
> stale (§6).

And §6 of the same document tabulates the correction:

> | "257 tools across 26 domains" | **487 / 129** (`docs/surface.json`, cross-checked against the AST
> catalog); 19 tools unwired — house line is several surface moves stale |

The gap between 257 and 487 is 230 tools, and the gap between 26 and 129 is 103 domains. That is not
a rounding difference. It is the difference between a product description and the product.

> **What broke.** The number used to sell the product was 230 tools and 103 domains away from the
> number the product serves. It was not a lie at the moment it was first written; it was a
> measurement that nobody re-took, carried forward through a reorganisation that nearly doubled the
> surface.
>
> **What we learned.** The project's own rule — "a deliverable exists only as a commit SHA on a
> pushed branch or a permanent URL committed under `docs/`" — has a counterpart for numbers that the
> program had not written down: **a number exists only as a command's output, and it expires.** The
> house figure survived because it lived in documents that no gate scanned. The doc-count drift gate
> scans *live* docs and explicitly exempts historical records, which is correct — but the positioning
> line was live, and it was not in the gate's scope until someone put it there.

*"they will rot."* Twelve branches with no PR, fifty commits, and a five-day window in which the refs

the triage order was a recommendation and the pruning was an operation.

> **What broke.** Fifty commits on twelve branches, with no PR open for any of them, were removed

> is serving. The directive's G2 asked for thirteen *merged* refs to be deleted, which was safe
> because they carried zero unmerged commits. The 16 November state was the opposite: twelve refs

> that (`git merge-base --is-ancestor`) and used it correctly on 1 November. **The lesson is that
> the check has to run at deletion time, not at audit time.** An audit that says "these twelve are at
> risk" is only useful if the deletion is gated on the same check.

## 6. The conformance sweep: seventy-nine issues in two days

The largest single body of work in the window is a conformance sweep that ran on 6, 7 and 8 November
and closed seventy-nine issues. It is the reason the commit count for those three days is what it is,
and it is the clearest example in the window of a program executing a written plan at scale.

### 6.1 The seven criteria

The sweep is organised around a seven-criterion conformance standard, defined in
`docs/renovation/4.0/RENOVATION_PLAN.md`. The plan's exit gate is unambiguous:

> 1. `conformance.py --all --fail-under 1.0` exits 0 — all 211 subsystems at 7/7.

Two hundred and eleven subsystems, seven criteria each. The plan's baseline table records where the
program started:

> | Subsystems fully conformant (7/7) | **6** |

Six of 211 at the start. The plan also names the cheapest win and the reason it should be batched:

> Criterion 5 (README examples) at 30.8% is the cheapest win and should be batched with criterion 6,

And it explains why the substrate had to land first:

> **Why first:** these are the modules every other subsystem must import to satisfy criterion 6. If
> [they are not first], criterion 6 work in waves 2–3 would be built [on sand].

### 6.2 What criterion 6 actually requires

Criterion 6 is the one that caused the most trouble, and the failures corpus records why. From the 6
November entry:

> **2026-11-06:** Conformance criterion 6 still failed after adding genuine cross-module calls
> because the calls sat inside a multi-line dict literal and coverage only marked the assignment
> line. NEXT ACTION: done — every mem20 call in `estate_context()` is now its own statement; the
> gate logs list each call site and report 7/7.

And from 8 November, more precisely:

> Criterion 6 is strict (import AND call on covered line via AST+coverage); guessed peer APIs caused
> missing covered calls

So criterion 6 is not "does this module import a peer." It is "does this module import a peer **and
call it on a line that coverage marks as executed**," verified by AST analysis plus a coverage run.
That is a much harder standard, and it explains the volume of work: every subsystem needed six real
peer integrations, each one a genuine call on a covered line, and each one against a peer API that
had to be discovered rather than assumed.

The failures corpus is full of the API mismatches this produced, and they are the most concrete
evidence in the whole window of what "real integration" costs. A sample, all from 7 November:

> - `mem20simz.simulate_load` returns a list (scaling/bottleneck take the list);
>   `mem20syntheticevaluatorarenaz.create_arena`/`evaluate` use hashable agent/subject IDs (strings),
>   not dicts.
> - `mem20gameproductioncontrolcenterz.milestone_status` takes numeric `due_day/today` and
>   `production_health` expects done/velocity fields; `mem20studioz.resource_allocation` takes
>   `{resource:capacity}` dict and demand `amount`; `mem20simz.funnel` takes stage dicts with
>   `conversion`, `growth_score` takes `viral_k/conversion/retention`.
> - `counterfactualmemorysimulatorz.replay` takes `(memory, steps_list)` not `(memory,int)`.
> - `mem20universalintegrationcompilerz.validate_mapping/transform` need field-mapping shape (not
>   wrapper dict); `mem20ambientteamradioz.send_message` returns `{ok,message}` and mutates channel
>   messages, so adapter must append message to channel before `channel_activity`.
> - `mem20intenttomissioncompilerz.compile_mission` expects intent dict (`goal`/`parts`), not plain
>   string.
> - `collectivemodelintelligencez.ensemble_predict` takes numeric predictions (not dicts);
>   `alternativedatabaseplaygroundz.suggest_index` takes `(columns, cardinalities_list)` and
>   benchmark needs plan dict; `crdtcollaborationenginez` GCounter/PNCounter `value` may be
>   property/callable; `prioritycollisionresolverz.submit(item, priority)` takes 2 args.

Every one of those is a signature that was guessed wrong and then discovered by running the code.
That is the honest cost of criterion 6, and it is worth recording that the standard was not relaxed
to make the sweep go faster. The failures corpus says so explicitly:

> Criterion 6 is strict (import AND call on covered line via AST+coverage); guessed peer APIs caused
> missing covered calls — fixed 336 (BatteryAwareAgentScheduler, energy_cost/greenest_node/
> migration_plan), 337 (offerassemblyfabricz/compoundingproductecosystemz/businessmodelsimulatorz/

> personalworkflowtwinz create_twin/observe/twin_health), 339 (restored leveldesign compile_level_plan
> import, dynamicnarrativeenginez create_story/add_node/current_text, replaced missing

On 7 November, partway through the sweep, the owner intervened, and the failures corpus records it
verbatim:

> **2026-11-07:** User feedback: "stop using shared patterns, use real meaningful implementations."
> Applied from #317 onward: peer integrations composed into domain outcomes (e.g. #317 computes
> production-control report where team presence affects effective capacity, resilience adjusts risk,
> economics/release/forge/assets contribute real sections) rather than only collecting probe
> `signals`. Cross-module calls remain real and covered for criterion 6.

satisfying criterion 6 by *collecting probe signals* — calling six peers and gathering their health
outputs into a `signals` dict. That passes the AST-plus-coverage check, because the calls are real
and on covered lines. It does not produce a subsystem that does anything with its peers.
