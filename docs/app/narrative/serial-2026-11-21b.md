# The Assembler and the Gate That Was Never Built

**Serial — 2026-11-21 (second instalment of the day)** · window: 2026-11-21T16:11Z → 2026-11-21T23:06Z · baseline `105b960213b0e8b0e9f02851bd0e7163eaedf447` · frontier at publication `77b72a1a7eedf7f696e1861da05985db085476b3`

This is the fourth instalment of the mem20 chronicle, and the second to be published on 21 November. The
previous one — *The Archive That Was Rewritten* (`serial-2026-11-21.md`, commit `fcca9535`) — closed at
`105b9602` and ended with a list of things it could not verify. Two of those items were questions about
gates: whether the repository had ever built a check that `VERSION` is monotonic across its release tags,
and whether it had ever built a check that a dated record is not rewritten after publication.

This instalment answers both. The answer, in each case, is no. Neither gate exists. What exists instead
is a skip list, a docstring, and a commit message that says the skip list was incomplete.

It also covers the seven hours between `105b9602` and `77b72a1a`, which turned out to be the most
instructive stretch of process the serial has yet had to describe. In those seven hours, sixty-six
commits landed on `main`. Fourteen of them were attempts to assemble a single Markdown file. Four were
probes to find out whether the write path worked at all. One was a fix to the artifact-evidence gate
that had been failing every CI-maintenance push by construction. And one was a red check that had been
green on the two commits before it.

The window is short and the commit count is high, which is the opposite of the previous instalment's
shape — twenty days and 815 commits. That difference is itself the story. A long window hides its
process in the volume. A seven-hour window with sixty-six commits shows every step, including the ones
that were wrong.

Every figure below carries the command that produced it, run in this session against a full clone of
`github.com/bythewayz66-glitch/mem20` at `main` = `77b72a1a`. Where a figure could not be re-derived, it
is labelled **quoted** rather than **verified**. Where the previous instalment was wrong, the correction
is stated in place and again in the corrections block at the end.

## 1. Where this post begins

The previous instalment closed at `105b9602`, subject *"fix CI: regenerate the two web lockfiles so npm
ci resolves"*. That commit is worth reading in full, because it is the last ordinary commit in the
window — the last one that does a normal thing for a normal reason.

Its message:

```
mem20agentz/web: the lockfile pinned loupe 3.2.1 while @vitest/utils
requires ^4.0.0, so npm ci failed with ETARGET and the npm install
fallback could not resolve it either. Regenerated against vitest 2.1.9.

mem20controlz/.../web: the lockfile was missing the nested
@jridgewell/trace-mapping/node_modules/@jridgewell/resolve-uri@3.1.3
entry, so npm ci failed with EUSAGE (out of sync). Regenerated.

Both verified locally: npm ci && npm run build succeed.
```

Two lockfiles, 503 and 20 lines changed, 295 insertions and 228 deletions between them. The commit
states the error code for each failure — `ETARGET` for the first, `EUSAGE` for the second — and states
that both were verified locally. This is what the repository's commit discipline looks like when it is
working: the defect, the cause, the fix, and the evidence that the fix was checked.

It is also, as it happens, the commit that the artifact-evidence gate would later be taught to exempt.
More on that in §10.

The previous instalment's check-run count for `105b9602` was 15 success and 1 failure, with the failure
being `artifact evidence`. Re-running the check-runs API in this session confirms it:

```
$ curl -s ".../commits/105b9602/check-runs?per_page=100"
  total 16 {'success': 15, 'failure': 1}
   RED: artifact evidence failure
```

Sixteen checks, fifteen green, one red. The red one is the gate that requires every push to carry a
committed artifact as evidence — a 40-character SHA of a pushed branch, or a permanent URL committed
under `docs/`. A lockfile regeneration carries neither, and cannot: the artifact a lockfile pins is
evidenced by the delivery that introduced the code, not by the lockfile itself.

So the gate was red on a commit that had done nothing wrong. That is the first thing to understand about
this window: it opens with a gate failing correctly by its own rules and incorrectly by any reasonable
reading of its purpose.

## 2. The file that took fourteen commits to land

At 11:35:15 -0700 on 21 November, commit `b5107c53` landed:

```
docs(narrative): serial 2026-11-21 — the archive that was rewritten (part 1/5)
```

That is the previous instalment, committed as the first of five parts. It was 4,903 words at that
point — a fraction of the 16,266 it would eventually be.

The reason it was committed in parts is stated in the commit that added the assembler, `35247d5c`:

```
ci(narrative): one-shot assembler for the 2026-11-21 instalment

The publishing API caps a single file write at ~30 KB, so the instalment is
committed in parts and concatenated here. No-op once .parts/ is empty.
```

Thirty kilobytes. The instalment is 101,467 bytes. It could not be written in one call, so it had to be
written in pieces and joined. That is a constraint of the tooling, not a decision of the author, and it
is the origin of everything that follows.

What follows is fourteen commits, all with the subject *"assemble serial 2026-11-21 from parts"* or a
variant, and ten commits that modify the assembler itself. Read in order, they are a complete record of
a small piece of software being debugged in production, one failure at a time, with each failure
described in the commit message that fixes it.

### 2.1 The first assembler, and why it was order-unsafe

`35247d5c` added 51 lines to `.github/workflows/assemble-serial.yml`. It concatenated everything in
`docs/app/narrative/.parts/` in filename order and wrote the result to the target.

The first defect was found immediately. `1ce1a4af`:

```
ci(narrative): make the assembler order-safe

Only concatenate once p1, p2 and p3 are all present, so the parts can be
committed one at a time without a partial run corrupting the target.
```

The cause is stated exactly: the parts were being committed one at a time, and the workflow ran on
every push, so it concatenated whatever happened to be present. A run that fired after part 1 but
before part 2 would write a one-part file over the target. The fix was a guard — wait until all three
named parts exist.

That guard was the wrong shape, and the next commit says so. `b305854b`:

```
ci(narrative): assemble from numbered parts on a DONE sentinel

Some larger single writes are rejected by the publishing API, so the
instalment is committed in small numbered parts and concatenated in
filename order once .parts/DONE exists.
```

The guard moved from "three named files exist" to "a sentinel file exists". This is a better design: the
sentinel is committed last, by the author, when the author knows the parts are complete. It removes the
workflow's need to guess.

But the trigger was still `push` on the parts directory, and that is what broke next.

### 2.2 The run that deleted its own input

`74ebe539`:

```
ci(narrative): assembler runs on manual dispatch only

The push trigger fired on every part commit and deleted .parts2/ after the first
one, so the target was assembled from a partial set. Dispatch-only means the
parts are all in place before assembly runs.
```

This is the failure that matters most, because it is a class of failure rather than an instance. The
workflow's job ended with `rm -rf "$PARTS"` — it cleaned up after itself, which is normally correct
hygiene. But because the trigger was a push to the directory it was cleaning, the first part commit
fired the workflow, the workflow assembled a one-part file and deleted the directory, and every
subsequent part commit landed in a directory that no longer existed.

The workflow destroyed its own input on the first run. The commit message says so plainly: "the push
trigger fired on every part commit and deleted .parts2/ after the first one, so the target was assembled
from a partial set."

The fix was to remove the automatic trigger entirely and require a manual dispatch. That is a retreat
from automation, and it is the right one: a workflow that cannot tell "the parts are ready" from "a part
has arrived" should not run automatically.

### 2.3 The 125,740-byte polluted file

`3bd8f7fa`:

```
ci(narrative): assembler replaces target from .parts2, never appends

The first run appended the existing target and picked up leftover failed-attempt
files, producing a polluted 125,740-byte file. This version starts from empty
and reads only .parts2/.
```

One hundred and twenty-five thousand, seven hundred and forty bytes. The correct file is 101,467. The
polluted file was 24,273 bytes larger than it should have been, and the cause is two mistakes
compounding: the assembler appended to the existing target instead of replacing it, and the parts
directory still contained files from earlier failed attempts.

This is the first place in the window where a number can be checked against another number and the
error is visible without reading any code. 125,740 against 101,467 is a 24% overshoot. A reader who
noticed the file size would have known something was wrong before anyone read the diff.

The fix: start from empty, read only `.parts2/`. Both halves matter. Starting from empty removes the
append; reading only `.parts2/` removes the stale files.

### 2.4 The newline the API eats

`905a68e0`:

```
ci(narrative): strip the API's trailing newline per part

The contents API appends one newline to every file it writes, which would insert
a newline at each chunk boundary. Strip exactly one per part so the assembled
file is byte-identical to the local source.
```

This is a subtle one, and it is the kind of defect that only shows up when you compare bytes rather than
reading the file. The GitHub contents API appends a newline to every file it writes. If you write a
document in ten parts, you get ten extra newlines — one at each boundary. The document still reads
correctly. It is still valid Markdown. It is simply not the file you wrote.

The fix strips exactly one newline per part. "Exactly one" is the important phrase: strip more and you
eat a real blank line, strip fewer and the boundary newline survives.

That fix was then superseded, because it was solving the problem at the wrong end. `3ab008f4`:

```
ci(narrative): assembler overwrites from empty, parts boundary-safe

The API strips trailing whitespace per write, so parts are now split on
non-whitespace boundaries and the assembler writes the target from empty with a
single final newline.
```

And then `dbcb6f39`:

```
ci(narrative): assembler joins parts with a newline

The API strips trailing whitespace per write, so parts are split on line
boundaries and joined with a newline, which restores exactly what the strip
removed.
```

Read those two together and you have the whole problem in two sentences. The API does not append a
newline; it *strips trailing whitespace*. So a part that ends with a newline loses it, and the join
between two parts collapses. The fix is to split on line boundaries and join with a newline — the join
puts back exactly what the strip removed.

The earlier commit (`905a68e0`) had the direction of the error backwards. It assumed the API added a
newline; the API removed one. The commit message for `905a68e0` is therefore wrong about the cause,
and the later commits correct it without saying so. That is a small thing, and it is exactly the kind
of small thing the chronicle exists to record: a fix that works for the wrong reason, followed by a fix
that works for the right one.

### 2.5 The trigger that fired on the sentinel

`6191a9bc`:

```
ci(narrative): assembler triggers on a dedicated sentinel file

The .parts2/ push trigger fired on every part commit and deleted the parts
directory after the first one. The trigger is now a single sentinel file
committed last, once every part is in place.
```

This is the same defect as `74ebe539`, fixed a second time. The first fix was to make the workflow
manual-dispatch-only. That worked, but it meant a human had to click a button, and the human was an
agent, and the agent's way of clicking a button was to commit a file. So the trigger came back — but
scoped to a single sentinel path rather than the whole directory.

The final workflow, as it stands at `77b72a1a`, states the design in its header comment:

```
# TRIGGER: push of docs/app/narrative/.assemble-trigger ONLY, committed last
# once every part is in place.
```

And the assembly step:

```
for f in $(ls "$PARTS"/*.md | sort); do
  echo "appending $f"
  if [ "$first" -eq 0 ]; then
    printf '\n' >> /tmp/assembled.md
  fi
  first=0
  cat "$f" >> /tmp/assembled.md
done
printf '\n' >> /tmp/assembled.md
mv /tmp/assembled.md "$TARGET"
rm -rf "$PARTS"
rm -f docs/app/narrative/.assemble-trigger
```

Read that loop carefully. It writes to `/tmp/assembled.md`, not to the target. It moves the result into
place only after the loop completes. It removes the parts directory and the sentinel only after the
move. Every one of those orderings is a fix for a failure described in an earlier commit message.

### 2.6 What the fourteen commits produced

The word count at each assembly commit, measured with `git show <sha>:<path> | wc -w`:

| Commit | Words | What it was |
|---|---|---|
| `b5107c53` | 4,903 | part 1/5, the first fragment |
| `b479c093` | 20,009 | first assembly — polluted, duplicated sections |
| `df055cb6` | 8,066 | second assembly — partial |
| `d1438766` | 8,199 | third assembly — partial |
| `43546167` | 16,264 | fourth assembly — complete, two words short |
| `fcca9535` | 16,266 | fifth assembly — final |

The 20,009-word file is the interesting one. It is larger than the final, and the reason is visible in
its headings. `git show b479c093:docs/app/narrative/serial-2026-11-21.md | grep '^## '` returns 21
headings, of which four are duplicated:

```
## 4. Twenty-two agents, one hour, and two absences
## 5. The branch count that fell from fifteen to two
## 6. The conformance sweep: seventy-nine issues in two days
## 7. The consolidation: 177 members into 56 runtimes
```

The final file has 17 headings and no duplicates. So the first assembly concatenated a parts directory
that contained two copies of sections 4 through 7 — presumably because a failed attempt had left its
parts behind and a later attempt added its own. The assembler did what it was told: it concatenated
everything in the directory. The directory contained more than it should have.

This is the same failure as the 125,740-byte file, in a different guise. Both are the assembler
faithfully assembling a directory that had accumulated debris. The fix in both cases was to make the
directory's contents trustworthy — start from empty, read only one directory, delete the directory
after use.

### 2.7 The four probes

Interleaved with the assembly commits are four commits whose subject begins with `probe:`.

| Commit | Time | Subject | File |
|---|---|---|---|
| `bdfb2cdf` | 11:13:31 -0700 | `probe: verify API write path` | `docs/app/narrative/.write-probe` |
| `b7c12544` | 11:16:08 -0700 | `probe: remove write-path probe` | (deletion) |
| `7098af0d` | 11:45:00 -0700 | `probe: quota check` | `docs/app/narrative/.parts/probe.txt` |
| `3fc93a75` | 11:49:25 -0700 | `probe: write check` | `docs/app/narrative/.parts/probe2.txt` |

Four commits, three files, all of them one line. These are not content. They are tests of whether the
write path works — whether a file can be created at all, whether the quota has room, whether a write
into a subdirectory behaves differently from a write at the top level.

The first pair is the cleanest: write a probe, confirm it landed, delete it. The second pair is less
clean — `probe.txt` and `probe2.txt` were written into `.parts/`, the directory the assembler reads.
That is a real hazard, and it is the same hazard that produced the 20,009-word file: anything in
`.parts/` gets concatenated. A one-line probe file in that directory would have appeared in the
assembled document as a stray line.

Whether it did is not recorded. The final file does not contain the string `probe`, and the parts
directories were deleted by the assembler. What can be said is that the probes were written into a
directory whose contents were being concatenated, and that this is the kind of thing that produces a
stray line in a published document and no error anywhere.

**What broke.** A workflow that cleaned up after itself deleted its own input, because its trigger was a
push to the directory it cleaned. A first assembly appended to an existing target and picked up debris,
producing a 125,740-byte file against a 101,467-byte source. A second assembly concatenated a directory
containing duplicated parts, producing 20,009 words against 16,266. A fix for the newline problem
assumed the API appended a newline when it strips one. And two probe files were written into the
directory the assembler reads.

**What we learned.** The lesson is not "write a better assembler". It is that a build step which reads a
directory must own that directory's contents, and a build step which deletes its input must not be
triggered by its input arriving. Both of those are structural, and both were learned by breaking them.
The commit messages record the breakage in the order it happened, which is why this section can be
written at all: fourteen commits, each one a sentence about what the previous one got wrong.

## 3. The gate that was never built: tag monotonicity

The previous instalment's §2 ended with a question it could not answer:

> Part two §12 asked whether the repository has a check that `VERSION` is monotonic across its release
> tags. `48c241a1` cuts 3.1.2, which is higher than both 3.1.0 and 3.1.1, so the *current* state is
> monotonic. Whether a *check* now exists is a separate question this note does not answer, and the
> next instalment should.

This is the next instalment, and the answer is no.

### 3.1 What was searched

The search was for code, not for intent. A plan document that says a gate should exist is not a gate. A
docstring that describes a rule is not a gate. The question is whether there is an executable check that
would fail if the rule were broken.

Searched:

- Every file under `.github/workflows/` (18 workflows) for `VERSION`, `git tag`, `refs/tags`.
- Every file under `scripts/` for `git tag`, `refs/tags`, `semver`.
- The whole tree for `monotonic`, `tag_monoton`, `tag-monoton`, `version_monoton`, `semver.*monoton`.
- `git log --all --grep='monoton' -i`.

### 3.2 What was found

**In the workflows**, three references to `VERSION` and one to tags:

- `.github/workflows/ci.yml:254` — a comment: *"VERSION, pyproject.toml and version.hpp each state the version and nothing compared them: on 2026-11-01 they read 4.0.0, 3.0.0 and 3.1.0."* Followed by a step that runs `python3 scripts/check_version_consistency.py`.
- `.github/workflows/ci.yml:495` — `print("stdlib-only import ok; api_version =", h.API_VERSION)`, an unrelated API version.
- `.github/workflows/controlz-desktop.yml:123-124` — `tagName: controlz-v__VERSION__`, a release-asset naming template.
- `.github/workflows/release.yml` — the Ruby SDK release, which checks that a pushed tag matches the gem version.

**In `scripts/`**, one file: `scripts/check_version_consistency.py`.

**In the whole tree**, `monotonic` appears in 25 files, none of them a version check. They are
monotonic clocks, monotonic counters, monotonic sequence numbers — `mem20orcaz/concurrency.py`,
`mem20kimiz/batch.py`, `mem20ircz/hub.py`, and so on. The word is used, but never about tags.

**In `git log --all --grep='monoton' -i`**, one commit: `4d166d90`, *"Option C batch 6: traffic control,
webhook network (17 tests)"*. Unrelated.

### 3.3 What `check_version_consistency.py` actually does

This is the closest thing in the repository to a version gate, and it is worth reading in full because
its docstring states precisely what it does and does not cover.

```
"""Fail when the version is stated in more than one place and the places disagree.

mem20 states its version in three files:

  VERSION                              -- the release marker, authoritative
  pyproject.toml  [project] version    -- what `pip install .` records
  sdk/cpp/include/mem20/version.hpp    -- what the C++ SDK was built against

On 2026-11-01 these read 4.0.0, 3.0.0 and 3.1.0. Nothing compared them, so the
package metadata had been two minor releases behind the tree it described and
the SDK baseline one behind. This script is the comparison.

VERSION is authoritative because it is the file the release process writes and
the only one that is a single token with no surrounding syntax to parse.

Exit 0 when all three agree, 1 when they do not, 2 when a file is missing.
"""
```

Three files, compared for equality. That is the whole check. It answers the question "do these three
files state the same version right now". It does not answer "is this version higher than the last one",
and it does not look at tags at all.

The distinction matters because the defect the previous instalment described was not a disagreement
between three files. It was a tag ordering: `v3.1.1` (`52ffe13d`) is an ancestor of `v3.1.0`
(`73343f68`). A tag cut before the release it names. `check_version_consistency.py` would pass on that
repository state, because all three files could agree on a version while the tag graph was still
inverted.

### 3.4 The one place tags are compared

`scripts/ops/scoreboard_signals.sh` does compare branches against `main`:

```
ahead=$(git rev-list --count "${MAIN_REF}..${sha}" 2>/dev/null || echo "?")
if git merge-base --is-ancestor "${sha}" "${MAIN_REF}" 2>/dev/null; then
  st=MERGED; merged=$((merged+1))
else
  st=UNMERGED; unmerged=$((unmerged+1))
fi
```

That is a branch-merge check, not a tag-order check. It iterates `git ls-remote --heads origin`, which
lists branches, not tags. It answers "is this branch merged into main", which is a different question
from "is this tag's version higher than the previous tag's version".

And it is a reporting script, not a gate. It prints a scoreboard. It does not exit non-zero on a
violation, and it is not invoked by any workflow.

### 3.5 The verdict
**No tag-monotonicity gate exists.** Not in CI, not in `scripts/`, not anywhere in the tree. The
repository has:

- a check that three files agree on a version string (`check_version_consistency.py`, wired into
  `ci.yml`);
- a check that a Ruby gem's tag matches its `version.rb` (`release.yml`, scoped to one SDK);
- a reporting script that counts merged branches (`scoreboard_signals.sh`, not a gate).

None of these would fail if a tag were cut with a version lower than its predecessor. The defect the
previous instalment documented — `v3.1.1` before `v3.1.0` — could recur tomorrow and nothing would say
so.

**What broke.** A question was asked in a published document and left open, and the answer took a
separate run to establish. That is not a failure of the repository; it is a failure of the previous
instalment, which should have answered it rather than deferring it.

**What we learned.** "There is a check for versions" and "there is a check for tag order" are different
claims, and a repository can have the first while lacking the second. The way to tell them apart is to
read the check's docstring and see what it compares. `check_version_consistency.py` says exactly what it
compares — three files, for equality — and that sentence is the answer.

## 4. The gate that was never built: dated-record exclusion

The second open question was whether anything prevents a dated record from being rewritten after
publication. The previous instalment had found two cases where it happened. The question is whether a
gate exists that would catch the next one.

The answer is again no, but the trail is more interesting, because there *is* a rule, written down, in
two places, and there is a fix that was applied to the wrong layer.

### 4.1 The rule, as written

`scripts/sweep-tool-counts.py` carries this docstring:

```
Append-only / dated records keep their historical numbers, because rewriting
them would falsify the record rather than correct it:

  CHANGELOG.md                  history of earlier reconciles
  published/**                  immutable delivery archive (MANIFEST-pinned)
  published/daily-reports/*.md  dated ops logs
  docs/audit/*.md               dated audits
  docs/recon/**                 the stale-file inventory and its evidence
  docs/ops/metrics.json         dated issue titles / branch names
  .sitemap/sitemap.json         generated snapshot
  toolchest/inventory.json      generated snapshot
  **/*.patch, bench/optionc     captured diffs of past states
  "older docs quote 258-260"    sentences that describe the retired value
```

That is a correct and complete statement of the rule. It is also, as the commit that added half of it
says, a statement the code did not implement.

### 4.2 The fix that came too late

`0eab51ad`, 7 November 2026, subject *"fix(sweep): stop rewriting the immutable archive and dated
records"*:

```
The sweep's own docstring says append-only records keep their historical
numbers, but its skip list was incomplete: it rewrote published/** (breaking
published/MANIFEST.tsv, which has no generator in the repo), .sitemap/,
docs/ops/metrics.json (dated issue titles) and the recon inventory's own
evidence strings. Add them to the skip list and mirror the new allowlist
entries in the inventory generator.
```

Two files changed, 26 insertions and 1 deletion. The diff adds `published/` and `docs/recon/` to
`SKIP_PREFIXES`, and four paths to `SKIP_FILES`:

```
+    ".sitemap/sitemap.json",                            # generated snapshot
+    "docs/ops/metrics.json",                            # dated issue titles / branch names
+    "docs/recon/stale-file-inventory-2026-11-07.json",  # inventory evidence strings
+    "toolchest/inventory.json",                         # generated snapshot (306 entries)
```

And the comment above the prefix list:

```
+    # published/ is the immutable delivery archive, integrity-pinned by
+    # published/MANIFEST.tsv (per-file sha-256) and governed by
+    # published/README.md rule 3 ("never edit a preserved file in place").
+    # There is no manifest generator in the repo, so rewriting a preserved file
+    # breaks the manifest permanently. The sweep must not touch it.
+    "published/",
```

Every sentence of that comment is true. `published/` is the immutable archive. It is pinned by
`MANIFEST.tsv`. Rule 3 of `published/README.md` says never edit a preserved file in place. And rewriting
a preserved file does break the manifest.

The comment also contains a claim that is false: *"There is no manifest generator in the repo."* There
is one. `scripts/gen_manifest.py` exists, has a `--check` mode, and its docstring says:

```
The manifest is a claim: for every file under published/, this many bytes and
this SHA-256. It was maintained by hand, and by 2026-11-01 thirty-two of its
128 rows were wrong -- unchanged across four separate measurements, because
nothing regenerated it and nothing checked it.

This script is both halves:

    python3 scripts/gen_manifest.py            # rewrite the manifest
    python3 scripts/gen_manifest.py --check    # exit 1 if any row is wrong
```

So the fix was written on a false premise — that the manifest could not be regenerated, and therefore
that any edit to `published/` was permanent damage. The premise was wrong, but the conclusion was
right: the sweep should not touch the archive. A correct rule resting on an incorrect reason is still a
correct rule, and it is also a rule that will be re-litigated by the next person who reads the comment
and discovers the generator exists.

### 4.3 The fix did not prevent the next rewrite

`0eab51ad` landed on 7 November. The 18 November sweep (`0cd80344`) rewrote four dated records anyway.

The reason is visible in the repository and it is not a bug in the skip list. `scripts/sweep-tool-counts.py`
is not invoked by any workflow. `grep -rn 'sweep-tool-counts\|stale-file-inventory' .github/workflows/`
returns nothing. The script is a tool a human runs by hand, and the 18 November commit was not that
script running — it was a hand-run find-and-replace across the working tree, with a commit subject that
says so: *"Replace 3.1.2 with 4.0.0 across repository and include pending workspace changes"*.

A skip list protects against the tool that reads it. It does not protect against a different tool, or
against a human with `sed`.

### 4.4 The other half of the rule

`scripts/ops/check-doc-counts.py` is the one gate in the repository that explicitly reasons about dated
records. Its exclusion list:

```
EXCLUDE_PREFIXES = (
    "published/",          # immutable delivery archive (MANIFEST-pinned)
    "docs/audit/",         # dated audits
    "docs/recon/",         # stale-file inventory + evidence
    "docs/ops/",           # dated ops logs
    "docs/app/narrative/", # dated serials
    "docs/app/deck/",      # dated deck records
    "docs/renovation/",    # in-flight 4.0 overhaul
    "ops/",                # dated ops records
    ".sitemap/",           # generated snapshot
)
EXCLUDE_FILES = {
    "CHANGELOG.md",        # history of earlier reconciles
    "DIARY.md",            # dated diary
    "failures.md",         # dated failure log
    "AbsoluteTruth113.md", # dated audit narrative
    "toolchest/inventory.json",  # generated snapshot
}
```

This is the most complete statement of the dated-record rule in the repository, and it is correct. The
gate excludes every dated record from its scan, because a dated record is allowed to contain a retired
number — that is what makes it a record.

But exclusion from a count check is not protection from a rewrite. The gate's purpose is to fail when a
*live* doc carries a retired tool count. It says nothing about whether a *dated* doc has been altered.
A dated record could be rewritten from top to bottom and `check-doc-counts.py` would pass, because it
never looks at it.

Running it confirms the gate works as designed:

```

$ python3 scripts/ops/check-doc-counts.py
live pin: 487 tools / 129 domains
scanned: 85 live doc(s)
OK: no retired tool/domain band in any live doc
```

Eighty-five live docs scanned, zero violations. The gate is healthy. It is also, by construction,
blind to the exact failure the previous instalment documented.

### 4.5 The verdict

**No dated-record-exclusion gate exists.** What exists is:

- a skip list in `scripts/sweep-tool-counts.py`, which is not invoked by CI and which protects only
  against that one script;
- an exclusion list in `scripts/ops/check-doc-counts.py`, which correctly excludes dated records from a
  count check and therefore cannot detect their alteration;
- a `--check` mode in `scripts/gen_manifest.py` that *would* detect byte changes under `published/`, and
  which is not invoked by any workflow.

The third is the closest thing to a real gate, and it is not wired up. Running it by hand:

```
$ python3 scripts/gen_manifest.py --check
  MISMATCH published/README.md
  MISMATCH .../mem20-ruby-sdk/CHANGELOG.md
  ... (10 total)
  UNLISTED published/checkpoints/ledger.md
  ... (10 total)
::error::published/MANIFEST.tsv does not describe the tree
```

Ten mismatches, ten unlisted files, 129 manifest rows against 172 files present. The archive's integrity
claim has been false for some time, and the only tool that can say so is not run automatically.

**What broke.** A rule was written down in a docstring, implemented in a skip list, and then bypassed by
a different tool. A second gate excluded dated records from its scan for the right reason and thereby
became incapable of noticing their alteration. A third tool could have caught it and was never wired up.

**What we learned.** A skip list is a promise a tool makes to itself. It is not a gate. The only thing
that would catch a rewrite of a dated record is a check that compares the record against the commit
that first published it — `git diff $(git log --diff-filter=A --format=%H -- "$f" | tail -1) HEAD -- "$f"`
— and no such check exists in this repository. The audit in §5 is that check, run by hand, once.

## 5. The audit: every delivered document against its publication commit

The previous instalment ended with a list of things it could not verify. One of them was whether the
rewrites it had found were isolated or representative. This section answers that, by running the check
that does not exist as a gate — by hand, once, across every delivered document in the repository.

### 5.1 The method

For each delivered document:

```
first=$(git log --diff-filter=A --format='%H' -- "$f" | tail -1)
git diff "$first" HEAD -- "$f"
```

`--diff-filter=A` finds the commit that *added* the file — its publication. `tail -1` takes the earliest
such commit, in case a file was deleted and re-added. The diff then compares the file as it stands at
`main` against the version at publication.

Thirty-one documents were audited: five serial instalments, two program-history documents, eleven
long-form copy assets, ten daily reports, the checkpoints ledger, and `published/README.md`.

### 5.2 The result

| Verdict | Count |
|---|---|
| Unchanged since publication | 19 |
| Legitimate correction | 4 |
| **Retroactive rewrite** | **5** |
| Append-only addition | 1 |
| Assembly, not editing | 1 |
| Content restored after a placeholder clobber | 1 |

Five retroactive rewrites. The previous instalment found two. The audit found three more, all in the
daily reports, all from the same 18 November sweep.

### 5.4 What a legitimate correction looks like

The audit found four, and they are worth stating because the distinction is the whole point.

`published/history/mem20-program-history.md` (added `c69b1fb0`, changed by `de37968a`, 2 insertions and
1 deletion) had a quoted rule changed from *"Sidney is not a storage location"* to *"Sidney is retired
and is not a storage location"*, with a parenthetical noting the host and publish gate no longer exist.

That is a correction. The change does not alter what the history says happened. It updates a rule that
is still in force, in a document that is a living statement of policy rather than a dated transcript.
The original sentence remains true; the new one is more true, and it is dated by its commit.

`published/history/README.md` (added `69507f2a`, changed by `de37968a`, 1 insertion and 1 deletion) got
the same treatment to the same rule.

`published/README.md` (added `4375f77c`, changed by five commits, 30 insertions and 8 deletions) is a
living index. `a80fd259` repaired a truncated write of `MANIFEST.tsv`; `2960e662` updated a stale
257-tool claim to 268; `de37968a` purged retired host references. Each change is dated by its commit and
none removes a claim a reader could have verified.

`published/content/mem20-long-form-v3/launch-copy-pack.md` (added `b17d5f84`, 9 insertions and 2
deletions) was published as a three-line placeholder and later filled in with the real pack. A
placeholder replaced by its content is not a rewrite of a record; the placeholder asserted nothing that
the replacement contradicts.

### 5.5 The test that separates them

The test is not "was the file edited". It is: **can a reader still reconstruct what was true at the
moment the document claims to describe?**

A correction adds information and leaves the old claim standing, dated. A rewrite removes the old claim
and puts a new one in its place, undated, so that the document now asserts something that was never true
when it says it was.

By that test, the four corrections above pass and the five rewrites fail. The publication note fails
because its printed transcript no longer matches what the printed commands return. Part two fails
because its reproduction script no longer runs. The three daily reports fail because their tables of
figures no longer describe the dates in their filenames.

### 5.6 The append-only addition

One document was extended without being edited: `published/daily-reports/2026-10-31.md` (added
`f25b57d7`, changed by `4f20ecfb`, 10 insertions and 0 deletions). A "Credential attestation" section was
appended at the end. No existing line changed.

That is the shape a correction to a dated record should take. The record is extended, not edited. A
reader can still see what the report said on 31 October, and can also see what was added to it later.

### 5.7 The assembly

`docs/app/narrative/serial-2026-11-21.md` (added `b5107c53`, changed by five assembly commits, 1,273
insertions and 0 deletions) is not an edit at all. No line was ever deleted. The intermediate word
counts — 4,903, 20,009, 8,066, 8,199, 16,264, 16,266 — are artefacts of partial assembly, not of content
being removed.

The 20,009-word intermediate is the one that needs explaining, and §2.6 explains it: the first assembly
concatenated a parts directory containing duplicated sections. Its heading list has 21 entries with four
duplicates; the final has 17 with none.

**What broke.** The previous instalment found two rewrites and reported them as the finding. There were
five. The three it missed were in a directory it had not thought to audit — `published/daily-reports/` —
because the two it had found were in `docs/app/narrative/`, and it generalised from the directory it
happened to be looking at.

**What we learned.** A finding is not a survey. Finding two instances of a defect in one directory is
evidence that the defect exists, not evidence about its extent. The extent has to be measured, and the
measurement is mechanical: enumerate the population, run the same check on every member, and report the
count. The previous instalment should have done that before publishing, and this one had to do it after.

## 6. The archive's integrity claim is false

`published/MANIFEST.tsv` is the archive's own claim about itself: for every file under `published/`, a
byte count and a SHA-256. It is the mechanism by which the archive can say "this file has not been
altered" without anyone having to trust a human.

Running the check:

```
$ python3 scripts/gen_manifest.py --check
  MISMATCH published/README.md
  MISMATCH .../mem20-ruby-sdk/CHANGELOG.md
  MISMATCH .../mem20-ruby-sdk/EVIDENCE.md
  MISMATCH .../mem20-ruby-sdk/README.md
  MISMATCH .../sidney-mem20-deploy-credential-update/DEPLOY_REPORT.md
  MISMATCH .../mem20-canonical-url-audit/index.html
  MISMATCH .../mem20_repo_v3/slide_01.html
  MISMATCH .../mem20-assets-refresh/mem20-asset-refresh-report.md
  MISMATCH .../mem20-design-research/README.md
  MISMATCH .../mem20-market-research-v3/gabe-bundle/PUBLISH-RUNBOOK.md
  UNLISTED published/checkpoints/ledger.md
  UNLISTED published/checkpoints/refresh_ledger.py
  UNLISTED published/content/mem20-long-form-v3/.probe
  UNLISTED published/content/mem20-long-form-v3/.probe2
  UNLISTED published/content/mem20-long-form-v3/README.md
```

Ten mismatches, ten unlisted files. 129 manifest rows against 172 files present.

### 6.1 What the mismatches are

Most of them are the 22 October tool-count sweep. `2960e662`, subject *"Fix #81: update stale 257-tool
claim to 268 (#89)"*, touched five of the ten:

- `.../mem20-ruby-sdk/CHANGELOG.md` — `257 registered tools` → `268 registered tools`
- `.../mem20-ruby-sdk/EVIDENCE.md` — the same substitution in two places
- `.../mem20-ruby-sdk/README.md` — `257 tools` → `268 tools` in two places
- `.../sidney-mem20-deploy-credential-update/DEPLOY_REPORT.md` — `/ready -> {"ready": true, "tools": 257}` → `268`, and `257 tools across 26 domains` → `268 tools across 26 domains`
- `.../mem20-design-research/README.md` — five lines
- `.../mem20-market-research-v3/gabe-bundle/PUBLISH-RUNBOOK.md` — `257 headline` → `268 headline`

That is a tool-count sweep rewriting preserved files in place. It is the exact act `published/README.md`
rule 3 forbids: *"Never edit a preserved file in place. This is an archive."*

Two more are the 26 October frontend copy sweep: `d27fcef0` on the canonical-url-audit page and
`269cd042` on the repo_v3 cover slide. Both changed `257 tools / 26 domains` to `270 tools / 27 domains`
inside a published artifact.

One is a content restore: `cd13951a`, *"restore: real content for mem20-asset-refresh-report.md"*,
following `0d4af6a3` which had clobbered seven assets with a placeholder payload.

### 6.2 The unlisted files

Ten files exist under `published/` with no manifest row at all. Nine of them are the entire
`published/content/mem20-long-form-v3/` directory — the long-form copy assets, added after the manifest
was last regenerated. One is `published/checkpoints/ledger.md` and its generator.

So the manifest does not describe the tree in two directions: it has rows for files whose bytes have
changed, and it has no rows for files that exist.

### 6.3 Why this matters more than it looks

The manifest is the archive's only self-verification mechanism. `published/README.md` rule 4 states the
law: *"Verify with hashes, not prose. `MANIFEST.tsv` is authoritative; a file whose SHA-256 does not
match the manifest has been corrupted or changed."*

That rule is correct, and it is currently unenforceable, because the manifest is wrong. A reader who
follows rule 4 today will find ten files that fail and ten that cannot be checked, and will have no way
to tell which failures are the 22 October sweep and which are something worse.

`gen_manifest.py` has a `--check` mode that exits 1 on any mismatch. It is not invoked by any workflow.
`grep -rn 'gen_manifest' .github/workflows/` returns nothing.

**What broke.** A manifest maintained by hand drifted from the tree it describes, and the tool that
could have caught the drift was written but never wired up. The drift is not a single event: it
accumulated across at least three sweeps over four weeks, and each sweep made it slightly worse.

**What we learned.** A verification mechanism that is not run is not a verification mechanism. The
manifest's own docstring says the problem out loud — *"It was maintained by hand, and by 2026-11-01
thirty-two of its 128 rows were wrong -- unchanged across four separate measurements, because nothing
regenerated it and nothing checked it."* That sentence was written by someone who understood the
problem, and the fix they wrote was a `--check` mode, and the `--check` mode was not added to CI. The
understanding was correct and the wiring was missing, which is the most common shape of a defect that
survives.

## 7. The gate that was fixed, and the labels it did not fix

At 23:05:17Z on 21 November, commit `77b72a1a` landed:

```
ci: exempt CI-infrastructure-only changes from the artifact-evidence gate

A push whose changed files are limited to CI/workflow/gate machinery and
dependency lockfiles produces no artifact of its own to evidence, so the gate
failed every CI-maintenance push by construction (105b9602, 987c9782). Exempt
that shape with an explicit EXEMPT (ci-infrastructure) reason printed.

The exemption is narrow: it applies only when EVERY changed file is CI
machinery or a lockfile. A commit mixing a lockfile with product code is still
a delivery and is still gated (self-test case 9).

Self-test extended 6 -> 9 cases: lockfile-only PASS, workflow-only PASS,
lockfile+product-code still FAIL.
```

This is a good commit. It names the two commits that failed by construction (`105b9602`, the lockfile
regeneration, and `987c9782`, the comic PDF). It states the exemption's boundary precisely — *every*
changed file, not *any*. It extends the self-test. And it explains why the exemption is not a weakening:
a commit that mixes a lockfile with product code is still gated.

The diff is 89 insertions and 6 deletions in one file. It adds a `LOCKFILE_NAMES` frozenset with
sixteen entries — `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`,
`bun.lockb`, `Cargo.lock`, `poetry.lock`, `Pipfile.lock`, `uv.lock`, `go.sum`, `composer.lock`,
`Gemfile.lock`, `packages.lock.json`, `pubspec.lock`, `Podfile.lock`, `mix.lock` — and widens
`GATE_OWN_DIRS` from `(".github/workflows/",)` to `(".github/",)`.

### 7.1 The labels that were not renumbered

The commit message says *"Self-test extended 6 -> 9 cases"*. The self-test now has nine cases. But the
labels were not renumbered:

```
$ python3 scripts/check_artifact_evidence.py --self-test
self-test [1/6] authored delivery with evidence -> PASS
self-test [2/6] authored delivery, no evidence -> FAIL
self-test [3/6] authored commit changing nothing -> PASS (empty)
self-test [4/6] gate-own change -> PASS (ci-infrastructure)
self-test [5/6] convergence push landing unevidenced work -> PASS (integration)
self-test [5b/6] same work delivered as a PR -> still FAIL (gate keeps teeth)
self-test [6/9] zero-diff convergence push -> PASS (integration)
self-test [7/9] lockfile-only change -> PASS (ci-infrastructure)
self-test [8/9] workflow-only change -> PASS (ci-infrastructure)
self-test [9/9] lockfile mixed with product code -> still FAIL (gate keeps teeth)
```

Ten lines of output, nine cases (one is labelled `5b`). The first six say `/6`; the last four say `/9`.
The transition happens between `[5b/6]` and `[6/9]`, which means the author renumbered from case 6
onward and left cases 1 through 5b alone.

This is a cosmetic defect and it is worth recording for exactly that reason. The gate works. The
self-test passes. The commit message is accurate about the count. And the output a human reads when the
self-test runs says the suite has six cases in its first six lines and nine in its last four.

The cause is visible in the diff: the new cases were appended after the existing ones, and the existing
ones' labels were not touched. The author was thinking about the new cases and not about the old labels.
That is how every cosmetic defect happens.

**What broke.** Nothing functional. A test suite's output labels disagree with its own case count.

**What we learned.** A self-test is documentation that runs. If its labels are wrong, the documentation
is wrong, and the wrongness is printed on every run to everyone who looks. The fix is one line per
label, and the reason it was not made is that the author was adding cases rather than reading output.
The lesson is not "renumber your labels" — it is that the output of a check is part of the check, and a
check whose output misleads is a check that will eventually be misread.

### 7.3 What the check does

`.github/workflows/mcp-verify.yml`:

```
- name: Checkout (shallow, no history)
  uses: actions/checkout@v4
  with:
    fetch-depth: 1

- name: Confirm the checkout really is shallow
  run: |
    echo "is-shallow: $(git rev-parse --is-shallow-repository)"
    test "$(git rev-parse --is-shallow-repository)" = "true"
```

The check is a regression guard for shallow clones: it deliberately checks out with `fetch-depth: 1` and
then verifies that the MCP server can still start and answer `tools/list` with 487 tools. The comment
above the dependency install step records why the guard exists:

```
# Install from requirements.txt, not a hand-written list. The hand

# the pinned floor) are imported at module scope by modules the
# server loads before it can answer a single request. Sixteen runs
# failed on that gap. The file is the source of truth; this step
# reads it.
```

Sixteen runs failed on a hand-written dependency list that had drifted from `requirements.txt`. That is
the same class of defect as the manifest: a hand-maintained list that nothing compared against its
source.

### 7.4 What could not be established

Running `verify_mcp.py` locally reproduces the failure:

```
$ timeout 120 python3 verify_mcp.py

```

`EOF from server` with empty stderr. The server process exits without writing anything to stderr, which
means the failure is not an exception being raised and printed — it is the process ending.

But the local environment is not the CI environment. The local run is against a full clone, not a
shallow one; the local interpreter is the sandbox's Python 3.11, not the CI's; and the local run has
whatever dependencies the sandbox happens to have installed, which is not `requirements.txt`.

So the honest statement is: the check is red on `77b72a1a`, it was green on the two preceding commits,
the commit in between does not touch the MCP server, and a local reproduction produces `EOF from server`
with empty stderr. The cause was not isolated in this run.

**What broke.** A check that was green went red on a commit that could not plausibly have caused it.

**What we learned.** A red check on a commit that does not touch the checked code is evidence about the
check, not about the commit. The two possibilities are that the check is flaky and that the check is
detecting something environmental. Both are worth knowing and neither can be distinguished from a single
red run. The next run should re-run the check on the same SHA before concluding anything, and this
instalment did not do that.

> **Rule learned:** never publish a hand-summed count. Publish the grep.

That rule is the reason §5 of this instalment exists in the form it does. The audit did not sample; it
enumerated thirty-one documents and ran the same check on each. The count of five rewrites is a count
produced by a loop, not by reading and remembering.

**`mem20kilnz/failures.md`, 2026-09-25 — "Sixteen engine functions declared but never implemented (not nine)":**

> **Actual error:** I first reported **nine**. The true count is **sixteen**. My check grepped nine names
> I had picked by hand and confirmed each appeared exactly once. It never audited the full declaration
> list, so seven more were missed.
>
> **Cause:** sampling the header by hand instead of enumerating it.

This is the previous instalment's error, stated a month and a half before it was made. It found two
rewrites by looking in the directory it happened to be reading, and reported two. The true count was
five. The cause is identical: sampling instead of enumerating.

That the same mistake was made twice, by the same series, with the rule already written down in the
corpus it draws from, is the most useful thing in this section. A lesson that is recorded and not applied
is a lesson that has not been learned.

**`failures.md`, 2026-11-04 — the launch-gate entry:**

> launch-gate check flagged the served page because `VERSION` (4.0.0) was itself listed in
> `RETIRED_VERSIONS`. NEXT ACTION: done — `retired_versions_for(current)` filters the live version;
> regression test added.

A gate that flagged the current version because the current version was on its list of retired versions.
That is the same shape as the artifact-evidence gate failing lockfile commits: a check whose rules were
correct in general and wrong for a case the author had not considered. The fix in both cases was to
narrow the rule, not to weaken it.

### 9.2 The corpus's silence

The corpus has no entry for 21 November. It has no entry for the fourteen assembly commits, the four
probes, the 125,740-byte polluted file, the 20,009-word duplicated assembly, or the self-test labels.

Every one of those is a failure in the corpus's own format: attempt, actual error, cause, next action,
rule learned. None of them was logged.

**What broke.** The failure log stopped recording failures at the moment the failures became
process-level rather than code-level.

**What we learned.** A failure corpus that only records product defects will miss the defects in the
process that produces the product. The assembly saga is fourteen failures with causes and fixes, each
one documented in a commit message and none of them in `failures.md`. The commit messages are the better
record here, and that is an accident — they were written to explain a change, not to teach a lesson.
