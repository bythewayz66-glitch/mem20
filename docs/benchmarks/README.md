## 1. Coverage: 7 read surfaces, 4 measured

`mem20api` exposes seven read paths on `Store`. Four of them are measured by the
harness today; three are not. This table is the honest state of that coverage.

| # | Surface | Signature (`mem20api`) | Measures | Status |
|---|---|---|---:|---:|
| 1 | `recall()` | `recall(topic=None, tags=None, k=5, include_simulated=False)` | reverse-chronological filter by topic/tags | **not yet measured** |
| 2 | `recall_at()` | `recall_at(as_of, **kw)` | point-in-time recall — what was true at `as_of` | **not yet measured** |
| 3 | `semantic()` | `semantic(query, k=5, topic=None, tags=None, strict=False)` | vector search over MiniLM embeddings | measured |
| 4 | `hybrid()` | `hybrid(query, k=5, topic=None, tags=None, alpha=0.5)` | RRF fusion of vector + BM25, then rerank | measured |
| 5 | `graph()` | `graph(entity, hops=2, max_results=20, min_facts=1, topic=None)` | multi-hop entity/edge traversal | measured |
| 6 | `entities()` | `entities(limit=50)` | entity index listing by degree | **not yet measured** |
| 7 | `ledger()` | `ledger(k=20)` | write ledger tail | **not yet measured** |

`keyword` appears in the results below but is **not** a separate public method: the
harness isolates it by calling `hybrid(alpha=0.0)`, which is the shipped code path
for the BM25 half. That is the honest way to measure it — a private re-implementation
would be measuring something users cannot call.

### Why the gaps are real, not an oversight to paper over

`mem20benchmarkz/mem20benchmarkz/bench.py` implements exactly four branches in
`_run_mode()` — `semantic`, `hybrid`, `graph`, `keyword`. There is no call to
`store.recall()` or `store.recall_at()` anywhere in the harness (verified by
grep on both `main` and `feat/scale-corpus-2000`). So the three unmeasured
surfaces are not "missing data we forgot to paste in"; they are surfaces the
suite cannot currently score. Filling them with estimates would be inventing a
benchmark.

`recall_at()` is the one worth prioritising: it is a distinct correctness axis
(point-in-time truth) that no other mode exercises, and it is the reason the
bi-temporal claim in the corpus had to be corrected in `d0f21e2`.

## 6. What this table does not say

- **It is not a comparison to Mem0 or Zep.** Mem0's LoCoMo (92.5) and LongMemEval (94.4)
  and Zep's DMR (94.8%) are recall numbers on different corpora — two of the three
  private or vendor-defined — with different metrics. Nothing here refutes or
  reproduces them, and this table must not be cited as if it did.
- **It is not the scale run.** 14 facts and 13 queries is the CI regression corpus.
  A 2000-fact result would answer a different question (does recall hold as the
  corpus grows) and is `not yet measured`.
- **`n` is small.** Per-kind `n` ranges from 2 to 5. A hit rate of `1.000` on
  `n=5` is five queries, not a confidence interval. Treat these as regression
  signals, not published effect sizes.
- **`graph` has `n=2`.** Graph traversal only runs on queries that carry an
  `entity`, so its row is two queries. It is directional at best.
- **Latency is one machine.** Python 3.14.6, x86_64, MiniLM-L6-v2 384-dim, cross-encoder
  enabled — see `environment` in the artifact. Latency will not transfer to other hardware.

## Adding the missing four modes

Two separate gaps, two separate fixes:

1. **`recall()` / `recall_at()` / `entities()` / `ledger()`** need new branches in
   `_run_mode()` plus query kinds that make sense for them (`recall` has no query
   text; it filters by topic/tag, so it needs a different query schema, not another
   mode branch). That is a harness change in `mem20benchmarkz/**` — a different
   layer from this directory.
2. **The scale run** only needs an executed `run-scale` and the resulting
   `benchmarks/results-scale/latest.json` committed. When that file exists, point
   `ARTIFACT` in `render.py` at it (or add a second section) and re-render — no
   numbers get edited by hand.

Until either lands, the cells stay `not yet measured`.
