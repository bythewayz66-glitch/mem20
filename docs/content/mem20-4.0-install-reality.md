# mem20 4.0 — Install Reality

**Release:** 4.0.0 · **Checkout:** `0224a64946a2c00313a9872515893157adcbc47e` · **Captured:** 2026-11-16

Companion to [`mem20-4.0-release-story.md`](./mem20-4.0-release-story.md), which covers the
487-tool / 129-domain surface and the auditable memory model. This file covers the part most
likely to waste a reader's afternoon: **how you actually get mem20 running.**

---

## There is no `pip install mem20`

This is the single most likely wrong assumption about the project, so it is worth stating
flatly: **mem20 is source-only.** It is not published on PyPI under the name `mem20`.

Verified live, while writing this:

```console
$ pip download mem20 --no-deps -d /tmp/dl
ERROR: Could not find a version that satisfies the requirement mem20 (from versions: none)
ERROR: No matching distribution found for mem20

$ curl -s -o /dev/null -w "%{http_code}\n" https://pypi.org/pypi/mem20/json
404
```

A 404 on the PyPI JSON API means the project name does not exist there. A **404 is not an
outage** — it is the absence of a package, and the correct reading is "clone the repository",
not "try again later" or "--pre".

Consequences a reader should internalise:

- You cannot pin mem20 as a `pip` dependency in the normal way. Downstream installs must
  vendor a clone, a tarball, or a wheel you build yourself.
- `pip install -e .` works **only from inside a checkout** — it is an editable install of the
  local tree, not a fetch from an index.
- Any tutorial showing `pip install mem20` is describing a package that does not exist and
  will fail on a clean machine.

The reason this matters strategically as well as practically: a source-only project has no
version-pinning story by default, so the `VERSION` file, `pyproject.toml` and the live site are
the *only* things telling anyone which 4.0 they have. Keeping those three in agreement is not
cosmetic bookkeeping — it is the substitute for a package index.

## What the install is

The supported path is clone-and-install:

```bash
git clone https://github.com/bythewayz66-glitch/mem20.git
cd mem20
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/pip install -r requirements.txt
```

`requirements.txt` is not just the MCP SDK. It carries the modules that the server imports at
**module scope** before it can serve a single request, and several that the test suite needs to
even collect:

| Dependency | Why it is required |
|---|---|
| `mcp>=2.1.1` | The MCP SDK itself |
| `mcp-types>=2.3.0` | `import mcp_types as mt` in `mcp/server.py` and tool modules |
| `aiohttp>=3.14.5` | Imported at module scope by `mcp/tools/a2a_tools.py` |
| `pydantic`, `anyio`, `numpy` | Core runtime |
| `faiss-cpu`, `sentence-transformers` | The semantic half of retrieval |
| `httpx`, `PyYAML`, `stripe` | Imported at module scope by subsystems; without them 20+ test modules cannot collect |
| `fastapi>=0.162.2,<0.163`, `starlette>=0.40,<0.42` | Pinned together — unpinned Starlette 1.x breaks FastAPI at import |
| `websockets>=16.1.1` | Imported at module scope by `mem20autouez` |

Two entries deserve to be called out, because they are the difference between "requirements"
and "requirements that actually boot":

- **`mcp-types`** — the MCP SDK does not bring it. Without it, `import mcp_types as mt` fails
  before any tool module loads.
- **`aiohttp`** — also not an SDK dependency, and imported at module scope by
  `mcp/tools/a2a_tools.py`. A requirements file that omits it produces a clone where the
  server dies on import and the tool directory is never reachable.

The `fastapi` / `starlette` pin matters for the same reason in a different key: it is a
*coupled* pin. Starlette 1.x breaks FastAPI at import, so installing one without constraining
the other produces an environment that looks complete and does not start.

Two other install shapes exist:

- **Portable installer (systemd host):** `sudo ./install.sh [--user u] [--dir d] [--venv v]`
  creates the venv, installs requirements, generates a unit from
  `systemd/mem20.service.template`, and enables/starts the service. `--no-systemd` skips the
  service step.
- **Editable package:** `pip install -e .` from the checkout installs the `memory_engine`
  package, the repo-root modules (`memory`, `procedural`, `launcher`, `metrics_collector`,
  `mem20path`), and three console scripts — `mem20-mcp`, `mem20-metrics`, `mem20-path`.

Blender and Unity are **optional external applications, not pip packages**. The server runs
without them and reports when a tool needs one — the right way round for a 487-tool surface
where most deployments touch a small fraction of it.

## `mem20-ce` is a different package

There *is* a PyPI package in this family, and conflating the two is the second most likely
mistake:

```console
$ curl -s https://pypi.org/pypi/mem20-ce/json | ...
0.1.1  mem20 Core Edition — trusted, auditable memory substrate for AI agents.
       Grounded facts and simulated ...
```

| | `mem20` (this repo) | `mem20-ce` (PyPI) |
|---|---|---|
| Distribution | Git clone | `pip install mem20-ce` |
| PyPI status | **404 — not published** | **200 — published, v0.1.1** |
| Version | 4.0.0 | 0.1.1 |
| Scope | MCP server + 129-domain tool surface + subsystem estate | The focused, installable memory substrate |
| License | Apache-2.0 | Apache-2.0 |
| Repository | `bythewayz66-glitch/mem20` | `bythewayz66-glitch/mem20-ce` |

So "mem20 is on PyPI" is true only if you mean Core Edition — and Core Edition at 0.1.1 is not
a 4.0.0 MCP server with 487 tools. The README is explicit about the split: Core Edition is
"the focused, installable memory substrate" living in `mem20-ce`.

This is the most consequential naming trap in the project. A reader who wants the auditable
memory substrate and runs `pip install mem20` gets an error; a reader who runs `pip install
mem20-ce` gets a real package that does far less than the 4.0 story describes. Both readers
were reasonable, and neither got what they expected. The only fix is to say which is which,
loudly, in the same place — which is what this section is for.

**Which one do you want?**

- *The auditable memory substrate, as a library* → `mem20-ce` from PyPI (v0.1.1), or the
  `memory_engine` package from a clone.
- *The 487-tool MCP server* → clone `mem20`. There is no other route.

## First run in four commands

Once the checkout exists, the substrate is usable without the MCP server at all:

```bash
export MEM20_STORE_PATH=$(mktemp -d)

python3 -m memory_engine.cli remember \
  --topic demo --content "the sky is blue" --epistemic-status observed

python3 -m memory_engine.cli recall --topic demo
python3 -m memory_engine.cli health
```

That sequence is deliberately the one used to produce the evidence transcript checked in at
[`evidence/memory-engine-transcript.txt`](./evidence/memory-engine-transcript.txt), so it is
known to work on a clean checkout rather than being copied from a README.

To run the MCP server instead:

```bash
MEM20_STORE_PATH="$HOME/.mem20/store" .venv/bin/python mcp/mcp_server.py
```

which logs its health endpoint on `:8080` (`/health`, `/ready`, `/metrics`) and then speaks
JSON-RPC 2.0 over stdio. The HTTP endpoint is for liveness and metrics only — tool calls go
over stdio. That split surprises people who expect the HTTP port to be the API; it is not.

One detail worth flagging for anyone following the in-repo examples: `python3 -m
memory_engine` is **not** the CLI entry point, because there is no `memory_engine/__main__.py`.
The working invocation is `python3 -m memory_engine.cli` (or the installed console script),
which is what every command in these documents uses. A small papercut with an outsized cost:
the error from the wrong form does not say "add `.cli`".

## What this install story does not claim

- **`requirements.txt` was read, not installed end-to-end in one clean venv for this
  document.** The dependency reasoning above comes from the file and from the import sites
  named in the table, not from a fresh environment build.
- **No PyPI publish is imminent or implied.** The 404 is the current, verified state.
- **The systemd installer and the editable package were read, not executed** on this host.
