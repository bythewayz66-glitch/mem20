## 1. What 4.0 is

mem20 is an MCP server that gives an agent a memory which survives the session and can be
audited afterwards. It is three layers in dependency order:

| Layer | Path | What it is |
|---|---|---|
| **Memory engine** | `memory_engine/`, `memory.py` | Global memory, append-only ledger, vector/BM25 retrieval. The durable substrate. |
| **MCP server** | `mcp/` | JSON-RPC 2.0 over stdio, plus an HTTP health/metrics endpoint on `:8080`. |
| **Subsystems** | `mem20*/` | Independently packaged capability modules, most with their own `pyproject.toml`. |

Version 4.0 is the release where the surface got **measured and published** instead of
asserted. The `VERSION` file reads `4.0.0`; `pyproject.toml` declares the same; the live site
at `mem20.com` shows `v4.0.0`. Those three agree, which sounds like a low bar until you
consider how often a version string, a package metadata field, and a marketing page drift apart.

`mcp/` is deliberately **a script directory, not an importable package** — it has no
`__init__.py`, because importing it as `mcp.*` would shadow the upstream `mcp` SDK. That
single constraint explains `from server import main` in `mcp_server.py` and the existence of
`launcher.py` behind the `mem20-mcp` console script.

## 2. The live surface: 487 tools across 129 domains

### 2.1 Where the numbers come from

The tool count is not a hand-written claim. `docs/surface.json` is generated from the **live
JSON-RPC `tools/list` response** produced by `launcher.py`, then cross-checked against an AST
catalog built by `web/scripts/extract-tools.py`. Its own `source` field says exactly that:

```
"source": "tools/list via launcher.py; domains and modules from the AST catalog
           generated by web/scripts/extract-tools.py"
```

The cross-check is the important part, because the two halves are computed by completely
different methods — one asks the running server what it serves, the other parses the source
tree — and both must agree:

```json
"cross_check": { "ast_domains": 129, "ast_tools": 487, "only_ast": [], "only_live": [] }
```

`only_ast` and `only_live` are both **empty**. That is a stronger statement than "487": it
says no tool exists in the source that the server fails to expose, and no tool is exposed that
does not exist in the source. Totals on this checkout:

| Measure | Value | Source |
|---|---:|---|
| Exposed MCP tools | **487** | `docs/surface.json` → live `tools/list` |
| Domains | **129** | `docs/surface.json` → AST catalog |
| Sum of per-domain tool counts | **487** | `docs/surface.json` → `domain_counts` |
| AST tools / AST domains | **487 / 129** | `docs/surface.json` → `cross_check` |
| Discrepancies between live and AST | **0** | `only_ast: []`, `only_live: []` |

The per-domain counts sum to exactly 487, so 487 is a *partition* of the surface, not an
estimate: every tool belongs to exactly one domain and the domain table has no orphan entries.

### 2.2 What the 487 tools actually cover

The surface is not 487 variations on `remember` and `recall`. It is dominated by memory
operations, but it reaches well past them. The fifteen largest domains:

| # | Domain | Tools | What it is |
|---:|---|---:|---|
| 1 | `memory` | 55 | The core: remember, recall, supersede, prune, namespaces |
| 2 | `cognitive` | 19 | Reasoning, planning, reflection, working memory |
| 3 | `world` | 14 | Variables, predictions, outcome resolution |
| 4 | `versioncontrol` | 11 | Git-facing operations |
| 5 | `cloudservice` | 10 | Service lifecycle |
| 6 | `database` | 10 | Structured storage |
| 7 | `filesystem` | 10 | File operations |
| 8 | `lie` | 10 | Adversarial / deception detection |
| 9 | `productivity` | 10 | Task and note operations |
| 10 | `braid` | 9 | Cross-subsystem wiring |
| 11 | `communication` | 9 | Message and channel operations |
| 12 | `dev` | 9 | Development tooling |
| 13 | `marketing` | 9 | Content and campaign operations |
| 14 | `thought_process` | 9 | Structured deliberation |
| 15 | `cloudstorage` | 8 | Object storage |

`memory` at 55 is the anchor — roughly one tool in nine — which matches the product thesis:
the substrate is the product, and the rest of the estate is a view onto it. But the surface
also spans `webscraping` (8), `finance` (8), `design` (8), `edgefleet` (8), `blender` (7),
`unity` (5), `temporal` (5), `a2a` (5), `irc` (5), `procedural` (6), and more.

Some of that breadth is genuinely load-bearing — `search` (7) is retrieval, `verify` (4) and
`temporal` (5) support audit, `a2a` (5) is agent-to-agent coordination. Some of it is estate
surface that a given deployment will never call. Both are true at once, and the honest framing
is: **487 is the size of the addressable surface, not the size of the surface you will use.**

### 2.3 The long tail: 129 domains, most of them small

129 domains for 487 tools means the average domain has under four tools — so the distribution
is heavily skewed. Counting how many domains have *n* tools:

| Tools in domain | Domains |
|---:|---:|
| 10 or more | 9 |
| 4 – 9 | 26 |
| 2 – 3 | 79 |
| 1 | 15 |

So 94 of the 129 domains (73%) hold three tools or fewer, while the 9 domains with ten or more
hold **149** between them, just under a third of the whole surface. The shape is a dense core
plus a long tail of narrowly scoped, individually packaged capabilities. That is also why the
estate has so many `mem20*z` directories: each tail domain tends to be its own package with its
own tests, which is good for isolation and expensive for anyone trying to hold the whole thing
in their head.

### 2.4 Nineteen unwired tools

`docs/surface.json` separately lists **19 tools that are registered but not wired into the
live surface**. Naming them matters, because a count of 487 that silently includes holes is
worse than a count of 468 that does not:

| Group | Tools | Count |
|---|---|---:|
| `gateway_*` | `admission`, `provenance`, `translate` | 3 |
| `lattice_*` | `emit`, `recall`, `report`, `search`, `verify` | 5 |
| `memory_engine_*` | `guard`, `health`, `namespace`, `recall`, `subsystem`, `veto` | 6 |
| `stream_*` | `publish`, `recall`, `report`, `search`, `verify` | 5 |
| | | **19** |

The `memory_engine_*` six are the substrate's own public API reachable over MCP; the
`lattice_*` and `stream_*` families are near-mirror images of each other (five tools each,
sharing `recall`/`report`/`search`/`verify` naming), which reads as two competing designs for
the same capability rather than two finished ones. Reporting them as unwired is the honest
option; quietly folding them into a headline count is not.

### 2.5 Numbers that are *not* 487

Two other counts get confused with the tool count, and the repository has a gate specifically
to stop retired numbers from reappearing in live prose:

- **Tool modules, not tools.** `mcp/tools/` holds **153** `*_tools.py` modules (157 `.py`
  files counting the directory's other files). Modules are not tools: one module registers
  many tools, which is why 487 tools can come from 153 modules.
- **Retired bands.** The surface has moved 257 → 258–260 → 265 → 268 → 270 → 306 → 311 → 487
  tools across 26 → 27 → 38 → 129 domains. `scripts/ops/check-doc-counts.py` scans every live
  doc for a retired band presented as current and fails the run. It reads the expected value
  from `docs/surface.json` rather than hardcoding it, precisely so the gate cannot drift when
  the surface moves:

  ```console
  $ python3 scripts/ops/check-doc-counts.py
  live pin: 487 tools / 129 domains
  scanned: 85 live doc(s)
  OK: no retired tool/domain band in any live doc
  ```

  Dated records, audits and generated snapshots are deliberately **out of scope** — rewriting
  a historical number would falsify the record instead of correcting it. This document is
  dated and carries a live pin, so it sits on the correct side of that rule.
