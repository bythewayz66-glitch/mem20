## 1. What 4.0 is

mem20 is an MCP server that gives an agent a memory which survives the session and can be
audited afterwards. It is three layers in dependency order:

| Layer | Path | What it is |
|---|---|---|
| **Memory engine** | `memory_engine/`, `memory.py` | Global memory, append-only ledger, vector/BM25 retrieval. The durable substrate. |
| **MCP server** | `mcp/` | JSON-RPC 2.0 over stdio, plus an HTTP health/metrics endpoint on `:8080`. |
| **Subsystems** | `mem20*/` | Independently packaged capability modules, most with their own `pyproject.toml`. |

Version 4.0 is the release where the surface got **measured and published** instead of
asserted. The `VERSION` file reads `4.0.0`; `pyproject.toml` declares the same; the live site
at `mem20.com` shows `v4.0.0`. Those three agree, which sounds like a low bar until you
consider how often a version string, a package metadata field, and a marketing page drift apart.

`mcp/` is deliberately **a script directory, not an importable package** — it has no
`__init__.py`, because importing it as `mcp.*` would shadow the upstream `mcp` SDK. That
single constraint explains `from server import main` in `mcp_server.py` and the existence of
`launcher.py` behind the `mem20-mcp` console script.

## 2. The live surface: 487 tools across 129 domains

### 2.1 Where the numbers come from

The tool count is not a hand-written claim. `docs/surface.json` is generated from the **live
JSON-RPC `tools/list` response** produced by `launcher.py`, then cross-checked against an AST
catalog built by `web/scripts/extract-tools.py`. Its own `source` field says exactly that:

```
"source": "tools/list via launcher.py; domains and modules from the AST catalog
           generated by web/scripts/extract-tools.py"
```

The cross-check is the important part, because the two halves are computed by completely
different methods — one asks the running server what it serves, the other parses the source
tree — and both must agree:

```json
"cross_check": { "ast_domains": 129, "ast_tools": 487, "only_ast": [], "only_live": [] }
```

`only_ast` and `only_live` are both **empty**. That is a stronger statement than "487": it
says no tool exists in the source that the server fails to expose, and no tool is exposed that
does not exist in the source. Totals on this checkout:

| Measure | Value | Source |
|---|---:|---|
| Exposed MCP tools | **487** | `docs/surface.json` → live `tools/list` |
| Domains | **129** | `docs/surface.json` → AST catalog |
| Sum of per-domain tool counts | **487** | `docs/surface.json` → `domain_counts` |
| AST tools / AST domains | **487 / 129** | `docs/surface.json` → `cross_check` |
| Discrepancies between live and AST | **0** | `only_ast: []`, `only_live: []` |

The per-domain counts sum to exactly 487, so 487 is a *partition* of the surface, not an
estimate: every tool belongs to exactly one domain and the domain table has no orphan entries.

### 2.2 What the 487 tools actually cover

The surface is not 487 variations on `remember` and `recall`. It is dominated by memory
operations, but it reaches well past them. The fifteen largest domains:

| # | Domain | Tools | What it is |
|---:|---|---:|---|
| 1 | `memory` | 55 | The core: remember, recall, supersede, prune, namespaces |
| 2 | `cognitive` | 19 | Reasoning, planning, reflection, working memory |
| 3 | `world` | 14 | Variables, predictions, outcome resolution |
| 4 | `versioncontrol` | 11 | Git-facing operations |
| 5 | `cloudservice` | 10 | Service lifecycle |
| 6 | `database` | 10 | Structured storage |
| 7 | `filesystem` | 10 | File operations |
| 8 | `lie` | 10 | Adversarial / deception detection |
| 9 | `productivity` | 10 | Task and note operations |
| 10 | `braid` | 9 | Cross-subsystem wiring |
| 11 | `communication` | 9 | Message and channel operations |
| 12 | `dev` | 9 | Development tooling |
| 13 | `marketing` | 9 | Content and campaign operations |
| 14 | `thought_process` | 9 | Structured deliberation |
| 15 | `cloudstorage` | 8 | Object storage |

`memory` at 55 is the anchor — roughly one tool in nine — which matches the product thesis:
the substrate is the product, and the rest of the estate is a view onto it. But the surface
also spans `webscraping` (8), `finance` (8), `design` (8), `edgefleet` (8), `blender` (7),
`unity` (5), `temporal` (5), `a2a` (5), `irc` (5), `procedural` (6), and more.

Some of that breadth is genuinely load-bearing — `search` (7) is retrieval, `verify` (4) and
`temporal` (5) support audit, `a2a` (5) is agent-to-agent coordination. Some of it is estate
surface that a given deployment will never call. Both are true at once, and the honest framing
is: **487 is the size of the addressable surface, not the size of the surface you will use.**

### 2.3 The long tail: 129 domains, most of them small

129 domains for 487 tools means the average domain has under four tools — so the distribution
is heavily skewed. Counting how many domains have *n* tools:

| Tools in domain | Domains |
|---:|---:|
| 10 or more | 9 |
| 4 – 9 | 26 |
| 2 – 3 | 79 |
| 1 | 15 |

So 94 of the 129 domains (73%) hold three tools or fewer, while the 9 domains with ten or more
hold **149** between them, just under a third of the whole surface. The shape is a dense core
plus a long tail of narrowly scoped, individually packaged capabilities. That is also why the
estate has so many `mem20*z` directories: each tail domain tends to be its own package with its
own tests, which is good for isolation and expensive for anyone trying to hold the whole thing
in their head.

### 2.4 Nineteen unwired tools

`docs/surface.json` separately lists **19 tools that are registered but not wired into the
live surface**. Naming them matters, because a count of 487 that silently includes holes is
worse than a count of 468 that does not:

| Group | Tools | Count |
|---|---|---:|
| `gateway_*` | `admission`, `provenance`, `translate` | 3 |
| `lattice_*` | `emit`, `recall`, `report`, `search`, `verify` | 5 |
| `memory_engine_*` | `guard`, `health`, `namespace`, `recall`, `subsystem`, `veto` | 6 |
| `stream_*` | `publish`, `recall`, `report`, `search`, `verify` | 5 |
| | | **19** |

The `memory_engine_*` six are the substrate's own public API reachable over MCP; the
`lattice_*` and `stream_*` families are near-mirror images of each other (five tools each,
sharing `recall`/`report`/`search`/`verify` naming), which reads as two competing designs for
the same capability rather than two finished ones. Reporting them as unwired is the honest
option; quietly folding them into a headline count is not.

### 2.5 Numbers that are *not* 487

Two other counts get confused with the tool count, and the repository has a gate specifically
to stop retired numbers from reappearing in live prose:

- **Tool modules, not tools.** `mcp/tools/` holds **153** `*_tools.py` modules (157 `.py`
  files counting the directory's other files). Modules are not tools: one module registers
  many tools, which is why 487 tools can come from 153 modules.
- **Retired bands.** The surface has moved 257 → 258–260 → 265 → 268 → 270 → 306 → 311 → 487
  tools across 26 → 27 → 38 → 129 domains. `scripts/ops/check-doc-counts.py` scans every live
  doc for a retired band presented as current and fails the run. It reads the expected value
  from `docs/surface.json` rather than hardcoding it, precisely so the gate cannot drift when
  the surface moves:

  ```console
  $ python3 scripts/ops/check-doc-counts.py
  live pin: 487 tools / 129 domains
  scanned: 85 live doc(s)
  OK: no retired tool/domain band in any live doc
  ```

  Dated records, audits and generated snapshots are deliberately **out of scope** — rewriting
  a historical number would falsify the record instead of correcting it. This document is
  dated and carries a live pin, so it sits on the correct side of that rule.

## 3. The auditable memory story

### 3.1 The one rule

Most agent memory is a single undifferentiated pile: once a guess and a fact are both
embedded, they look identical, and every later retrieval launders the guess a little further.
mem20's answer is to keep them apart **at the storage layer**, so the distinction survives
retrieval, summarisation and time.

| | Grounded | Simulated |
|---|---|---|
| What it is | What was observed | What was inferred |
| Written from | A real event, document, or tool result | A model reasoning about what might be |
| Partition | `grounded` | `simulated` |
| Ledger | `ledger.jsonl` | `simulated_ledger.jsonl` |
| Origin tag | `grounded` (immutable) | `simulated` (immutable) |
| Retrieval | Default | Opt-in only (`include_simulated`) |
| Assertable as true | **Yes** | **Never** |

This is the claim that is worth testing rather than reading, so the rest of this section quotes
actual runs. The full transcript is checked in at
`docs/content/evidence/memory-engine-transcript.txt`.

### 3.2 Epistemic status: a required field

Every grounded write must declare **how it was learned**. There are six accepted statuses plus
an explicit `unlabeled`:

```
observed · inferred · imagined · user_stated · hypothesis · agent_generated   (+ unlabeled)
```

The field is keyword-only in the API and required on the CLI — with no default. That is the
design decision that matters: an engine which silently defaults the basis to `observed` would
manufacture certainty out of a caller's omission. Instead:

```console
$ python3 -m memory_engine.cli remember --topic launch --content "unlabeled claim"
usage: memory_engine remember [-h] --topic TOPIC --content CONTENT
                              --epistemic-status EPISTEMIC_STATUS
                              ...
memory_engine remember: error: the following arguments are required: --epistemic-status
```

And an invented basis is refused against the closed set, with the valid list printed back:

```console
$ python3 -m memory_engine.cli remember --topic launch --content "x" --epistemic-status guessed
error: Invalid epistemic_status 'guessed'. Must be one of: ['observed', 'inferred',
'imagined', 'user_stated', 'hypothesis', 'agent_generated', 'unlabeled']
```

A caller that genuinely does not know is expected to say `unlabeled` — the engine has a word
for ignorance and refuses to supply one on the caller's behalf.

The label is stored, not consumed. Recall returns it:

```console
$ python3 -m memory_engine.cli recall --topic launch
[
  {
    "action": "remember",
    "actor": "agent",
    "content": "mem20 4.0.0 exposes 487 tools across 129 domains",
    "epistemic_status": "observed",
    "event_time_basis": "assumed_ingestion",
    "id": "1a1e47394ed2f0c",
    "origin": "grounded",
    "priority": "normal",
    "source": "memory_engine.substrate",
    "store": "grounded",
    "topic": "launch",
    "ts": "2026-11-16T13:02:22.444507+00:00",
    "valid_from": "2026-11-16T13:02:22.444507+00:00",
    "valid_to": null
  }
]
```

Three fields in that record are worth pausing on. `epistemic_status: "observed"` is the label
the caller had to supply. `event_time_basis: "assumed_ingestion"` is the engine flagging a
weaker claim than it looks — it was not told when the event happened, so it is reporting that
it assumed the event time equals ingestion time. And `valid_from`/`valid_to` give every fact a
validity window, which is what makes an "as of" read possible later.

### 3.3 Two partitions, two ledgers

Writing simulated content goes through a **different code path**, not a flag on the same one:

```python
from memory_engine.api import MemoryEngine
e = MemoryEngine()
g = e.remember("launch", "487 tools across 129 domains", epistemic_status="observed")
s = e.remember_simulated("launch", "10,000 users by Friday", scenario="optimistic")
```

```console
grounded:  observed  store=grounded   origin=grounded
simulated: imagined  store=simulated  origin=simulated   valid_to=2026-12-16T13:01:33Z
```

The simulated record arrives with `epistemic_status: "imagined"` and `origin: "simulated"`
**immutable**, a `scenario` tag, a TTL (`valid_to` one month out by default), and a line in
`simulated_ledger.jsonl` rather than `ledger.jsonl`. It never touches the grounded ledger or
the retrieval indexes. The point is structural: there is no method that writes a hypothesis
into the grounded ledger, so no bug in a caller can promote one.

Note the contrast with a plain `remember(..., epistemic_status="imagined")`. That path
*accepts* the label and writes to the grounded partition with `store: "grounded"` — the label
says `imagined`, the storage says grounded. Both facts are visible in the record, and the veto
below catches it anyway, but the correct way to record speculation is `remember_simulated`.

### 3.4 The veto: asking permission before acting

Reading labels is not enough — something has to *refuse*. `veto_plan(ids)` takes the fact ids
a plan intends to rest on and returns a verdict:

```console
# plan resting on a grounded fact
$ veto_plan([grounded_id])
{"veto": false, "offenders": [], "unresolved": [],
 "message": "OK: plan rests on validated grounded memory."}

# plan resting on a simulated fact
$ veto_plan([simulated_id])
{"veto": true,
 "offenders": [{"fact_id": "1a1e472f03080cd", "kind": "simulated",
                "reason": "relies on unvalidated simulated content"}],
 "unresolved": [],
 "message": "VETO: plan relies on unvalidated simulated/imagined beliefs."}

# plan resting on an id that does not exist
$ veto_plan(["deadbeef"])
{"veto": true,
 "offenders": [{"fact_id": "deadbeef", "kind": "unverifiable",
                "reason": "fact id not found in grounded or simulated store"}],
 "unresolved": [{"fact_id": "deadbeef", "kind": "unverifiable"}],
 "message": "VETO: plan relies on unvalidated simulated/imagined beliefs,
             and 1 cited fact id(s) could not be verified."}
```

The third case is the one that separates this from a filter. A citation of a fact that does
not exist is a **veto with `kind: "unverifiable"`**, not a silently dropped id — so a plan
cannot escape the check by citing something the engine has never heard of. And the mixed case
behaves correctly: one `imagined` fact among grounded ones vetoes the whole plan, because a
plan is only as trustworthy as its weakest cited input.

There is a second entry point, `guard_plan(ids)`, which asks the same question through
`mem20crewz`'s guardrail bundle so that a crew execution and a direct caller cannot disagree
about whether a plan may run.

Beyond the veto, the substrate exposes exactly ten public functions — a deliberately small
contract for the rest of the estate to build against:

```
remember_fact · recall_facts · veto_plan · guard_plan · namespace_for_agent
subsystem_status · envelope · health · dream_lineage · validate_artifact
```

`namespace_for_agent` gives each agent its own address space (`namespace --agent atlas` →
`mem20agentz:atlas`), and `--json` wraps any command in a fleet envelope (`schema:
"mem20.cli/1"`, `ok`, `exit_code`, `stdout`, `stderr`) so an orchestrator can parse failures
without scraping prose.

### 3.5 What an audit actually looks like

`health` is the one-command summary of a store's epistemic state:

```console
$ python3 -m memory_engine.cli health
{
  "bm25_available": false,
  "grounded_facts": 1,
  "label_coverage": 1.0,
  "labeled_facts": 1,
  "ledger_events": 1,
  "public_api": ["remember_fact", "recall_facts", "veto_plan", "guard_plan",
                 "namespace_for_agent", "subsystem_status", "envelope",
                 "health", "dream_lineage", "validate_artifact"],
  "store": "/tmp/tmp.EIfJjfCQKr",
  "vector_available": false
}
```

`label_coverage: 1.0` is the headline: 100% of stored grounded facts carry a declared basis.
That ratio is the audit metric — a store that drifts toward 0.6 tells you a caller is writing
unlabelled facts, and `labeled_facts` / `grounded_facts` explains why.

`vector_available: false` and `bm25_available: false` are equally important and equally
blunt. On a clean checkout without the optional `vector` extra, the engine reports that it has
**neither** retriever available. It does not run a lexical fallback and then describe the
result as a semantic search. The README states the same policy: the engine "falls back to
BM25 and says so — it does not pretend to have run a vector search."

### 3.6 What the engine honestly does not do

Four limits, stated plainly because a trust product whose docs overstate it is worse than a
plain one:

1. **The ledger is not hash-chained.** It is *append-only* and *tamper-evident* in the sense
   that every mutation is a new line and nothing is rewritten in place — but there is no
   prev-hash chain linking record *n* to record *n+1*, so an attacker with write access cannot
   be *proven* to have edited it. Records do carry `content_hash` (md5, 16 chars) per fact,
   which detects content-level drift, not line deletion.
2. **The ledger is bounded.** Past 2,000 lines it rotates to a timestamped archive under the
   backup directory. Nothing is lost, but a single-file audit of "everything ever" requires
   the archive too.
3. **True semantic recall requires the `vector` extra.** Without `sentence-transformers` and
   `faiss`, retrieval is exact/lexical only, and `health` says so.
4. **`imagined` is a label, not a partition.** As shown in §3.3, `remember(...,
   epistemic_status="imagined")` accepts the label into the grounded partition. The veto
   catches it at plan time; the storage does not separate it. `remember_simulated` is the
   correct API for speculation.
