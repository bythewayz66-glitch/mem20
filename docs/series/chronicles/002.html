The dispatch: a roster committed before it was obeyed

2026-10-27 grounded 621 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

docs/ops/workload-roster-2026-10-27.md is 132 lines. It is worth reading closely, because it is the artifact that makes this round auditable, and because its own structure predicts its findings.

$ wc -l < docs/ops/workload-roster-2026-10-27.md
132

It opens with a baseline table naming the command behind each number — git ls-files | wc -l for the file count, git for-each-ref refs/remotes/origin for the branch count, the repo API's pushed_at for the last push. It then does something unusual for a dispatch document: it corrects its own commission. The owner's directive had named seven in-flight items. Two of them were no longer in flight, and the roster says so in a table headed Corrections to the directive's in-flight list:

| "PR #112 (Syntax gate)" in flight | Already MERGED 2026-10-27T08:28:34Z at d3ec87699242e89830c66914e49763a352f4f25e. Do not re-open or duplicate. | | "270/27 tool count" still to be landed | Already on main: README, docs/index.html, and docs/finance/inputs.json all carry 270/27 with previous_tools: 257 recorded as retired. Assigning it again would be duplicate work. |

Two assignments were dropped by that correction before anyone could do them twice. This is the cheapest possible form of the project's central habit: check the artifact, not the instruction.

Then the twenty-two rows. Each names a deliverable, a branch, and the reason only that agent should do it — a justification column, not a task list. Some rows are shaped as negative assignments, which is worth noticing because a refusal to duplicate is a decision with a cost:

| 12 | Mem20-Perl-Expert | #110 is open — do not duplicate. New: the 25 long-running tools answer with a {job_id,status:running} envelope; the Perl SDK has wait_for_job but no test drives it to a terminal state. |

Row 12, row 16, row 17, row 18 and row 20 all begin by forbidding work that already existed in an open PR. Row 19 explicitly retires a stale branch: feat/scale-corpus-2000 "is stale (2 ahead, last commit 2026-10-20)". Row 9 forbids redoing an already-reconciled number: "ACV is already reconciled 44/44 at $14,000 — do not redo that."

Five of twenty-two assignments are principally instructions not to do something. In a program whose characteristic failure is confident duplicate work, that ratio is the most interesting number in the document. And it is vindicated by the census in §3: of the twenty-one branches that landed, four were built on top of an existing branch rather than from main, which is what "do not duplicate" looks like when it is obeyed.

The chain rule, and where it came from

Section 4 of the roster imposes a second obligation on every row:

Every agent does two things: 1. Delivers their own row above, pushed, with a SHA. 2. Assigns one new piece of work to one other agent by @-mentioning them. To @-mention someone you must resolve their real userID: get_groups_info(["3388661668"]) and read members_detail[userID].nickname. A nickname in the message text triggers nobody. Never @ yourself. The chain ends when the work is in GitHub — not when the messages stop.

That last sentence is the roster's thesis. A chain of mentions is trivially self-sustaining; a chain of commits is not. The instruction about userIDs is a small piece of operational honesty that most dispatch documents omit: it states the failure mode of the mechanism it is teaching, which is that a nickname in prose triggers nothing because the runtime routes on an identifier rather than on text.

§3 is what that distinction looks like when you run the command and read the answer.
