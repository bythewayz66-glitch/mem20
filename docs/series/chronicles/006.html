The failures corpus: forty entries that stop a month before the frontier

2026-10-27 grounded 4058 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

The charter for this serial is that the "what broke / what we learned" thread is the spine, not an appendix. So: where is the corpus, and how current is it?

Searching the tree by filename for the usual markers — failure, lesson, learned, postmortem, retro, incident, diary, regret, broke, tech_debt — lands on eight paths. Two are false positives and one is a genuine find that the earlier draft of this document missed:

The newest entry in either failures file is 2026-09-27. The newest commit on main is 2026-10-27. The corpus therefore stops thirty days before the frontier, and every defect in the window this serial narrates exists only in commit subjects, PR bodies, audit documents and worklogs. That is a finding about the ledger, and it is the reason §3 and §4 lean so heavily on PR bodies: the corpus that should have carried those incidents had stopped being written.

DIARY.md is the closest thing to a live record and it is worth naming precisely, because it is not a failures ledger. It is a capability-and-operations log — what each estate service does, which systemd unit owns which port, and a "Fixed this session" block per date. Its newest date is 2026-09-29, four weeks before the frontier, and its register is what works, not what broke. A reader looking for the round's incidents will not find them there.

The corpus's format is the model, though, and each entry already has the shape the chronicle needs: attempt · actual error · cause · next action · rule learned. Here is what is in it.

6.1 The decimator that hit its triangle count and destroyed the shape

The most instructive sequence in the corpus is not a single entry but five, spread across three days, all concerning one op: decimate_mesh.

First attempt — quadric error metrics. Three defects, and the corpus is precise about the order in which they were found:

  1. The flip guard compared cross(b-a, p-a) against cross(b-a, c-a). The actual post-collapse

normal is cross(p-a, c-a). With the operands in the wrong order, every interior quadric minimiser looked like a flip, so all 552 candidates were rejected and the mesh never changed — the op reported success while doing nothing.

  1. Fixed, it then segfaulted: collapsing deleted degenerate faces and swapped in a compacted vector,

which renumbered faces while the vertex→face index still held the old numbers.

  1. Fixed again, it hit its triangle targets and lost **20% of signed volume at ratio 0.5 and 79% at

0.1**; once hole-filling was added it stopped reaching its target at all, reaching a fixed point at 297 faces.

The cause, as recorded: the link condition was being applied to n-gon faces, where "the vertex opposite the edge" is not well defined, and the boundary case was never handled.

The decision was to replace it with vertex clustering — "which has no topological failure mode" — measured at 4% area drift at ratio 0.75 and 6.7% at 0.5, with zero degenerate, zero non-finite and zero non-manifold geometry, measured by tests/mesh_metrics.py. QEM was recorded as the planned replacement, "not silently dropped".

Second attempt — refused rather than shipped broken. The 2026-09-27 entry fixes all three of the above and then measures six variants against a watertight 528-triangle sphere. The table is the best thing in the corpus:

attemptresult
boundary quadrics computed once100-140 boundary edges, −93% volume at ratio 0.1
boundary quadrics refreshed per collapse140 boundary edges, no better
link condition checked after collapsing564 triangles out of 528 in, +3% area, still holed
link condition checked before collapsing564 triangles out, unchanged
triangulate first, then collapse1,470 triangles out of 528, +2457% area

That last row is arithmetically 278.4% of the input triangle count (1470/528 = 2.784). The recorded cause: "the hole left by a collapse must be retriangulated from the hole boundary, and the loop was being built from every neighbour of the surviving vertex. That adds more faces than the collapse removed, so the mesh grows."

The decision line is the one to keep verbatim:

decimate defaults to cluster, the only method measured to preserve the surface … method: "qem" refuses with that reason rather than returning a larger mesh. A decimator that hits its triangle count while destroying the shape is worse than a simpler one that preserves it, and one that returns 278% of the input is not a decimator at all.

Third attempt — the fix, and what it was. The next entry names the actual mistake in its title: "the hole boundary needed an order, not a set". The loop was a set of neighbours; a set has no order, and a fan over an unordered loop produces overlapping triangles. It was rewritten to walk the 1-ring in cyclic order through the face fan. The measured outcome, on the same sphere:

methodratiotriangleshitarea driftvolume driftboundarydegeneratewatertight
qem0.7539675%+3.10%−1.32%00yes

qem0.2513225%+60.01%−8.80%00yes

qem became the default. And then the entry adds a guard that is really the lesson in executable form:

decimation refuses a mesh that is not a closed surface, with the actual boundary and non-manifold edge counts. A decimator run on a holed or non-manifold input returns confident nonsense, so it says no instead.

What we learned, in the corpus's own words: "Count targets are not quality." The generalised form for a program of this kind: a quality metric that can be satisfied while the artifact degrades is worse than no metric, because it converts a broken result into a green one. The decimator is the cleanest example in the repository of a component that refuses instead of lying, and refusals of this kind are among the most important entries in the story — which is why this section spends its length on them rather than on the features that worked.

6.2 The exporter that wrote every face index one too high

Attempt: round-trip a scene through OBJ. Actual error: my own importer rejected kiln's export with "face references vertex 275 but only 274 vertices exist". Blender accepted the file anyway. Cause: int base = 1; combined with writing base + v + 1, so the first mesh's indices started at 2 instead of 1. Why it survived: nothing round-tripped OBJ through kiln before, and Blender is lenient about a trailing out-of-range index.

Three sentences of cause, and one of them is a fact about the ecosystem rather than the code. The defect was invisible for as long as it existed because the only consumer anyone had tried was a tolerant one. Blender's leniency was not a courtesy; it was a missing test.

The corpus draws the conclusion the project needed: "The importer caught it; that is the argument for having an importer at all." A writer with no reader is untested. This is the same structural insight as the non-diff-scoped gate, one level down: a component that is only ever exercised by its own output, or by a consumer known to be forgiving, has not been exercised.

6.3 "Never publish a hand-summed count. Publish the grep."

The 2026-09-25 entry titled "Proposal claimed 263 AI-native features; real count was 212" is the origin of this serial's governing rule, and it is worth reproducing entire because the error's cause is not arithmetic:

Actual error: the per-family subtotals in the same paragraph summed to 212. The 263 was not derived from anything; it was wrong. Cause: hand-summed headline figure never reconciled against the item list. The subtotals were correct, which is exactly why it survived a read-through. Next action: recounted mechanically with grep -cE '^- [A-L][0-9][0-9] ', then added family L (43 genuine generative-pipeline capabilities) to clear 250 honestly rather than padding. Now 255, verified. The document carries the verification command and the correction note. Rule learned: never publish a hand-summed count. Publish the grep.

The subtotals were right. That is the whole mechanism: a wrong total sitting beside correct components survives review, because a reader's checking instinct is satisfied by the parts. And the repair was not to adjust the headline to 212 — it was to do the missing work (43 capabilities) and then report 255 with the command that produces it.

The neighbouring entry in the same corpus applies the same discipline to a scan rather than a sum: sixteen engine functions were declared and never implemented, but the first report said nine, because "I grepped nine names I had picked by hand". Two of the seven missed were apply_frame and ik_two_bone — the engine's frame evaluation and two-bone IK. A hand-picked sample under-reported by 44% and hid the two functions whose absence mattered most.

What we learned. The failure mode is not "I cannot count". It is "I counted the part I could see and reported it as the whole". The countermeasure is mechanical and cheap: publish the command, not the number, and let the reader re-derive. §5 of this document is that rule applied to itself, and §5 is also where the rule caught this document's own brief.

6.4 The transform chain that was mathematically wrong

A glTF node transform is TRS, and composing two gives TRSTR*S — which is not expressible as a single translation/quaternion/scale triple, because the inner translation has nowhere to go. The code collapsed the chain into one triple, "which is only correct when rotations are absent".

The evidence is a single distinguishing case: a parent with a 90° rotation and a 2× non-uniform scale, a child with its own 90° rotation and an offset. The true chain gives (0, 2, 0); the collapsed triple gives (0, −2, 0). Both are plausible numbers. Only one puts the point on the right side of the origin.

And then the entry records something rarer, about its own investigation:

Note on the investigation: my first hand-computed "expected" value was also wrong (2.0 instead of 3.0) because I forgot that the child's own translation moves the point. The code was right; the expectation was not. Recorded because the same trap would mislead the next reader.

A ledger that records its author's own wrong working is doing something no changelog can. The rule that falls out: a test whose expected value was hand-derived is itself a suspect, and the first disagreement between code and expectation is not evidence about the code.

6.5 The manifest that described the blockout

Actual error: the replay produced 1,720 bytes with 24 vertices where the original was 161,772 bytes with 5,952. Diffs were confined to the accessor counts, so the geometry itself differed, not just the encoding. Cause: the journal was read immediately after the brief, before the refine stage ran.

The manifest recorded the operations that produced the blockout while the file on disk was the refined asset. Replaying it faithfully rebuilt the wrong thing — "faithfully, and wrongly". The corpus's assessment is exact:

this is worse than having no journal. A manifest that looks complete and replays cleanly is trusted; one that is quietly truncated is not.

What we learned. Provenance has to be sampled at the same moment as the artifact, and a provenance record that replays successfully is a stronger claim than one that merely lists steps — which is why its failure is more dangerous, not less.

6.6 The refusals and the deletions

The corpus keeps three things a tidier ledger would have dropped.

An experiment deleted rather than half-kept. Classifying each voxel shell cell by its own nearest triangle normal gave 2.1% volume error on a remeshed sphere against 11% for the binary field — a five-fold improvement — but left 2,829 non-manifold edges, because neighbouring cells disagreed about which side of the surface they were on. A majority filter restored manifoldness and pushed the error straight back to 10.9%. The recorded conclusion: "the raggedness it removed was not noise, it was the accurate boundary. Both were deleted rather than left in as a partial feature."

That is a capability with a genuinely better headline number, removed because the number was the only thing better about it. It is the same judgment as the decimator, made earlier and without a shipped alternative.

A source file preserved against a destructive edit. A brace-counting script written to replace one C++ function body did not skip string literals, so "its match ran past the intended function and deleted everything up to the next coincidental brace balance" — apply_and_reply was gone, and dsl_command with it. The compiler caught it because the project builds with warnings-as-errors on unused symbols; the fix was git checkout on the one file and redoing the edit by hand by exact match. The recorded rule: "git diff reviewed for deletions before rebuilding."

A probe that states what it cannot measure. OBJ geometry: "probe states geometry not measured by this probe in reason rather than presenting 0 as a measurement." One line, and it is the same principle as not_measured in the family_otherstack fix. The program has a house style for not knowing, and it appears independently in two components.

6.7 The defect classes the corpus names

Reading all forty entries together, the failures cluster into a small number of repeatable classes, and naming them is more useful than any single entry:

  1. Plausible output that is wrong — the colourless description that measured in local space, the

animation curve shifted by one key, the transform chain, the surface-nets winding. The corpus says of the animation case: "every individual check passed. The file was valid glTF, the accessor counts were right, the times increased, and the import reported no error. Only comparing the sampled curve before and after a save caught it."

  1. Success reported for work not done — 552 candidates all rejected while the op reported success;

skin reporting skinned=True while the exporter wrote no skin data; translate reporting "translated <name>" having moved nothing. The corpus's verdict: "A false success is worse than a crash, because the caller believes it."

  1. Unit-of-count errors — the 263/212 hand sum, the nine-versus-sixteen sampler, the advisory op

table drifting to ops: 79 against 87 dispatched. The fix for the last one was a checker, tests/check_op_sync.py, that "reads apply_op's dispatch, the advisory table, the live ping count and the live initialize list, and fails on any mismatch in either direction."

  1. Environment and path assumptions — a relative output path resolved against the engine's own

directory, a sys.path[0] insertion that shadowed an installed package with a namespace directory, a cwd documented but never applied.

  1. Tests that assert the wrong thing — three assertion failures that "looked like defects" and were

the author's expectations; a test writing broken.glb into the repository root because it used a relative path instead of tmp_path; a green suite read as evidence of clean lint, followed by an F401 committed anyway.

Class 5 is the one the corpus treats most seriously, because it corrupts the instrument. The entry on the debris test ends with a process rule rather than a code fix: "the post-commit verification now lints and tests as separate steps, after the final edit, and the result is read rather than assumed."

Class 3 is the one this document committed, in §5, and the corpus's own countermeasure — publish the grep — is what caught it.

6.8 The gate that had never passed once

The corpus's lessons are about components. The audit tree holds a lesson about infrastructure, and it is the sharpest single document in the repository: docs/audit/2026-10-pages-build-failure.md, dated 2026-10-18, 110 lines, concerning issue #54. Its opening measurement is the whole argument:

Every GitHub Pages run fails. At the time of diagnosis the workflow had 23 runs, 0 successes.

Twenty-three runs and zero successes. A gate with zero successes has told you nothing about its subject and a great deal about itself, and the audit knows which is which. The failure was not in the build:

##[error]fatal: No url found for submodule path 'kanban-mcp' in .gitmodules
##[error]The process '/usr/bin/git' failed with exit code 128

Step outcomes: Set up job success → Checkout failure → Upload artifact skipped → deploy job skipped. Nothing after checkout ever ran, which means every hypothesis about the deploy configuration was a hypothesis about a step that was never reached. The audit says so in a table of ruled-out causes — missing pages: write permissions, a missing concurrency group, a wrong artifact path, Jekyll processing a non-Jekyll site, a missing index.html, base-path 404s, a Node version mismatch — and each row's verdict is a reason the step was skipped, not a reason it failed.

The cause: the repository contained three entries with git mode 160000 (gitlinks), added by a plain git add of nested working trees rather than git submodule add. A gitlink records a commit pointer but writes no URL; the URL comes only from .gitmodules, which did not exist — not at HEAD, and not anywhere in history. All three pointed at repositories that return 404.

And here is the part worth the chapter. CI was green throughout:

.github/workflows/ci.yml uses actions/checkout@v4 with no submodules: input (default false), so CI never recursed and never surfaced the problem — CI green, Pages red.

Two workflows, one checkout step each, different defaults, and the difference between them was invisible because only one of them recursed. The defect was not in either workflow. It was in the absence of a workflow that exercised the other's assumption.

What broke. Every Pages deployment for at least five days (the audit's table runs from 2026-10-14 17:18 to 2026-10-17 03:04) failed at checkout, and no test, gate or human noticed, because the only check anyone was reading (ci.yml) had disabled the exact mechanism that would have failed.

What we learned. The audit's own record of the fix is a refusal to over-correct: the gitlinks were removed with git rm --cached, and the document is explicit that this is not a feature removal — "These pointers reference repositories that do not exist, so they carry no content and no functionality; nothing can ever check them out. This is a broken pointer being repaired, not a feature being removed. The SHAs above are kept in the commit message so the original intent is recoverable." It also preserves the thing that could have been quietly lost: mem20kilnz/ keeps all 43 of its real files.

The generalisable rule: when two paths through the same tool use different defaults, the untested path is the one that will break, and it will break silently. The corollary is an operational one — a workflow with zero successes is not a flaky workflow, it is a workflow that has never run, and the difference between those two readings is one query on the run history.

6.9 The debt register, read as a prediction

2.0_roadmap/tech_debt_register.md is 29 lines and eight rows, and it is the only place in the tree where the project states its own architectural risks in a scored form. Severity and effort are 1–5.

Two of these read differently on 27 October than they did when written, and the difference is the finding.

TD-04 is closed in fact and stale in the document. It records "No automated test suite until Phase 7 close; only 2 verification scripts." The tree now contains test suites across multiple subprojects — node --test suites in the control-plane frontend (9 tests in #108, 22 in #109), 32 Rust tests in #113, 57 plus 8 live-server tests in the Perl SDK (#110), 153 in mem20agentz per #103, and 9 in the Telegram turnstile suite (#105). TD-04's own mitigation column says "Add tests/ pytest suite (in progress)", so the row is not wrong — it is unmaintained. A debt register that is not re-scored becomes a document that understates the work done and overstates the risk remaining, which is a specific and unusual way to be wrong.

TD-01 and TD-02 are the rows that matter, and neither is discussed anywhere in this round's twenty-two assignments. TD-02 — the vector index is in-process FAISS and is not shared across MCP processes — is recorded at severity 3, the highest in the file, with the mitigation "Document single-writer constraint; for 2.0 consider external vector store (ADR pending)". TD-01 — metrics are in-memory and lost on restart — is what makes TD-08 ("no health-based readiness gating") unfixable as written, because there is nothing durable for a readiness probe to read.

Set that against the roster. Twenty-two assignments, and the closest any comes to TD-01 or TD-02 is row 14, which asks Analytics Reporter to "measure what is real: commit velocity, PR cycle time, test counts, branch divergence — from git log" and emit docs/ops/metrics.json. That is a good assignment and it is explicitly a substitute for telemetry ("No visitor telemetry exists"). But it is metrics about the project's git history, not about the server, and it does not touch the in-memory health surface. The highest-severity architectural debt in the register went unassigned in a round whose stated purpose was to assign meaningful work to every agent.

What we learned. A risk register and a work roster are two documents that almost never get read together, and the gap between them is the most expensive gap in a planning cycle. The check is one line long: for each row in the register above severity 2, name the assignment that addresses it. If the answer is "none," the round is optimising something other than its stated risk. This document makes no claim that TD-02 should have been prioritised over, say, the Tauri shell — only that the choice was never made explicitly anywhere in the tree, and an unrecorded choice is indistinguishable from an oversight.
