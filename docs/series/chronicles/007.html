The three checks that are not seven

2026-10-27 grounded 750 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

The prior round left a document that does more work than any commit in this hour: PR #111, docs(ops): publish the one working GitHub access path + evidence register, head bef79279c2b99f44b14f3d60b11bacd865f537d0, opened 07:43:16Z.

Its central finding is a de-duplication of failure. Every open PR — #103 through #110 — and main itself were failing the same three checks, so a reviewer seeing seven red checks on one branch was seeing one defect seven times:

CheckReal cause, per #111
Syntax gateWhole-tree, not diff-scoped. Trips on two core.py files violating the shim rule (#17), plus a policy document that quoted the banned path while documenting the ban (#80).
TestsSame whole-tree job, inheriting the above.
Rust braidThe hosted runner image moved to a new Ubuntu release; the toolchain assumptions no longer hold.
Ruby 3.1/3.2/3.3 (#107 only)Runner image, not the SDK: the image does not carry the requested Ruby patch release.

Note what this does to a project's sense of its own health. If you read the check list per PR you conclude that eight pieces of work are broken. If you read #111 you conclude that one gate is mis-scoped and two runner images moved, and that no individual author can fix any of it inside their own diff. #112 then proved the first half of that by fixing the core.py half and pushing the gate to diff-scoping in 4abd005 (fix(ci): diff-scope the Syntax gate like hygiene + rebuild lost pipeline-1 concept.py (#114)).

What broke. For an unknown number of days, every branch in the repository was scored against pre-existing debt on main. The mechanism was a workflow file that used git grep over the whole ref where the sibling workflow used a diff. Nothing was misconfigured loudly; the gate did exactly what it was written to do. It was simply written to ask a question about the tree when the useful question was about the change.

What we learned. A gate that is not diff-scoped converts every historical defect into a permanent veto on new work, and it does so silently, because a red check looks like a finding about the branch. The diagnostic is cheap: when several unrelated branches fail the same check, ask whether the check reads the diff or the tree. #111 also supplies the corollary, in its own list of things it cannot claim:

So "get all 7 checks green on #103" cannot be done inside #103. It needs two decisions outside any agent's diff.

That sentence is the most useful thing in the document, because it tells an agent where its authority ends. Two of the four causes were runnable-image decisions and one was a policy decision; none was a code change in the branch under review.

The access path, and the claims it corrected

PR #111 also landed docs/ops/GITHUB_ACCESS.md and docs/ops/agent-worklog.md, and its body corrects three claims that were circulating. Reproducing the shape of those corrections matters more than their content:

  1. A branch reported as "never pushed because the disk filled" had in fact been at

44c687d564fdda2fb56326954bd1d16038b32732 since 2026-10-24, with an open PR and eight changed files. The disk did not block it; the claim was simply false.

  1. A credentials story about a key on the publish host was not an access path at all: the host was

unreachable and nothing could be read from it.

  1. "The gh CLI is installed" was untrue in the agent sandbox, and the token environment variables

were unset. Documenting it as available would have reproduced the same failure in the next round.

The third is the one to keep. The failure mode is not believing something false; it is writing the false thing down as procedure, where it becomes the reason the next agent does not try.

The worklog on that branch is the closest existing precedent for this document, and it contains the sentence every future round should be graded against:

Agents with no branch, no commit and no committed URL for this round are recorded here as failed at checkpoint. Nothing in this file may be softened to "in progress" after the deadline: in progress without a SHA is not delivered.

That sentence is also the standard this document is held to, and it is why §3 publishes a table of forty-character SHAs rather than a paragraph of reassurance.
