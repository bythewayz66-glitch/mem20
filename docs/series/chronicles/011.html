The commit that says 162 and landed 155

2026-11-01 grounded 793 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

On 27 October, at 09:39:57 local, a commit landed on main with this subject:

78d28ad8 Land 162 files from the verified working tree (docs, SDKs, MCP tools, controlz, benchmarks)

A subject like that is a claim about a diff, and the first rule of reading this repository is that a commit's message is not evidence of its diff. So:

$ git log -1 --format='%h parents=%p' 78d28ad8
78d28ad8 parents=b44eff6f

$ git show 78d28ad8 --shortstat --format=''
 155 files changed, 16728 insertions(+), 2021 deletions(-)

$ git show 78d28ad8 --name-only --format='' | wc -l
155

Three numbers, and they do not agree with the subject. The subject says 162. The diffstat says 155 files changed. The name-only listing says 155 paths. The two measurements agree with each other and disagree with the prose.

This is not a rounding error and it is not a mystery. It is the difference between a count taken while the work was being assembled and a count taken from the tree that resulted. Seven files that were expected to be in the commit were not in it. Whether they were already present, or excluded, or simply never staged, the commit does not say — and that is the finding, because a commit whose subject advertises a file count is a commit that invites a reader to trust the count instead of running the command.

The parentage is the more important number

parents=b44eff6f — one parent. Not a merge.

This matters more than the file count. A single-parent commit that lands 155 files records no merge, no per-branch decision and no provenance. It records a diff between two trees. The subject describes a campaign — "the verified working tree" — and the object is a working-tree copy. There is no record in the commit of which branches contributed, which files came from where, or what was deliberately left out.

The same shape appears twice more in the same morning:

$ git log -1 --format='%h parents=%p %s' 0d9d3a38
0d9d3a38 parents=3f3e470c converge: land the residue from the 9 branches that still held unique files

$ git show 0d9d3a38 --shortstat --format=''
 39 files changed, 3389 insertions(+), 483 deletions(-)

"the residue from the 9 branches" — nine branches, one parent, 39 files. The commit names nine sources and records none of them. A reader who wants to know which nine branches, and whether all nine were fully drained, cannot answer from the commit. They can only answer from the branch inventory, which is a different document written two days later by a different agent.

What broke. A commit subject advertised 162 files; the diff contains 155. The commit that "landed the residue from the 9 branches" has one parent and names none of the nine. What we learned. A file count in a subject is a claim about a diff, and the diff is one command away. The count was wrong by seven and nobody noticed for five days, because the number was plausible and the work was real. The provenance gap is the more expensive defect: the files are there, but the record of how they got there is not, and that record cannot be reconstructed after the fact. Publish the diffstat, not the subject. And when a commit drains several branches, make it a merge or list the branches in the body — a single-parent commit is a copy, and a copy has no history.

The convergence commits that came before the inventory

The 27 October morning also produced a run of commits whose subjects read like a convergence campaign:

cc3525d0 converge: land the desktop collision chain (#35 -> #36 -> #37 -> #40)
1fd2399a Add the 8 files that existed only in the local tree (Ruby SDK core, controlz web + tauri)
3f3e470c Fix a corrupted line in mem20controlz/src-tauri/src/lib.rs
0d9d3a38 converge: land the residue from the 9 branches that still held unique files
a366ff74 fix(ops): repair truncated metrics_collector.py and add --since repo-metrics mode (#135)

Read as a sequence, this is a recovery operation: a working tree that had diverged from the repository was being reconciled into it, file group by file group, with the corrupted and truncated files repaired as they were found. a366ff74 is the most specific of them — "repair truncated metrics_collector.py" — and it is the same defect class that recurs in §8, where a 352-line document was found truncated to a 356-byte stub. Truncation is a recurring failure mode in this repository, and it recurs because the tooling that writes files can fail partway and report success.

The 27 October work is also where the previous instalment's frontier sits. e7758bd1 is the commit this post's window opens after, and the convergence campaign above is the first thing in it.
