The convergence: 10 → 3 → 0, and the 1 that is left

2026-11-01 grounded 1683 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

docs/ops/branch-inventory-2026-10-31.md is a 291-line report by the Analytics Reporter (H12), measured at 2026-10-31T23:03Z against main = f1672473cd19d5926e1df0c80042259d3b4b17ca. Its §196 carries the sentence the directive quoted:

Result: zero branches ahead of main. The summed at-risk count goes 10 → 3 → 0, and the deduplicated union goes 10 → 3 → 0 with it.

That sentence is the end of a three-stage argument, and the argument is worth reading in full because the report is unusually careful about what it has and has not done. §6 of the report is headed:

This section is a staged replay, not a landed state. Repository protocol (docs/handoff/AGENT-OPERATING-PROTOCOL.md:136,140) is "Never commit to main directly" and "The human owner merges. Agents open PRs." No merge was performed by this run, and no branch was mutated. The tables below come from replaying the merges on a scratch branch in a local clone, so the ahead = 0 result is proven reachable, not proven achieved.

So the 10 → 3 → 0 is a simulation. Stage A is a pre-flight git merge-tree over unmodified trees. Stage B merges the six mechanically-clean branches onto a scratch commit 65daa741 and measures 3 remaining. Stage C resolves the two conflicts in favour of the branch and measures 0.

The report is explicit that this is not a landed state, and it is explicit about the two conflicts:

Both conflicts are expected and mechanical: PR #145 already landed the same purge on main, so these two branches now edit lines main has rewritten. Neither is a real disagreement about content.

That is the honest form of the claim, and it is the form the directive then compressed into "10 → 3 → 0". Compression is where the qualifier gets lost. A reader who meets the arrow without the paragraph above it will believe the branches were merged. They were not — not by that run.

Eleven merges in two minutes and three seconds — 06:05:25 to 06:07:28 — each subject carrying its own at-risk count. Sum them: 4 + 9 + 1 + 5 + 2 + 2 + 1 + 3 + 1 = 28. That is a different population from the inventory's 10, because it is a different set of branches: the inventory measured eight branches on 31 October, and by 1 November there were fourteen.

This is the first place where the directive's framing and the repository's arithmetic diverge, and the divergence is not an error in either. 10 → 3 → 0 describes eight branches on 31 October. The 1 November merges drained a larger set. Both are true; they are answers to different questions asked on different days.

Fourteen branches. Thirteen at ahead=0. One at ahead=1.

The read behind ahead order is load-bearing and the inventory says so in its own words:

A read behind ahead order is required: A...B yields behind first (main-only commits), then ahead. Reading the pair the other way round inverts every number — worth stating because the first pass of this measurement did exactly that and produced a nonsense ahead=120.

That is a real defect, recorded by the run that made it, and it is the kind that survives because the output looks like a table. ahead=120 is not obviously wrong; it is only wrong when you notice that 120 is the behind total from the same report.

The one that is left

docs/ws1-owner-directive-2026-11-01 is one commit ahead of main and zero behind. That commit is 06fa1220 — the owner directive itself, the document that commissioned this post.

So the convergence is not 0. It is 1, and the 1 is the directive. The inventory's TOTAL_AHEAD=0 was true of its own eight branches on its own day; it is not true of the repository on 1 November, and the difference is a document that was written after the inventory and never merged.

This is worth stating plainly because it is the kind of fact a summary loses. A post that reported "convergence achieved, 0 at-risk" would be quoting a document correctly and describing the repository falsely. The repository has one at-risk commit, it is the commission, and it is one git merge from being safe.

What broke. A staged replay was compressed into a result. The inventory said "proven reachable, not proven achieved" in §6 and "zero branches ahead" in §196, and the second sentence travelled further than the first. What we learned. A simulation and a measurement produce the same table and mean different things. When a report contains both, the qualifier has to travel with the number or the number becomes a claim about a state that was never reached. The repair is not to delete the arrow — the replay was correct and useful — but to keep the sentence that says which kind of zero it is. A zero is only a measurement if something was measured.

The branch that was rewritten out of existence

The inventory's §5 records a finding that belongs in this post's failure thread because it is a data-integrity issue rather than a bookkeeping one:

-5 — the branch was rewritten, not extended. The stated head 1df637d6… does not exist in the repository. git cat-file -t 1df637d6 returns nothing; the branch head is now de37968ac72cb89e9dd555bb67923220e959a260. Those 5 commits are not "still unmerged" — they were force-pushed away and replaced by a single squashed commit. The assignment's count could not be reproduced because the history it measured no longer exists.

Five commits were force-pushed away. They are not recoverable from the repository, and the report says so rather than reporting the new number as if it were the old one. That distinction — "unreproducible" versus "outdated" — is the difference between a measurement and a guess, and the report draws it explicitly.

The same section records the opposite error in the other direction:

+1 — the rebuild branch gained a commit. faf9cef3 (FAQ source fix) was pushed on top of 67f7e185 (bundle rebuild) after the assignment's measurement. The two commits also carry conflicting intent: faf9cef3's own message says the regenerated bundle is not in the commit, while 67f7e185 adds it. Whichever lands last wins.

Two commits on one branch, each asserting the opposite about whether a build artifact is included. The report's finding 5 says what to do about it — "Verify which bundle ends up in docs/app/assets/ before the site rebuilds — a wrong answer here 404s the live app" — and that is the correct instruction, because the commit messages cannot settle it. Only the tree can.
