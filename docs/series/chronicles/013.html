270 tools, 27 domains, and the number that is editorial

2026-11-01 grounded 1275 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

The directive's G3 records the launch artifacts as stale on version:

docs/index.html and the served https://mem20.com/ both contain 270 tools ×8, 27 domains ×8, and v3.0.0 ×4 — while VERSION = 3.1.0 and tag v3.1.1 exists.

The first two of those reproduce exactly:

$ grep -c '270 tools' docs/index.html
8
$ grep -c '27 domains' docs/index.html
8
$ grep -o 'v3\.[0-9]\.[0-9]' docs/index.html | sort | uniq -c
      4 v3.0.0

Eight, eight, four. The page says 270 tools and 27 domains in eight places each and calls itself v3.0.0 in four, while VERSION on main reads 3.1.0. That is a real staleness and the directive is right about it.

But "270 tools / 27 domains" is two numbers travelling together that do not have the same status, and the repository contains a document that says so.

270 is confirmed by two independent methods

$ grep -rho 'self\.tools\["[^"]*"\]' mcp --include=*.py | wc -l
271
$ grep -rho 'self\.tools\["[^"]*"\]' mcp --include=*.py | sort -u | wc -l
270
$ grep -rn 'def register_.*_tools' mcp --include=*.py | wc -l
28

271 registration sites, 270 distinct names, 28 registrars. And the runtime agrees:

$ cd mcp && python3 -c "
from server import Mem20MCPServer
s = Mem20MCPServer()
print('RUNTIME len(server.tools)=', len(s.tools))
print('has lie_status:', 'lie_status' in s.tools)
"
RUNTIME len(server.tools)= 270
has lie_status: True

len(server.tools) is the authoritative count — it is exactly the dict _handle_list_tools returns to an MCP client. 270. Two methods, different in kind (a static grep and a constructed server), agreeing to the digit.

27 is not a property of the code

docs/ops/surface-measurement-2026-10-31.md is an independent measurement taken at 8f0a310d5dbcb77e92188dd2312516d47ea0bffd, and its verdict table is blunt:

Claim under testResultStatus
270 unique tools270CONFIRMED by two independent methods
28 register_*_tools groups28CONFIRMED
27 domainsnot reproducible from the codeREFUTED as a code-derived number
Which group is "not a domain"register_a2a_toolsnamed below, with evidence
The repo ships 270 tools across 28 registration groups. "27 domains" is an editorial subtraction performed by docs/TOOL-DOMAINS.md, not a property the code exposes.

That is the finding, and it is a good one, because it separates two numbers that had been travelling together. 270 is measured. 27 is a decision — someone looked at 28 registrars, decided that register_a2a_tools is an inter-agent transport rather than a tool domain, and subtracted it. The subtraction is defensible. It is not a measurement, and docs/TOOL-DOMAINS.md presents it as one:

270 tools across 27 domains. This file is the ground truth for both numbers. It is generated from the registry itself, not hand-counted, so it cannot drift silently.

"Generated from the registry itself" is true of 270 and false of 27. The 27 comes from a table row that reads minus the A2A Hermes layer | −1 | register_a2a_tools — an inter-agent transport, not a tool domain. That is an editorial judgement written in the grammar of a derivation.

Twenty-seven lines, each with a count of 1. The 28th — register_a2a_tools — is not in this list because the grep pattern def register_[a-z_]_tools does not match it: the name contains a digit. That is a small, instructive detail. The count of 28 came from def register_._tools, which matches; the listing above used a narrower pattern and returned 27. Two greps, two answers, one of them wrong — and the wrong one is the one that happens to agree with the claim under test. That is the most dangerous possible coincidence, and it is why the surface measurement used two methods of different kinds rather than two greps.

The duplicate that is not a duplicate

docs/ops/tool-count-270-27.md explains the 271 → 270 gap:

lie_status is assigned twice — mcp/tools/lie_tools.py:69 and :77. The second assignment overwrites the first, so the server exposes 270 tools while the source contains 271 assignments.

The line numbers are right. The mechanism is wrong. Here is the code:

    def register_lie_tools(self):
        if not LIEZ_AVAILABLE:
            # Still register a status tool so the absence is visible
            self.tools["lie_status"] = mt.Tool(
                name="lie_status",
                title="Lie / Behavioural Signal Status",
                description="Report whether mem20liez is available",
                inputSchema={"type": "object", "properties": {}},
            )
            return

        self.tools["lie_status"] = mt.Tool(
            name="lie_status",
            title="Lie / Behavioural Signal Status",
            description="Report mem20liez availability and active sessions",
            inputSchema={"type": "object", "properties": {}},
        )

The first assignment is followed by return. The two assignments are mutually exclusive branches, not an overwrite. Exactly one executes, always. There is no defect here at all — the pattern is deliberate and correct: register a status tool either way, so that a missing optional dependency is visible to a client rather than silently absent.

So the arithmetic reconciles (271 sites, 270 distinct, 270 at runtime) and the stated cause does not. The document says "the second assignment overwrites the first", which would be a bug worth fixing. The code says "one branch or the other", which is a design worth keeping. A reader who trusted the ops note would go looking for a defect that is not there, and might "fix" a correct pattern.

What broke. An ops note explained a real 271-vs-270 gap with a mechanism that is not in the code. The numbers were right; the cause was invented by reading two line numbers and not the control flow between them. What we learned. A count discrepancy has a cause, and the cause is a claim like any other. Two assignments to the same key look like an overwrite until you read the return between them. The note's own conclusion — "This run did not fix it: removing a tool registration changes the exposed schema, which is a behaviour change and belongs with the tests" — was the right call for the wrong reason, and it is the reason the wrong explanation survived: nobody was going to touch the code to check. Read the control flow, not the line numbers.

What the 27 actually costs

None of this makes the launch page wrong to say 27 domains. It makes the word "domain" a product decision rather than a code fact, and the cost of blurring that is specific: when the next registrar is added, 270 will move by measurement and 27 will move by whoever remembers to edit the table. One of those two numbers is self-maintaining and the other is not, and the document that presents both as "generated from the registry itself" has removed the reader's ability to tell which is which.

The honest sentence is: 270 tools across 28 registration groups, presented as 27 domains because the A2A transport layer is not counted as a domain. That sentence is longer and it is checkable.
