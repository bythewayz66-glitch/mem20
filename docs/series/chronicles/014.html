The tag that was cut before the release it names

2026-11-01 grounded 1140 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

This is the finding that gave the post its title, and it is the one that no document in the repository states. It came out of a single loop over three tags:

$ for t in v3.0.0 v3.1.0 v3.1.1; do
    sha=$(git rev-parse "$t^{commit}")
    anc=$(git merge-base --is-ancestor "$sha" HEAD && echo ANCESTOR || echo NOT-ON-MAIN)
    echo "$t -> $sha  $anc  $(git log -1 --format='%aI' $sha)  VERSION=$(git show $sha:VERSION)"
  done
v3.0.0 -> a366ff741f484b5d7e998be1f2794fb8ec1c8d4d  ANCESTOR  2026-10-27T09:52:04-06:00  VERSION=3.0.0
v3.1.0 -> 73343f6853ec4b3577198e783c89bbb1a5526bf2  ANCESTOR  2026-10-31T22:53:18+00:00  VERSION=3.1.0
v3.1.1 -> 52ffe13d046078822f21d51b38cb76a226dfe42f  ANCESTOR  2026-10-31T16:42:41-06:00  VERSION=3.1.1

Read the timestamps. v3.1.1 is dated 16:42:41−06:00. v3.1.0 is dated 22:53:18+00:00.

Those are the same clock expressed two ways, and the conversion is the whole story. 22:53:18+00:00 is 16:53:18−06:00. So v3.1.0 was cut at 16:53:18 local and v3.1.1 at 16:42:41 local — eleven minutes earlier.

The ancestry confirms it, and ancestry is the check that does not depend on trusting a timestamp:

$ git merge-base --is-ancestor 52ffe13d 73343f68 && echo YES || echo NO
YES

52ffe13d — the commit tagged v3.1.1 — is an ancestor of 73343f68, the commit tagged v3.1.0. The graph makes the order unambiguous:

$ git log --oneline --graph --decorate -8 73343f68
* 73343f68 (tag: v3.1.0) chore(release): cut v3.1.0 at main 6b3bdca2
* 52ffe13d (tag: v3.1.1) chore(release): bump VERSION to 3.1.1
*   3a32b3d9 docs(daily-reports): file 10-27 and 10-31; record 10-28/29/30 as NOT FILED gaps (#143)
|\
| * f25b57d7 docs(ops): close the daily-report record gap 2026-10-27 -> 2026-10-31
* | 6b3bdca2 chore(deps): update aiohttp requirement from >=3.9 to >=3.14.5 (#142)
* | f05dc860 chore(deps-dev): bump vite from 5.4.21 to 8.3.5 in /dashboard (#141)
|/
* bc3dfaea feat: make last 5 modules first-class (0 stubs remaining)

52ffe13d sits directly beneath 73343f68. The higher version number was committed first, and the lower one was committed on top of it.

What that does to VERSION

The consequence is visible in one command:

$ git show HEAD:VERSION
3.1.0
$ git show v3.1.1:VERSION
3.1.1

main at the frontier declares itself 3.1.0. The tag v3.1.1 — which is an ancestor of main, and therefore already contained in it — declares 3.1.1. The repository's own version file went backwards relative to a tag it already contains.

This is not a mystery once the order is known. 52ffe13d bumped VERSION to 3.1.1. Then 73343f68 — "cut v3.1.0 at main 6b3bdca2" — wrote VERSION back to 3.1.0 as part of cutting the 3.1.0 release. The second commit's job was to make the tag and the trunk agree, and it did that for v3.1.0 by overwriting the value the first commit had set.

The release notes for 3.1.0 describe the intent, and they are accurate about everything except the ordering:

This release closes the 93-commit gap between v3.0.0 and main. The v3.0.0 tag had drifted 93 commits behind the trunk. v3.1.0 is cut on a release commit whose parent is main at 6b3bdca2, so the tag and the trunk agree again.

"so the tag and the trunk agree again" — true of v3.1.0, and achieved by making VERSION disagree with v3.1.1. The document is not lying. It is describing one tag's reconciliation without noticing that a second tag had been cut eleven minutes earlier and was now inconsistent.

The drift the directive measured

The directive's G4 states:

Tag is 63 commits stale — compare/v3.1.1...main → ahead_by 63, behind_by 0. v3.1.0 → 62.

Both reproduce:

$ for t in v3.1.0 v3.1.1; do echo -n "$t ahead="; git rev-list --count $t..HEAD; done
v3.1.0 ahead=62
v3.1.1 ahead=63

62 and 63. And the one-commit difference is itself the evidence: v3.1.1 is one commit further back than v3.1.0, so it is one commit more stale. A tag that is older than the tag below it will always be more stale, and the 63-versus-62 pair is the arithmetic fingerprint of the ordering defect.

A reader who saw only "63 commits behind" would conclude the release process had simply not run for a while. The truth is stranger and more useful: the release process ran twice, in the wrong order, and the second run overwrote the first run's version number.

What broke. v3.1.1 was tagged at 16:42:41 local; v3.1.0 was tagged at 16:53:18 local, on top of it. VERSION on main reads 3.1.0 while an ancestor commit reads 3.1.1. What we learned. A version number is a claim about ordering, and git already records ordering independently. The two disagreed for a day and nothing caught it, because every check in the repository compares VERSION to a tag rather than to the set of tags. The check that would have caught it is one line: for each release tag, assert that VERSION at that tag is greater than VERSION at every ancestor release tag. A monotonic version is a property of the tag graph, not of a file. And when two release commits land eleven minutes apart, the second one's "make the tag and the trunk agree" is only true of its own tag.

Why the ordering happened, as far as the record shows

The record does not say, and this post will not invent a reason. What it does show is the shape: two release commits, both authored on 31 October, both touching VERSION, eleven minutes apart, with the higher number first. 73343f68's subject says "cut v3.1.0 at main 6b3bdca2" — it names its parent explicitly, which is the behaviour of a commit written to repair a known drift. 52ffe13d's subject says "bump VERSION to 3.1.1" — a bump, not a cut.

The most economical reading is that a 3.1.1 bump was prepared, and then a 3.1.0 cut was performed to close the 93-commit gap from v3.0.0, and the cut did not know about the bump. That reading is consistent with every fact above and is stated here as a reading, not as a finding. The finding is the ordering, and the ordering is in the graph.
