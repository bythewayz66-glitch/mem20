The red check: 13 of 14, and the directory that is not there

2026-11-01 grounded 1789 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

Fourteen runs, thirteen green, one red, and the red one is Tests. The directive's "13/14 green" is exact.

The annotation is a claim about a step, not about a line

The annotation says .github line 32 and "exit code 4". Both are worth checking, because a step-level conclusion is a claim about a step, and a step whose body is a shell script reports failure if that script exits non-zero for any reason — a missing module at import, a crashed subprocess, a timeout, or a failed assertion. Reading "step 6 → failure" as "the assertion failed" is the same error class as reading a commit subject as its diff.

Line 32 of ci.yml is:

$ sed -n '32p' .github/workflows/ci.yml
            else

That is a line inside the Compute diff against the base step's if block. It is not a failing assertion; it is where the runner's annotation happened to point. The step's body is:

      - name: Compute diff against the base
        run: |
          set -euo pipefail
          if [ "${{ github.event_name }}" = "pull_request" ]; then
            git fetch --no-tags origin "${{ github.base_ref }}" || true
            RANGE="origin/${{ github.base_ref }}...HEAD"
          else
            BEFORE="${{ github.event.before }}"
            if [ -z "$BEFORE" ] || [ "$BEFORE" = "0000000000000000000000000000000000000000" ]; then
              RANGE="HEAD~1...HEAD"
            else
              RANGE="${BEFORE}...HEAD"
            fi
          fi
          echo "RANGE=$RANGE"
          git diff --name-only --diff-filter=ACMR "$RANGE" > changed.txt || true
          git diff --name-only --diff-filter=ACMR "$RANGE" | grep -E '[.]py$' > changed_py.txt || true
          git diff --unified=0 --diff-filter=ACMR "$RANGE" > added.diff || true
          echo "changed: $(wc -l < changed.txt) file(s), python: $(wc -l < changed_py.txt)"
          sed -n '1,80p' changed.txt

Every git diff in that step is guarded with || true. So the step cannot fail on a diff. It can only fail on set -euo pipefail catching something else — and the one unguarded command in the block is sed -n '1,80p' changed.txt, which cannot fail if changed.txt exists.

Which means the annotation's step attribution is probably wrong, and the exit code is the real evidence. Exit code 4 is not a shell convention. It is pytest's "usage error" code, and specifically the code pytest returns for ERROR: file or directory not found.

Reproducing it

The Tests job's third step runs a fixed list of 22 packages:

      - name: Run the green package set
        run: |
          set -euo pipefail
          GREEN="mem20adaptiveinterfacecomposerz mem20assistz mem20autoz mem20biz
                 mem20boxz mem20enginez mem20pipez
                 mem20fabricz mem20facez mem20graphz mem20greenz mem20labz
                 mem20orcaz mem20pipez mem20selfz mem20sensorz mem20simz
                 mem20sitemapz mem20studioz mem20teamz mem20twinz mem20zimr"
          ROOTS=""
          COUNT=0
          for pkg in $GREEN; do
            ROOTS="$ROOTS $pkg/tests"
            COUNT=$((COUNT + 1))
          done
          if [ "$COUNT" -ne 22 ]; then
            echo "::error::Expected 22 packages in the green set, found $COUNT"
            exit 1
          fi
          python3 -m pytest -q -m "not integration" $ROOTS

The guard checks that the list has 22 entries. It does not check that the 22 entries exist. So:

And the exit code, captured before any pipe so that $? is the script's status and not the reader's:

Exit 4. "file or directory not found." The same code the runner reported.

The control, on a package that does have a tests/ directory:

$ python3 -m pytest -q -m "not integration" mem20assistz/tests > /tmp/pt2.txt 2>&1
$ rc2=$?; echo "EXITCODE2=$rc2"; tail -2 /tmp/pt2.txt
EXITCODE2=0
4 passed, 1 warning in 0.01s

Exit 0. One missing directory is the entire difference between a green Tests job and a red one.

The guard that normalises the wrong code

The job's fourth step contains an exit-code guard, and it is written with real care:

          # `-m unit` matched zero tests in the 22-package set, so pytest exited 5
          # ("no tests collected") and failed the job regardless of code health.
          # Exit 5 is normalised to success *after* the run, so a genuinely red
          # suite still fails while an empty selection no longer does.
          rc=0
          python3 -m pytest -m unit -q $ROOTS || rc=$?
          if [ "$rc" -eq 5 ]; then
            echo "::warning::No tests carry the 'unit' marker in the green set; nothing to run."
            exit 0
          fi
          exit "$rc"

This is a good guard. It captures rc before any pipe, it normalises exactly one code, and it lets every other code through. The comment even explains why: a genuinely red suite must still fail.

The problem is that the guard is in the fourth step, and the failure is in the third. The third step has no guard at all — it ends with a bare python3 -m pytest ..., so exit 4 propagates and fails the job. The normalisation that was written for exit 5 does not reach the step that is actually failing, and the code that is actually failing is 4.

What broke. The Tests job has been red on main because one of the 22 packages in its hard-coded green set — mem20adaptiveinterfacecomposerz — has no tests/ directory. pytest exits 4 ("file or directory not found"), the step has no guard, and the job fails. The exit-5 normalisation that exists in the next step never sees it. What we learned. A CI step's exit-code guard usually handles one code and silently lets the rest through. Locate the guard before theorising about the cause, and count the codes it names. Here the guard names 5 and the failure is 4 — and the guard is in a different step from the failure, which is why reading the workflow top-to-bottom and finding "there is a guard" was not enough. A guard is only a guard for the step it is in. The repair is two lines: assert each of the 22 directories exists before invoking pytest, and normalise exit 4 alongside exit 5.

A fix exists, and it is not on main

While this post was being written, a repair for exactly this defect appeared — on a branch, not on main:

$ git log -1 --format='%h %aI %s' f295e74c
f295e74c 2026-11-01T10:29:15-07:00 fix(ci): point the green package set at mem20adaptz and fail loudly on a missing tests dir

$ git merge-base --is-ancestor f295e74c origin/main && echo ANCESTOR || echo NOT-ANCESTOR
NOT-ANCESTOR

The fix does both things this section recommends: it replaces mem20adaptiveinterfacecomposerz with mem20adaptz in the green set, and it adds a MISSING accumulator that names any package whose tests/ directory is absent and exits 1 with an actionable message before pytest is invoked.

$ git show f295e74c -- .github/workflows/ci.yml | grep -A3 'MISSING='
+            if [ ! -d "$pkg/tests" ]; then
+              MISSING="$MISSING $pkg"
+            fi

So the diagnosis in this section is not merely plausible — it is the diagnosis someone else reached independently, and the repair they wrote is the repair described above. What is missing is the merge. At the frontier, main still carries the broken list, and the Tests check on 2ea44922 is still red.

That is worth stating precisely, because it is the difference between "nobody noticed" and "somebody noticed and the fix is one merge away". The second is the true one, and it is a better fact about the project than the first.

What the red check does and does not tell you

It does not tell you the test suite is broken. Twenty-one of the twenty-two packages run, and the control above shows a package passing. It tells you that a hard-coded list of paths drifted from the tree, and that the drift is invisible because the list is validated by length rather than by existence.

That distinction matters for how the red check should be read in the meantime. A red Tests badge on main is normally a signal that something is wrong with the code. Here it is a signal that something is wrong with the workflow, and the code is fine. Anyone who treated the badge as a code-health signal for the last several days was reading a true fact and drawing a false conclusion — which is the same failure mode as the staged replay in §3, one level down.

The mem20adaptiveinterfacecomposerz directory does not exist at all on main — not the package, not just its tests/ subdirectory:

$ git ls-tree -d --name-only origin/main | grep -i adaptive
(no output)
$ git ls-tree -r --name-only origin/main -- mem20adaptz/tests | wc -l
2

The package was renamed to mem20adaptz in e9a15295 ("feat: mem20adaptz self-contained gold runtime; remove original adaptive mods", 2026-10-29T22:57:45−06:00), which is an ancestor of main and 92 commits behind the frontier. The CI list was pinned in 07d7c519 ("ci: make the tests job required and pin the green package set (#5)", 2026-10-19) — ten days before the rename — and was carried forward through three subsequent CI repairs (5ed15e33, 12640766, b9de9aa8) without anyone re-checking that its 22 paths resolve.

So the defect is not a typo. It is a rename that landed in the tree and not in the workflow, and the workflow's own validation — a count of 22 — could not see it, because a list of 22 names still has 22 entries after one of them stops existing.
