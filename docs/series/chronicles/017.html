Truncation: the failure mode that keeps coming back

2026-11-01 grounded 632 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

Three commits in this window are repairs to files that had been silently truncated. They are worth reading together, because the pattern is identical each time and the pattern is the lesson.

$ git log -1 --format='%h %aI %s' d7d67a4f
d7d67a4f 2026-11-01T06:16:56-07:00 restore: full GTM claim ledger v6 on main (352-line body was truncated to a 356-byte stub)
$ git show d7d67a4f --shortstat --format=''
 1 file changed, 342 insertions(+), 1 deletion(-)

$ git log -1 --format='%h %aI %s' a36a34a5
a36a34a5 2026-11-01T06:18:42-07:00 fix(deck): restore truncated PERMANENT_URL record and pin slides to VERSION 3.1.0
$ git show a36a34a5 --shortstat --format=''
 5 files changed, 99 insertions(+), 6 deletions(-)

d7d67a4f is the clearest case. A 352-line document had become a 356-byte stub. The repair added 342 lines and deleted 1. The file at the frontier:

$ wc -l docs/gtm/claim-ledger.md
342 docs/gtm/claim-ledger.md

342 lines, against a subject that says 352. The difference is not necessarily an error — a restore can legitimately land a slightly different body than the one that was lost, and the subject's "352-line" may describe the pre-truncation file rather than the restored one. But it is the second time in this post that a subject's file count and the tree's file count disagree, and the first was §2's 162-versus-155.

The third instance is older and is in the failures corpus, from the kiln subproject:

2026-09-26 — A salvage implementation that deleted the functions after it. The script counted braces without skipping string literals, so its match ran past the intended function and deleted everything up to the next coincidental brace balance. […] this was an unreviewed destructive edit to a 1,478-line file.

And a fourth, from the same corpus, is the inverse:

2026-09-26 — Truncated model output discarded every complete op. The model ran out of tokens part-way through the array, and extract_json_array required a closing ], so the whole response was thrown away — including the ops that were already complete and valid.

Four instances, three mechanisms, one shape: a write that stops partway and reports success. The brace-counting script wrote a truncated file. The model returned a truncated array. Whatever wrote the GTM ledger wrote 356 bytes of a 352-line document. Whatever wrote the deck's PERMANENT_URL record wrote a truncated one.

What broke. A 352-line claim ledger was committed as a 356-byte stub and stayed that way until someone noticed. A deck's permanent-URL record was truncated the same way. Both were repaired on 1 November, within two minutes of each other, by commits whose subjects name the truncation. What we learned. Truncation is the failure mode that survives review, because a truncated file is a valid file — it parses, it renders, it commits. Nothing in the toolchain objects. The only reliable detector is a size or line-count assertion against an expected value, and the repository did not have one for either file. The kiln corpus already contains the rule, written after the brace script: "Read the diff after deleting debug code." The general form is stronger: assert the artifact's size, not its validity. A 356-byte file that parses is still a 356-byte file.

The two 1 November repairs are also a small piece of good news about the process. They landed at 06:16:56 and 06:18:42, two minutes apart, in the same run that merged eleven branches. Someone was reading the tree rather than the reports, found two truncated files, and fixed both. That is the behaviour the program's own culture asks for, and it happened on the same morning as the convergence.
