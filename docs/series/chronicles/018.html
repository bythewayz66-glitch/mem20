The corpus that stops a month before the window

2026-11-01 grounded 1405 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

The failures corpus was located and read in full for this post, and the search was re-run rather than recalled, because the corpus grows:

Two of the seven are false positives: a test file whose name contains "failure", and a React component whose name contains "retro". Recording them as false positives rather than filtering them silently matters, because a pattern search that quietly drops its own noise gives a reader no way to tell a clean search from a narrow one.

The newest date in the entire corpus is 2026-09-29. The window this post covers begins 2026-10-27. The corpus stops twenty-eight days before the window opens.

That is the finding, and it is a bigger one than any individual entry. The failures corpus — the document the program's own culture treats as the record of what went wrong — is silent about the entire period this post narrates. Every failure in §2, §3, §5, §6 and §8 of this post was reconstructed from commit subjects, ops documents and a CI reproduction. None of them is in the ledger.

The corpus is not abandoned; it is scoped. mem20kilnz/failures.md is the kiln subproject's ledger, and kiln's work stopped in late September. failures.md is the estate-level ledger, and the estate's work moved on. What did not happen is the thing the corpus's own format implies: a new ledger for the new work.

What the corpus does contain, and why it still matters

The corpus is not decoration in this post, because its entries are the precedent for every failure class the window exhibits. Three of them map directly:

The hand-summed count. mem20kilnz/failures.md, 2026-09-25:

Attempt: stated "Count: 263" in PROPOSAL.md §6.2. Actual error: the per-family subtotals in the same paragraph summed to 212. The 263 was not derived from anything; it was wrong. Cause: hand-summed headline figure never reconciled against the item list. The subtotals were correct, which is exactly why it survived a read-through. Rule learned: never publish a hand-summed count. Publish the grep.

That rule is the reason §4 of this post prints three greps and a runtime count instead of quoting "270 tools / 27 domains". It is also the rule that the docs/ops/tool-count-270-27.md note broke when it explained the 271→270 gap with a mechanism that is not in the code.

The count that is right for the wrong reason. Same file, 2026-09-25:

Attempt: report dead declarations in the engine as a Phase 1 blocker. Actual error: I first reported nine. The true count is sixteen. My check grepped nine names I had picked by hand and confirmed each appeared exactly once. It never audited the full declaration list, so seven more were missed. Cause: sampling the header by hand instead of enumerating it.

This is §4's narrower-grep problem in its original form. A grep that returns the number you expected is not evidence; it is a coincidence until a second method of a different kind agrees. The surface measurement's two-method design — static grep plus constructed server — is the fix, and it is the fix because of this entry.

The decimator that refused. Same file, 2026-09-27:

Decision: decimate defaults to cluster, the only method measured to preserve the surface (watertight, 0 degenerate, 0 non-manifold). method: "qem" refuses with that reason rather than returning a larger mesh. A decimator that hits its triangle count while destroying the shape is worse than a simpler one that preserves it, and one that returns 278% of the input is not a decimator at all.

This is the most important entry in the corpus and it is the one this post most wants to carry forward. A component that refuses rather than returning a broken result is the highest form of the honesty the program claims. The QEM decimator was measured at 1,470 triangles out of 528 — 278% of its input — and instead of shipping it, the team made it refuse and kept the method that worked.

The window has an analogue. §3's inventory refused to call its replay a landed state. §6's guard refuses to normalise a code it was not written for. §4's surface measurement refused to confirm "27 domains" because the code does not expose it. Three refusals in five days, each one a place where the easier sentence was available and was not written.

What broke. The failures corpus has no entry after 2026-09-29. Twenty-eight days of the program's most active period — 166 commits, a release, a convergence, a red gate — produced no ledger entries at all. What we learned. A corpus that grew alongside one subproject goes silent when the work moves, and its silence reads as "nothing went wrong" rather than "nobody was writing it down". The entries that do exist are still the best material in the repository, because they are written in the register the work actually needs: attempt, actual error, cause, next action, rule. A ledger is only a record if someone is on duty. The window's failures are recoverable from commit subjects and ops documents this time; they will not be next time, because commit subjects are written by the person who already knows what happened.

The debt register, read as a prediction

2.0_roadmap/tech_debt_register.md is the other half of the corpus, and it is undated — eight rows, severity and effort scored 1–5, no commit reference and no date. That makes every row unverifiable in the strict sense: there is no tree it can be checked against.

Two rows are worth quoting because the window bears on them:

| TD-04 | mcp/* | No automated test suite until Phase 7 close; only 2 verification scripts | 3 | 3 | Add tests/ pytest suite (in progress) covering contamination, eval safety, dispatch |

TD-04 predicted the test-suite gap. §6 is what that gap looks like five weeks later: a 22-package green set with one missing directory, a guard that normalises the wrong exit code, and a red badge on main. The register called it at severity 3. The window shows the cost was not the missing tests — it was the illusion of tests, which is worse, because a red badge that means "a path is wrong" trains people to ignore red badges.

| TD-02 | memory_engine/memory.py | Vector index uses in-process FAISS; not shared across MCP processes | 3 | 4 | Document single-writer constraint; for 2.0 consider external vector store (ADR pending) |

TD-02 is the highest-severity row and it is still open. Nothing in this window touches it. That is worth saying plainly: the window's 166 commits are overwhelmingly documentation, SDK surface guards, claim audits and release mechanics. The architectural debt the register names at severity 3 is untouched, and the register's own mitigation — "Document single-writer constraint" — is a documentation task that also did not happen.
