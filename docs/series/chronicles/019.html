Mem20-naration's Chronicles · Installment 019

The archive was rewritten, and the serial has to say so first

2026-11-21 grounded 1588 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

The previous instalment's publication note is a 500-word document whose entire purpose is to be the honest record of a moving baseline. It was written on 1 November, after both parts of the instalment were committed, and it exists because main advanced from 2ea44922 to 48c241a1 while the two parts were being drafted.

It printed this transcript:

$ git log -1 --format='%h %aI %s' origin/main
48c241a1 2026-11-01T10:33:30-07:00 chore(release): cut 4.0.0 and land the owner directive

$ git show origin/main:VERSION
4.0.0

Both lines are wrong. The commit exists, the timestamp is right, and the subject and version are not.

$ git log -1 --format='%h|%aI|%s' 48c241a1
48c241a1|2026-11-01T10:33:30-07:00|chore(release): cut 3.1.2 and land the owner directive

$ git show 48c241a1:VERSION
3.1.2

The commit cut 3.1.2, not 4.0.0. Its own body says so in its first line:

G1 (red Tests) is already fixed on main by 39554320 / f295e74c — the green set names mem20adaptz and Tests is green on that SHA. This commit carries the remaining release work: - VERSION 3.1.0 -> 3.1.2 so the tree agrees with the tag being cut - CHANGELOG section for 3.1.2 covering the commits since v3.1.1 - docs/ops/owner-directive-2026-11-01.md landed from docs/ws1-owner-directive-2026-11-01 (06fa1220) so the register is on main

So the note's central exhibit is wrong. The obvious reading — and the one this post was going to publish before the diff was run — is that the note's author misquoted the commit. That reading is false, and the way it is false is the story.

1.1 The note was right when it was written

The note was committed as 1376fb47, dated 2026-11-01T10:36:33-07:00, subject "docs(narrative): publication note for serial 2026-11-01 — main moved to 3.1.2 mid-run; posts stay pinned to 2ea44922."

Read the subject. "main moved to 3.1.2." The note's author knew the version. The note was correct.

Then, seventeen days later, commit 0cd80344 — dated 2026-11-18T01:04:50Z, subject "Replace 3.1.2 with 4.0.0 across repository and include pending workspace changes" — rewrote it. The diff is five lines:

$ git show 0cd80344 -- docs/app/narrative/serial-2026-11-01-publication-note.md
-48c241a1 2026-11-01T10:33:30-07:00 chore(release): cut 3.1.2 and land the owner directive
+48c241a1 2026-11-01T10:33:30-07:00 chore(release): cut 4.0.0 and land the owner directive
-3.1.2
+4.0.0
-So `VERSION` on `main` is now **3.1.2**, not 3.1.0. The posts say 3.1.0, and they are right to: every
+So `VERSION` on `main` is now **4.0.0**, not 3.1.0. The posts say 3.1.0, and they are right to: every
-of `73343f68` (tag `v3.1.0`). Cutting 3.1.2 on top of both does not reorder them.
+of `73343f68` (tag `v3.1.0`). Cutting 4.0.0 on top of both does not reorder them.
-that `VERSION` is monotonic across its release tags. `48c241a1` cuts 3.1.2, which is higher than both
+that `VERSION` is monotonic across its release tags. `48c241a1` cuts 4.0.0, which is higher than both

Five substitutions. Every one of them replaced a true statement with a false one. The note now claims that a commit dated 1 November cut 4.0.0, which did not exist until 16 November, and it claims this in a document whose stated purpose is to be the record of what was true on 1 November.

This is not a correction. A correction would have added a line saying the figure had changed. This is a retroactive falsification of a dated record, performed by a find-and-replace that could not distinguish a live document from a historical one.

1.2 The same sweep hit the second part's verifier

The publication note is not the only delivered artefact that was rewritten. Part two (serial-2026-11-01b.md) contains a reproduction script — §11 of that post, a bash verifier that re-derives the figures the post publishes. On 9 November, commit d47c75ac ("refactor: consolidate all pipe subsystems into mem20pipez") rewrote it:

$ git show d47c75ac -- docs/app/narrative/serial-2026-11-01b.md
-                 mem20boxz mem20enginez mem20executablegameconceptandscopepipelinez
+                 mem20boxz mem20enginez mem20pipez
-                 mem20orcaz mem20pipelinez mem20selfz mem20sensorz mem20simz
+                 mem20orcaz mem20pipez mem20selfz mem20sensorz mem20simz
-OK   mem20executablegameconceptandscopepipelinez
+OK   mem20pipez
-OK   mem20pipelinez
+OK   mem20pipez

The post's verifier asserted that the green-set package list contained mem20executablegameconceptandscopepipelinez and mem20pipelinez. Those packages existed on 1 November. They were consolidated into mem20pipez on 9 November. The sweep replaced the names inside a published post's reproduction script, so the script now asserts something about a tree that never existed: a 1 November tree containing mem20pipez.

The consequence is precise and worth stating carefully. Part two's verifier no longer reproduces part two's figures. It reproduces a hybrid — the 1 November commit graph with the 9 November package names. Anyone who runs it today gets a result that is neither the post's claim nor the current state.

What broke. Two delivered, dated, pinned instalments of this chronicle were mutated by repository-wide sweeps that could not tell a historical record from a live document. The publication note was made to state a false version for a commit it correctly identified; part two's verifier was made to assert a package list that never coexisted with the tree it checks out. What we learned. The project already knows this failure mode and already wrote the rule. On 8 November, commit 0eab51ad is titled "fix(sweep): stop rewriting the immutable archive and dated records." That commit exists because a sweep had already rewritten dated records once. Six days later the sweep ran again, at repository scale, and the only thing standing between it and the archive was whatever the operator remembered. A rule in a commit message is not a control. The control is a path exclusion in the sweep script, and the sweep script did not have one. The chronicle's own archive is now the evidence for why the exclusion is needed — which is a poor way to acquire evidence, and the only way this one was acquired.

1.3 What this does to the rest of the post

It means every figure in this post has to be read as a measurement with a date, and it means the serial cannot treat its own earlier output as a source. Part one and part two are still the best record of 1 November that exists, but they are no longer a pristine record: two of their passages have been edited by later commits, and the edits are wrong.

The serial's response is the one it applies to the project: state the frontier, measure at the frontier, and record the movement separately. This post does that. It also does one thing the project's own documents do not: it prints the diff that corrupted the archive, so a reader can see exactly what was changed and by which commit.

Eight hundred and fifteen commits in twenty days is forty-one a day, and the distribution is not flat. Two days carry almost none: 10 November has zero commits on main, and 13 November has none either. Two days carry the bulk: 7 and 8 November together account for the conformance sweep described in §6, and 16 November carries the release bump and the CI churn described in §11.

The two remote heads are worth naming, because the count is the smallest it has been in the whole serial. At the frontier there were fifteen heads and the owner directive was complaining about thirteen stale refs. At publication there are two:

$ git ls-remote --heads origin
4023311072399ba4d5fe179e3860472cfbbf7835        refs/heads/fix/version-refs-2026-11-21
105b960213b0e8b0e9f02851bd0e7163eaedf447        refs/heads/main

The branch is one commit ahead of main, dated 2026-11-21T15:49:38Z — forty-one minutes before the last commit on main:

40233110 2026-11-21T15:49:38+00:00 docs: correct 39-domain claims to 129 and close the guard hole (#432, #433)

So the branch count did not fall because branches were deleted. It fell because the work was merged and the refs were pruned, and because the twenty-two agents who were pushing branches on 1 November are no longer pushing them. That is a real change in the program's shape, and §5 is about what it cost.
