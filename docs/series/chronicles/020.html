The version that was cut twice, and then rewritten

2026-11-21 grounded 1461 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

The window contains two release cuts and one repository-wide rewrite of the version string. They disagree with each other in a way that is instructive, and the disagreement is the same one that corrupted the archive in §1.

2.1 3.1.2, on 1 November

48c241a1 is a small commit doing three things: it moved VERSION from 3.1.0 to 3.1.2, it added a CHANGELOG section for 3.1.2, and it landed the owner directive from its branch onto main.

The interesting part is the first line of its body, quoted in full in §1: "G1 (red Tests) is already fixed on main by 39554320 / f295e74c — the green set names mem20adaptz and Tests is green on that SHA."

That sentence is the resolution of the red check that part two spent a whole section on. Part two §6 reproduced the failure locally, established that it was a pytest usage error (exit code 4) rather than a test failure (exit code 1), traced it to a directory named mem20adaptiveinterfacecomposerz that had been deleted in e9a15295 while .github/workflows/ci.yml kept pointing at it, and found the phantom name in two places — line 266 and line 286 — with the second hidden only because the first failed before it ran.

The fix that landed is the one the second-opinion document recommended, and it is worth recording that the recommendation was substitute, not delete:

Keep COUNT -ne 22 intact — mem20adaptz replaces the removed entry one-for-one, so the cardinality contract holds at 22 and the 13 mem20adaptz tests join the guarded set (D3). Substitute, do not delete: deleting drops the count to 21 and trips the cardinality guard at ci.yml:275-279, failing the job on the next line.

That is a small piece of engineering judgement that deserves its own line in the record. The obvious fix — remove the name that does not exist — would have turned the check green and reduced coverage, because mem20adaptz is the successor package and carries thirteen tests that CI was not running. The guard that counts names in a string cannot tell the difference between a list of twenty-two real directories and a list of twenty-two strings, so the cheap fix passes the guard and loses the tests. Substituting keeps the count and gains the coverage.

What broke. A CI job failed for twenty days with exit code 4, and the failure was read as a test failure by everyone who saw the annotation, including the owner directive that assigned it. The directive's §2/G1 attributed the failure to the Compute diff against the base step. That step concluded success in CI and replayed clean locally. The real failing step was Run the green package set. What we learned. Exit code 4 and exit code 1 look identical in a check-run annotation that says only "Process completed with exit code 4." The distinction — usage error versus failing assertion — is the difference between "the product is broken" and "the invocation is broken," and it changes who owns the fix. The second-opinion document earned its place by printing the exit-code table before printing any diagnosis. Publish the exit code's meaning, not just its value.

2.2 4.0.0, on 16 November

The second cut is 7fb3fc32, dated 2026-11-16T06:37:20Z, subject "chore(release): bump site to 4.0.0 and apply blocker fixes." It touches seventeen files with 37,165 insertions and 5,781 deletions, and the bulk of that is the regenerated agent skill catalog:

 toolchest/skills/skills.catalog.agent.json |    2 +-
 toolchest/skills/skills.index.agent.json   |    2 +-
 17 files changed, 37165 insertions(+), 5781 deletions(-)

Two lines changed in a JSON file and 37,165 insertions in the commit is not a contradiction: the catalog files are single-line JSON, so a one-line diff to a large document is a large diff. This is the kind of figure that reads as alarming in a --stat and is entirely ordinary once you know the file format. It is recorded here because a later reader comparing commit sizes will otherwise conclude that 16 November was a rewrite. It was not. The rewrite was two days later.

2.3 The rewrite, on 18 November

The third event is not a release cut. It is 0cd80344, dated 2026-11-18T01:04:50Z, subject "Replace 3.1.2 with 4.0.0 across repository and include pending workspace changes."

Ninety-seven files, 15,861 insertions, 260 deletions. The subject is doing two jobs at once and the second one is the one that matters: "and include pending workspace changes." A commit that sweeps unrelated working-tree state into a version bump is the same failure mode the failures corpus records on 6 November, where a shared working tree meant git commit swept another agent's staged files into 87f4d4e5:

2026-11-06: Shared working tree race — staging only my files was not enough because another agent had already staged its mem20assistz files, so git commit swept them into 87f4d4e5. NEXT ACTION: done — use git commit --only <paths> for every commit in a shared tree. The swept files were byte-identical to the other agent's staged work, so no content was lost or reverted.

The 18 November commit does not record whether the swept changes were byte-identical to anything. It records that they were included. That is a weaker statement than the 6 November entry, and the difference is the point: the 6 November entry could say no content was lost because someone checked. The 18 November entry cannot, and does not claim to.

And this is the commit that rewrote the publication note. The same find-and-replace that moved VERSION from 3.1.2 to 4.0.0 across the repository also moved it across a dated record of what VERSION had been on 1 November. The sweep was correct about the live tree and wrong about the archive, and it had no way to tell the difference.

What broke. A version-string rewrite landed as a 97-file commit whose subject admits it carried unrelated working-tree state, and which retroactively falsified a delivered instalment of this chronicle. The commit is not wrong about the live tree — the version string did need replacing — but it is unauditable in the way that matters: a reader cannot tell which of the 97 files are the rewrite and which are the sweep, and one of them is a historical record that should have been excluded. What we learned. The 6 November rule (git commit --only <paths>) was written down and then not applied twelve days later. A rule in a failures file is not a control. The control is the flag in the command, and the only way a rule survives is if the command that violates it is the one that feels slower. The same is true of the 8 November rule about not rewriting dated records: it was written down, and then a sweep ran without a path exclusion.

2.4 What the three events say together

Three version events in twenty days, and the sequence 3.1.0 → 3.1.2 → 4.0.0 is monotonic. The project's version discipline, judged only by the numbers, improved across the window: the frontier had a working tree one patch level behind its newest tag, and the publication point has a working tree that agrees with a version higher than every tag before it.

Judged by the mechanism, nothing improved. There is still no check that the release tags form a monotonic sequence in VERSION — the question part two §12 left open, and the answer is still no. And the 18 November commit shows what happens without one: the version string is corrected by a repository-wide find-and-replace, which is the correct tool for the job and also the tool that cannot tell a live document from a historical record.

VERSION changed exactly twice in the window:

$ git log --format='%h|%aI|%s' 2ea44922..HEAD -- VERSION
7fb3fc32|2026-11-16T06:37:20+00:00|chore(release): bump site to 4.0.0 and apply blocker fixes
48c241a1|2026-11-01T10:33:30-07:00|chore(release): cut 3.1.2 and land the owner directive

Two commits, two values, and a third event — the 18 November sweep — that changed no VERSION file because VERSION was already 4.0.0. The sweep's job was to make the rest of the repository agree with a file that was already correct. That is the shape of the problem: the authoritative value was right, and 97 files disagreed with it, and the tool used to reconcile them could not read dates.
