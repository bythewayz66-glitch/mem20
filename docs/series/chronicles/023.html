The branch count that fell from fifteen to two

2026-11-21 grounded 762 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

At the frontier there were fifteen remote heads and the directive was complaining about thirteen stale refs. At publication there are two. The fall is real, and it is not the story the numbers suggest.

5.1 What the directive asked for

G2 asked GitHub Repo Assistant to delete thirteen merged refs, with this acceptance criterion:

Acceptance: branch SHA with Tests = success in check-runs; git ls-remote --heads shows only main; compare/<newtag>...main → ahead_by 0.

The score records that this did not happen:

Not met: the 13 merged refs were not deleted — the remote still carries 21 heads. G2 remains open.

So the count went up on 1 November, from 15 to 21, because six new branches were pushed and none were deleted. The score says so in its "what changed" section:

- Remote heads: 15 → 21 (6 new branches; none deleted).

5.2 What happened between then and now

By 16 November the count is 103:

Snapshot: 10/13 checks green (76.9%); 103 remote heads; 12 ahead; 0 open PRs; 1 open issue; 132 tags; 11,439 tracked files; 1,158 commits on main.

One hundred and three heads, of which twelve are ahead of main and none has an open PR. The program status names this as blocker B2 and quantifies it:

B2 | 50 at-risk commits on 12 branches, unmerged, no PR open for any of them — they will rot. Triage order in §3.

Fifty commits, twelve branches, zero PRs. And one of those branches is this serial's own: docs/ws1-narrative-serial-2026-11-01 at 2d2e6212, two commits ahead. The roster score credited the narrative work at feba039c, which is on main; the branch is a leftover.

5.3 The fall

Between 16 November and 21 November the count goes from 103 to 2. That is a hundred and one refs removed in five days, and the repository does not record a single commit that says "delete the branches." The refs were pruned, and the pruning is not in the history because branch deletion is not a commit.

What is in the history is the consequence: the fifty at-risk commits are gone from the remote. The gtm/claim-ledger-v7-rebase branch with fourteen commits, the fix/post20-defects branch with nine, the three SDK branches — none of them is in git ls-remote --heads origin today.

Whether those commits were merged first or discarded is not something this post can determine from the repository. What it can determine is that the program status predicted the outcome exactly: "they will rot." Twelve branches with no PR, fifty commits, and a five-day window in which the refs disappeared. The prediction was correct and the triage order it recommended was not executed, because the triage order was a recommendation and the pruning was an operation.

What broke. Fifty commits on twelve branches, with no PR open for any of them, were removed from the remote within five days of being catalogued as at-risk. The program status predicted this in writing and prescribed a triage order; the triage order was not followed. What we learned. A branch with no PR is not work in progress; it is work in a queue that nobody is serving. The directive's G2 asked for thirteen merged refs to be deleted, which was safe because they carried zero unmerged commits. The 16 November state was the opposite: twelve refs carrying fifty unmerged commits and no PR. The distinction between "safe to delete" and "at risk" is entirely in whether the commits are ancestors of main, and the program had the command for that (git merge-base --is-ancestor) and used it correctly on 1 November. The lesson is that the check has to run at deletion time, not at audit time. An audit that says "these twelve are at risk" is only useful if the deletion is gated on the same check.
