The conformance sweep: seventy-nine issues in two days

2026-11-21 grounded 1485 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

The largest single body of work in the window is a conformance sweep that ran on 6, 7 and 8 November and closed seventy-nine issues. It is the reason the commit count for those three days is what it is, and it is the clearest example in the window of a program executing a written plan at scale.

6.1 The seven criteria

The sweep is organised around a seven-criterion conformance standard, defined in docs/renovation/4.0/RENOVATION_PLAN.md. The plan's exit gate is unambiguous:

1. conformance.py --all --fail-under 1.0 exits 0 — all 211 subsystems at 7/7.

Two hundred and eleven subsystems, seven criteria each. The plan's baseline table records where the program started:

| Subsystems fully conformant (7/7) | 6 |

Six of 211 at the start. The plan also names the cheapest win and the reason it should be batched:

Criterion 5 (README examples) at 30.8% is the cheapest win and should be batched with criterion 6,

And it explains why the substrate had to land first:

Why first: these are the modules every other subsystem must import to satisfy criterion 6. If [they are not first], criterion 6 work in waves 2–3 would be built [on sand].

6.2 What criterion 6 actually requires

Criterion 6 is the one that caused the most trouble, and the failures corpus records why. From the 6 November entry:

2026-11-06: Conformance criterion 6 still failed after adding genuine cross-module calls because the calls sat inside a multi-line dict literal and coverage only marked the assignment line. NEXT ACTION: done — every mem20 call in estate_context() is now its own statement; the gate logs list each call site and report 7/7.

And from 8 November, more precisely:

Criterion 6 is strict (import AND call on covered line via AST+coverage); guessed peer APIs caused missing covered calls

So criterion 6 is not "does this module import a peer." It is "does this module import a peer and call it on a line that coverage marks as executed," verified by AST analysis plus a coverage run. That is a much harder standard, and it explains the volume of work: every subsystem needed six real peer integrations, each one a genuine call on a covered line, and each one against a peer API that had to be discovered rather than assumed.

The failures corpus is full of the API mismatches this produced, and they are the most concrete evidence in the whole window of what "real integration" costs. A sample, all from 7 November:

- mem20simz.simulate_load returns a list (scaling/bottleneck take the list); mem20syntheticevaluatorarenaz.create_arena/evaluate use hashable agent/subject IDs (strings), not dicts. - mem20gameproductioncontrolcenterz.milestone_status takes numeric due_day/today and production_health expects done/velocity fields; mem20studioz.resource_allocation takes {resource:capacity} dict and demand amount; mem20simz.funnel takes stage dicts with conversion, growth_score takes viral_k/conversion/retention. - counterfactualmemorysimulatorz.replay takes (memory, steps_list) not (memory,int). - mem20universalintegrationcompilerz.validate_mapping/transform need field-mapping shape (not wrapper dict); mem20ambientteamradioz.send_message returns {ok,message} and mutates channel messages, so adapter must append message to channel before channel_activity. - mem20intenttomissioncompilerz.compile_mission expects intent dict (goal/parts), not plain string. - collectivemodelintelligencez.ensemble_predict takes numeric predictions (not dicts); alternativedatabaseplaygroundz.suggest_index takes (columns, cardinalities_list) and benchmark needs plan dict; crdtcollaborationenginez GCounter/PNCounter value may be property/callable; prioritycollisionresolverz.submit(item, priority) takes 2 args.

Every one of those is a signature that was guessed wrong and then discovered by running the code. That is the honest cost of criterion 6, and it is worth recording that the standard was not relaxed to make the sweep go faster. The failures corpus says so explicitly:

Criterion 6 is strict (import AND call on covered line via AST+coverage); guessed peer APIs caused missing covered calls — fixed 336 (BatteryAwareAgentScheduler, energy_cost/greenest_node/ migration_plan), 337 (offerassemblyfabricz/compoundingproductecosystemz/businessmodelsimulatorz/ capabilitymarketplacez real APIs), 338 (modalitybridgez.analyze_bridge path restored, personalworkflowtwinz create_twin/observe/twin_health), 339 (restored leveldesign compile_level_plan import, dynamicnarrativeenginez create_story/add_node/current_text, replaced missing universaltranslatorcoprocessorz with loreragcontentgeneratorz, fixed word_count(text)→ word_count(parsed)).

6.3 The user intervention

On 7 November, partway through the sweep, the owner intervened, and the failures corpus records it verbatim:

2026-11-07: User feedback: "stop using shared patterns, use real meaningful implementations." Applied from #317 onward: peer integrations composed into domain outcomes (e.g. #317 computes production-control report where team presence affects effective capacity, resilience adjusts risk, economics/release/forge/assets contribute real sections) rather than only collecting probe signals. Cross-module calls remain real and covered for criterion 6.

This is the most important sentence in the window, and it is worth reading slowly. The sweep had been satisfying criterion 6 by collecting probe signals — calling six peers and gathering their health outputs into a signals dict. That passes the AST-plus-coverage check, because the calls are real and on covered lines. It does not produce a subsystem that does anything with its peers.

The owner's correction changed the standard from "call six peers" to "compose six peers into the domain outcome." The example given is concrete: #317 computes a production-control report where team presence affects effective capacity, resilience adjusts risk, and economics/release/forge/assets contribute real sections. That is a different kind of code. It is also much more work per subsystem, which is why the sweep's pace changes after 7 November.

What broke. For the first part of the sweep, criterion 6 was satisfied by collecting peer health signals into a dict — technically real calls, technically covered, and functionally decorative. The gate passed and the subsystems did not compose. What we learned. A conformance criterion that can be satisfied without producing the behaviour it is named for is a criterion that will be satisfied that way. The gate was not wrong — it checked exactly what it said it checked — but what it said it checked was "import and call," and "import and call" is not "integrate." The owner's correction is the general form of the lesson: when a gate is passing and the product is not improving, the gate is measuring the wrong thing, and the fix is to change the gate, not to add more passing instances. The sweep's later entries show the change taking effect — #317 through #329 are all described as "meaningful" rebuilds rather than conformance fixes, and the commit subjects change from fix(conformance) to fix:.

6.4 The regression inside the sweep

The sweep also produced a regression, and the failures corpus records it with unusual precision:

Regression detected/fixed: 332 and 334 domain/test extensions (appended earlier) were missing from disk later; restored analyze_bridge/pipeline (compile_level_plan etc.) and added tests, re-verified 7/7.

Two subsystems had their work appended, then lost, then restored. The corpus does not say why the files went missing, and this post will not guess. What it does say is that the loss was detected by re-running the conformance check rather than by reading the diff, which is the only way it could have been detected: a file that is missing from disk leaves no trace in a commit that did not touch it.

What broke. Work that had been appended to two subsystems was later absent from disk, and the absence was found by re-running the gate rather than by any review of the change. What we learned. In a shared working tree with concurrent agents, "I wrote it" and "it is there" are different claims. The only check that distinguishes them is a re-read, and the only cheap re-read is the gate. This is the same lesson as the 6 November shared-tree race, arriving from the opposite direction: there, work was swept into a commit it did not belong to; here, work was swept out of the tree entirely. Both are consequences of many agents writing to one directory, and both are only visible to a check that reads the result rather than the intent.

6.5 The scale

The sweep's output is best read as a range. The closes # references in the window run from #267 to #391, and there are 79 of them:

$ git log --format='%s' 2ea44922..HEAD | grep -c 'closes #'
79

Seventy-nine issues closed by commit subject in twenty days, the overwhelming majority in the 6–8 November window. The commit subjects for 6 November alone run to more than thirty lines of fix(conformance): <subsystem> 7/7 (closes #NNN), and 7 November adds the "full depth spec" variants for the same subsystems.

That is a program executing a written plan at a pace that is only possible because the plan was written first. The renovation plan named the criteria, named the substrate that had to land first, named the cheapest win, and set an exit gate. The sweep then executed it. Whatever else is true about the window, that part worked.
