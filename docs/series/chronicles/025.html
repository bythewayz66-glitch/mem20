The consolidation: 177 members into 56 runtimes

2026-11-21 grounded 1170 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

On 9 and 14 November the estate was reorganised twice, and the second reorganisation is the largest structural change in the window.

7.1 The first pass: nine consolidations in one day

The 9 November diary entries record nine consolidations, each one merging a family of long-named subsystems into a short-named runtime:

- consolidate training/cert/apprenticeship into mem20schoolz — Created mem20schoolz (unified training + certification + apprenticeship) ... removed originals mem20apprenticeshipruntimez, mem20trainingz, mem20certificationz. - consolidate all pipe subsystems into mem20pipez — Created mem20pipez as unified pipeline subsystem with all pipe runtimes copied as modules under mem20pipez/pipes/. Removed all pipe-named originals (mem202dand3dartproductionoptimizationpipelinez, mem20aipipelinecostoptimizerz, mem20assetintakecatalogingandvalidationpipelinez, ... fourteen in total). - consolidate simulation subsystems into mem20simz — Merged simulator/simulation-related subsystems into mem20simz as modules under mem20simz/sims/ (twelve members). - consolidate twin subsystems into mem20twinz — seven members under mem20twinz/twins/. - consolidate studio subsystems into mem20studioz — five members under mem20studioz/studios/. - consolidate brain subsystems into mem20causalroutingbrainz — four members under mem20causalroutingbrainz/brains/. - consolidate lab subsystems into mem20labz — seven members under mem20labz/labs/. - consolidate forge subsystems into mem20rewardforgez — four members under mem20rewardforgez/forges/.

Nine families, dozens of packages, one day. And this is the commit that rewrote part two's verifier (§1.2), because the pipe consolidation removed mem20pipelinez and mem20executablegameconceptandscopepipelinez from the tree, and the sweep that updated references did not exclude docs/app/narrative/.

7.2 The second pass: 177 members

The 14 November entry is the larger one, and it states the rule that drove it:

Rehoming complete (extended): All long mem20z subsystems (name length > 15) absorbed into short runtimes (len < 15) with full trees copied into <target>/absorbed/<member>/, member READMEs appended to target READMEs, tests copied to <target>/tests/absorbed/<member>/ (and pkg_tests where applicable), originals deleted. 177 members rehomed across rounds (87+42+45+3) + 1 stale pycache-only remnant removed (mem20versioncontrollargeassetandrecoverypipelinez, source already in mem20pipez/pipes/...). 0 long standalone mem20z dirs remain (short runtimes 56, mem20benchmarkz len==15 unchanged). No symlink compatibility shims.

The rule is a name-length rule: any subsystem whose directory name is longer than fifteen characters is absorbed into a runtime whose name is shorter. 177 members, in four rounds of 87, 42, 45 and 3.

That is an extraordinary criterion for a refactor, and it is worth being clear about what it is and is not. It is not an architectural principle — there is no reason a fifteen-character boundary corresponds to a module boundary. It is a mechanical rule, chosen because it can be applied without judgement, and its virtue is that it is checkable: after the pass, 0 long standalone directories remain, and that is a fact you can verify with ls.

The cost is recorded honestly in the same entry:

Import compatibility: Added mem20_absorbed.py, _mem20_absorbed_finder.py, .mem20-absorbed-map.json, and venv .pth (.venv/lib/python3.13/site-packages/_mem20_absorbed.pth) to resolve mem20<member>z imports to canonical absorbed locations (177 mapped; 39 multi-target).

So the refactor required a custom import finder, a JSON map of 177 entries with 39 members mapping to more than one target, and a .pth file in the virtualenv. That is the price of moving 177 packages without breaking every import in the estate, and it is a price the entry does not hide.

7.3 What the finder broke, and how

The failures corpus records the consequences, and they are exactly what a custom import finder predicts:

Broken imports after symlink removal (resolved): Removing top-level symlinks for absorbed members left old mem20<member>z import paths unresolved. Fixed by adding _mem20_absorbed_finder.py + .mem20-absorbed-map.json and venv .pth for canonical resolution; bootstrapped in MCP/gateway.

And then, on 21 November — the last day of the window — the finder itself is found to be broken in a clean checkout:

_mem20_absorbed_finder.py: resolve the absorbed map relative to the checkout instead of the hard-coded /opt/mem20, and rebase recorded absolute paths onto this root. Without it every absorbed member failed to import and the ecosystem probe reported 0 peers.

That is the single most instructive failure in the window, and it deserves its own treatment.

What broke. The import finder that made the 177-member consolidation possible resolved its map against a hard-coded absolute path, /opt/mem20. On the machine where the consolidation was performed, that path existed and everything worked. In a clean checkout anywhere else, every absorbed member failed to import and the ecosystem probe reported 0 peers — a number that looks like a measurement and is actually an absence. What we learned. A refactor that requires a custom resolver has moved the failure mode from "the import is wrong" to "the resolver is wrong," and the second is much harder to see because it fails silently and plausibly. 0 peers is not an error; it is a valid probe result. The only thing that distinguishes "this subsystem has no peers" from "this subsystem's peers could not be imported" is knowing that it should have peers — which is exactly the knowledge a clean checkout does not have. A resolver must be rooted in the thing it is resolving, not in the machine it was written on. The fix is one line of path arithmetic; the cost of not having it was a probe that reported a confident zero for an unknown number of days.

7.4 The absorbed-ecosystem exception bug

There is a second consequence, and it is a textbook Python defect:

Absorbed ecosystem probe crashes (resolved): Many absorbed ecosystem.py files caught CircuitOpen in a separate except block but could leave CircuitOpen unbound if mem20faultcontainmentcellsz import failed (e.g. due to missing toolchest.catalog in some envs), causing UnboundLocalError. Fixed in 57 files to handle by exception class name in the generic handler.

Fifty-seven files. The pattern is:

try:
    from mem20faultcontainmentcellsz import CircuitOpen
except ImportError:
    pass

try:
    ...
except CircuitOpen:      # UnboundLocalError if the import above failed
    ...

If the import fails, the name CircuitOpen is never bound, and the except CircuitOpen clause raises UnboundLocalError at the moment it is supposed to handle an error. The handler becomes a second failure. Fifty-seven copies of the same pattern, because the pattern was copied.

What broke. Fifty-seven absorbed ecosystem files caught an exception class that might not have been imported, so the error handler raised UnboundLocalError instead of handling the error. What we learned. An except clause naming a symbol that may be unbound is a handler that can fail, and a handler that can fail is worse than no handler because it converts a handled condition into an unhandled one at the worst possible moment. The fix — match on the exception class name in the generic handler — is uglier and correct. The general rule: when a module is copied 57 times, every defect in it is copied 57 times, and the copy is the reason the defect is invisible. One file with this pattern is a code smell; fifty-seven is a pattern, and a pattern is what a linter should catch and a reviewer will not.
