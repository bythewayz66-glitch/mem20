The engine that was deleted with a gitlink

2026-11-21 grounded 1279 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

Issue #229 is the longest-running defect in the window, and its resolution on 16 November is the cleanest piece of engineering in the twenty days.

8.1 The defect

The failures corpus states it:

Issue: #229 "mem20kilnz: 200 test failures because the C++ engine source was deleted with the gitlink" — the engine source was tracked as a gitlink (submodule pointer) to JaysonAIOnline/mem20kilnz-engine but the submodule was never initialized, leaving mem20kilnz/engine/ empty. The gitlink was removed in commit 71939ee0 to unblock Pages builds.

The introducing commit is 71939ee0, dated 2026-10-18T14:47:43-06:00, subject "Remove dangling gitlink submodules blocking Pages checkout." That commit is correct in its own terms: a dangling gitlink does block a Pages checkout, and removing it unblocks the build. What it also does is remove the only pointer to the engine source, leaving mem20kilnz/engine/ empty and every test that needs the engine failing at fixture setup.

The program status names the consequence as blocker B1 and refuses to paper over it:

B1 | main not release-clean: 3 of 13 checks red on 0224a649 (Tests, MCP handshake (shallow clone), artifact evidence). Root cause is issue #229: mem20kilnz/engine/ dropped with a gitlink in 71939ee0, so ~200 tests fail loudly by design. Restore the engine source or retire the package — do not paper over it with a skip. Not an agent call.

"Do not paper over it with a skip" is the sentence that makes this entry worth recording. The cheapest way to make 200 tests stop failing is to skip them, and the program status forbids it in advance.

8.2 The fix

The fix is three commits on 16 November, and the failures corpus records the whole procedure. The engine repository was cloned into the engine directory of the kiln package, so the source sits inside the checkout rather than behind a pointer. The engine needs the Assimp development headers for FBX import, which were installed from the distribution's package manager; the package manager reported a non-fatal error on a dbus post-install script because of container permissions, and the headers installed successfully regardless. The build then ran clean with the project's makefile — 0 warnings, 0 errors — and produced the kiln binary in the engine directory.

The verification is the part that matters: the full test suite passes, 279 passed, 7 skipped in 35.93s. The seven skipped are named as expected rather than left as an unexplained number — they require a GUI, Vulkan, or specific fixtures.

Two hundred and seventy-nine passed, seven skipped, and the seven are named as expected rather than left as an unexplained number. The commits are 58e8b78f ("Fix mem20kilnz engine build (issue #229)"), 76ea8ca1 and 7196a10b ("Add mem20kilnz engine source (from JaysonAIOnline/mem20kilnz-engine)"), all dated 2026-11-16 between 04:33 and 04:35 UTC.

Note what the fix is: the engine source is now in the repository, not referenced by a gitlink. The defect was that a pointer to an external repository was treated as if it were the content, and the fix is to stop doing that. That is the same class of error as the import finder in §7.3 — a reference that resolves on one machine and not another — and it is worth noticing that the window contains two independent instances of it.

What broke. A commit that correctly removed a dangling gitlink also removed the only reference to the C++ engine source, leaving 200 tests failing at fixture setup for twenty-nine days. The failure was loud and correct: the tests were telling the truth about a missing dependency. What we learned. The program status's instruction — "Restore the engine source or retire the package — do not paper over it with a skip" — is the whole lesson, and it is worth recording that the instruction was written before the fix and followed by the fix. Two hundred failing tests are not a problem to be silenced; they are a measurement of a missing dependency, and the measurement is the useful part. A skip converts a true failure into a false pass, and the false pass is permanent while the true failure was temporary.

8.3 The engine's own failures corpus

mem20kilnz/failures.md is 45,085 bytes and is the richest single document in the repository. It is also, for most of the window, the only part of the failures corpus that is being written to. Its entries are the register this chronicle is trying to hold, and three of them are worth carrying into this post because they are the best statements of the project's engineering values that exist.

The first is the count that was wrong:

2026-09-25 — Proposal claimed 263 AI-native features; real count was 212 - Actual error: the per-family subtotals in the same paragraph summed to 212. The 263 was not derived from anything; it was wrong. - Cause: hand-summed headline figure never reconciled against the item list. The subtotals were correct, which is exactly why it survived a read-through. - Rule learned: never publish a hand-summed count. Publish the grep.

"The subtotals were correct, which is exactly why it survived a read-through" is the most useful sentence in the corpus. A document whose parts are right and whose total is wrong is a document that rewards careful reading with a false confirmation.

The second is the decimator that refused:

2026-09-27 — QEM, second attempt: refused rather than shipped broken - Decision: decimate defaults to cluster, the only method measured to preserve the surface (watertight, 0 degenerate, 0 non-manifold). method: "qem" refuses with that reason rather than returning a larger mesh. A decimator that hits its triangle count while destroying the shape is worse than a simpler one that preserves it, and one that returns 278% of the input is not a decimator at all.

A decimator that returns 278% of its input is a function that has failed and reported success. The refusal is the correct behaviour, and it is recorded as a decision rather than a bug.

The third is the exporter that was one off:

2026-09-25 — OBJ exporter wrote every face index one too high - Actual error: my own importer rejected kiln's export with "face references vertex 275 but only 274 vertices exist". Blender accepted the file anyway. - Cause: int base = 1; combined with writing base + v + 1, so the first mesh's indices started at 2 instead of 1. - Why it survived: nothing round-tripped OBJ through kiln before, and Blender is lenient about a trailing out-of-range index.

"Blender accepted the file anyway" is the reason the defect survived, and it is the general shape of every lenient-parser bug: the tool that should have caught it was more forgiving than the tool that produced it.

What broke. Three separate defects in the engine's own history, each of which produced output that looked correct: a hand-summed total that contradicted its own subtotals, a decimator that destroyed the shape while hitting its count, and an exporter that wrote indices one too high and was accepted by the only external tool that read it. What we learned. The corpus's own rule — "never publish a hand-summed count. Publish the grep" — is the same rule this post applies to the tool count in §3, and it is the same rule the publication note violated in §1. The corpus has been saying it since September. The window contains at least three fresh violations of it, which is the honest measure of how much a written rule is worth without a gate behind it.
