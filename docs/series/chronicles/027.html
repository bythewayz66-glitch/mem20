The keyless rewire, and the dreamer that starved the box

2026-11-21 grounded 786 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

On 11 and 12 November the estate was rewired to run without API keys, and the failures corpus records the operational consequences with a candour that is unusual even for this repository.

9.1 The rewire

Commit 0c785ac3, dated 2026-11-12T01:35:56Z, subject "feat(llm): rewire estate to keyless providers (pollinations + local ollama)." The diary records the verification: a root-level chat call returned a pollinations gpt-oss-20b reply with no key and no environment variable set, and an offline vision call returned a local moondream description with no model argument and no key.

And the smoke tests across the estate:

- gamez live: a role chat returned GAMEZ-SMOKE-OK (6.3s); an orchestrator chat returned ORCH-SMOKE-OK (56.8s); a vision chat returned a description (646.7s). A NIM model with no key raised RuntimeError — honest. - crewz live: CogBrain().propose(...) → {'action':'final','final':'CREWZ-SMOKE-OK'} (5.8s). - rpgz live: asyncio chat_completion(...) → 'RPGZ-SMOKE-OK\n' (8.5s, after freeing CPU).

Note the parenthetical on the last line: "after freeing CPU." That is the whole of §9.2.

9.2 The dreamer

The failures corpus records the incident in full, and it is the best operational entry in the window:

- rpgz live smoke FAILED twice (TimeoutError 61.1s, 60.5s) — NOT a code defect. Root cause: my own mem20dreamz idle loop (PID 233583) was running the keyless panel nonstop: 4 concurrent 180s-timeout calls to local Ollama, both llama-server runners ~85% CPU, load average 12.6, 3-min/500 timeouts in the ollama journal. Fix: stopped the dreamer service, let the queue drain, retried → RPGZ-SMOKE-OK in 8.5s. Lesson: on this CPU-only box the idle dream loop starves every other LLM consumer; stop it before latency-sensitive verification, and report saturation instead of blaming the client.

Read the sequence. A smoke test failed twice with a 61-second timeout. The obvious diagnosis is that the client is broken. The actual cause is that the operator's own background process — an idle "dream" loop, running the keyless panel continuously — was saturating the CPU with four concurrent 180-second calls to a local model server, driving load average to 12.6. Stopping it made the same test pass in 8.5 seconds.

The lesson the corpus draws is exactly right and worth quoting again: "report saturation instead of blaming the client."

There is a second entry from the same session that is a smaller version of the same thing:

- Stopping the dreamer service hit State 'stop-sigterm' timed out. Killing. — the process was mid-generation and did not handle SIGTERM until inference returned. Operational note: dreamer restarts can take the full stop timeout (SIGKILL). Not a code change this session; recorded so the next agent does not mistake it for a crash.

And a third, which is the purest example of a self-inflicted false failure in the whole corpus:

- The time binary does not exist on this box — earlier benchmark attempts produced a self-inflicted false failure; the operator used shell timestamp arithmetic instead.
What broke. A latency-sensitive smoke test failed twice, and the cause was the operator's own background process saturating the CPU. The failure looked exactly like a client defect, and the first two diagnoses were wrong. What we learned. "Report saturation instead of blaming the client" is the rule, and it is a rule about the order of investigation rather than about the code. Before diagnosing a timeout, look at what else is running. The corpus's own framing is the useful part: the entry does not say "the test was flaky" or "the client was slow." It says the test failed, the cause was saturation, the fix was to stop the saturating process, and the retry passed in 8.5 seconds. A failure that is caused by the environment is still a failure, and recording it as an environment problem is not the same as recording it as a non-event. The distinction matters because the next agent will hit the same saturation and needs to know it is saturation.

9.3 The stale documentation

The same session produced a documentation correction that is a small masterpiece of the genre:

- docs/03-installation.md still claimed a provider API key was required — stale after the rewire; corrected to keyless-default with optional key.

One line, and it is the whole of §3 in miniature: a document that was true before a change, was not updated by the change, and was found by someone reading it. The rewire made the key optional; the installation guide still said it was required. Nothing failed. No test caught it. A person read the document and noticed.
