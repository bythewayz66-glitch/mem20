The CI that would not stay green

2026-11-21 grounded 1298 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

The last five days of the window are a sustained fight with continuous integration, and the fight ends with a commit that claims a victory it did not achieve.

11.1 The 16 November churn

The commit subjects for 16 November are dominated by two lines repeated many times:

6dfc0e29|fix(ci): map green-set pipe packages to actual tests paths
e77de922|fix(mcp): disable health server during handshake/surface verification
cf0b58b0|fix(ci): map green-set pipe packages to actual tests paths
c7b31a30|fix(mcp): disable health server during handshake/surface verification
e8f43126|fix(ci): map green-set pipe packages to actual tests paths
43b09080|fix(mcp): disable health server during handshake/surface verification
52d6e6e5|fix(ci): map green-set pipe packages to actual tests paths
976fe419|fix(mcp): disable health server during handshake/surface verification

Eight commits, two subjects, alternating. And then:

e9cd5eca|fix(mcp): align AST wiring/catalog with live handshake and sync doc versions
91ff7eb9|fix(mcp): align AST wiring/catalog with live handshake and sync doc versions
ee1ecc31|fix(mcp): align AST wiring/catalog with live handshake and sync doc versions
f02fbf5f|fix(mcp): align AST wiring/catalog with live handshake and sync doc versions
d787f1ce|fix(mcp): align AST wiring/catalog with live handshake and sync doc versions
814bd486|fix(mcp): align AST wiring/catalog with live handshake and sync doc versions
df5d1aa5|fix(mcp): align AST wiring/catalog with live handshake and sync doc versions
3f8da756|fix(mcp): align AST wiring/catalog with live handshake and sync doc versions
5b6986d4|fix(mcp): align AST wiring/catalog with live handshake and sync doc versions

Nine commits with the identical subject. That is not nine fixes; it is one fix applied nine times, which means eight of them did not take. The most likely mechanism is a rebase or a re-apply loop against a moving main, and the repository does not record which. What it records is that the same change was committed nine times in one day, and that the commit message was never updated to say what was different about the ninth.

What broke. Nine commits with the identical subject line landed on 16 November, and eight commits alternating between two subjects. A reader of the log cannot tell what changed between the first and the ninth, because the message is the same. What we learned. A commit message that is identical to eight others is a message that has stopped carrying information. The failures corpus has a rule for the adjacent problem — "read the diff after deleting debug code" — and this is its sibling: when you re-apply a fix, say what was different about the attempt. "align AST wiring/catalog with live handshake and sync doc versions" is a description of the goal, not of the change, and a goal repeated nine times is a log that has been written for the author rather than for the reader.

11.2 The 21 November claim

The window's last substantive commit is 7ba10cf4, dated 2026-11-21T09:07:45-07:00, subject:

fix CI: make all four red checks green on main

The body is specific and confident:

- ci.yml: add toolchest/src and mem20core to the green-set PYTHONPATH (a clean checkout failed with ModuleNotFoundError on import); treat pytest exit 5 in the unit-marked step as the expected empty selection instead of a failure (the 22-package set carries no unit-marked tests). - _mem20_absorbed_finder.py: resolve the absorbed map relative to the checkout instead of the hard-coded /opt/mem20, and rebase recorded absolute paths onto this root. Without it every absorbed member failed to import and the ecosystem probe reported 0 peers. - mem20assistz/domain.py, mem20graphz/ecosystem.py: install the absorbed import finder before importing absorbed members. - sdk/cpp/tests/consumer/main.cpp: assert the current 487 tools / 129 domains surface instead of the retired 311/39. - mem20agentz/web, mem20controlz/.../web: regenerate package-lock.json so npm ci resolves (vitest/loupe drift).

Five changes, each one a real defect, each one described precisely. This is a good commit message.

The subject is false.

11.3 What the check-runs say

The parent of 7ba10cf4 is 987c9782 ("comics: THE Z CORPS #10 — The Four-Channel Claim (38pp)"), and its check-runs are:

--- 987c9782 ---
total 14 Counter({'success': 9, 'failure': 5})
RED: ['C++ surface guard', 'artifact evidence', 'controlz desktop wiring',
      'mem20agentz OREO integration', 'Tests']

Five red, not four. The subject says "all four red checks," and the parent had five.

And 7ba10cf4 itself:

--- 7ba10cf4 ---
total 14 Counter({'success': 11, 'failure': 3})
RED: ['mem20agentz OREO integration', 'controlz desktop wiring', 'artifact evidence']

Three red. The commit took five red checks to three, which is a real improvement and a real piece of work. It did not make them green.

The next commit, 105b9602 ("fix CI: regenerate the two web lockfiles so npm ci resolves"), takes it to one:

=== TODAY CHECK RUNS on HEAD (105b9602) ===
total 16 Counter({'success': 15, 'failure': 1})
failure | artifact evidence

Fifteen of sixteen green, one red. The one red is artifact evidence, and its check-run carries no output summary:

artifact evidence 136903384930 None |

So the window ends with a repository that is one check away from release-clean, and a commit in the middle of the last day that claimed to have finished the job three checks early.

What broke. Commit 7ba10cf4 is titled "make all four red checks green on main." Its parent had five red checks; the commit left three. The subject overstates the result by three checks, and the overstatement is in the one field a reader is most likely to trust without checking. What we learned. This is the same defect as the publication note in §1, in a different medium. There, a find-and-replace made a dated record state a false version. Here, a commit subject states a result the commit did not achieve. Both are claims that a reader would take at face value, and both are wrong in the direction of looking better. The project's own standard — "A partial pass is not a clean pass" — is exactly the standard this subject violates: five red to three red is a partial pass, and calling it "all green" is the failure the standard exists to prevent. The subject line is a claim, and a claim about a check must be written after the check has run, not before. The body of 7ba10cf4 is exemplary; the subject is the only part of it that is wrong, and it is the part that will be read.

11.4 The artifact-evidence check

The one remaining red check is worth a paragraph, because it is the check that has been red the longest. It appears in the 16 November program status as one of three reds:

| artifact evidence | 8 | 43820093456 |

Eight annotations. And it appears in the 1 November scoreboard's list of passing checks, which means it was green then and is red now. The failures corpus records the rule it enforces, from 2 November:

85cee574|fix(ci): exempt convergence merges and gate-own changes from artifact-evidence

So the check requires every PR to carry a 40-character SHA or a 200-verified URL, and it has been patched at least once to exempt convergence merges. It is red at the end of the window with eight annotations and no summary, which means the check is failing and the check-run does not say why in a form the API exposes.

This post cannot determine the cause. What it can say is that the check that enforces the program's central evidence rule is itself failing, and that the failure is not diagnosable from the check-run output. That is a real limit, and §13 records it as one.
