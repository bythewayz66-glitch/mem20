The file that took fourteen commits to land

2026-11-21 grounded 1639 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

At 11:35:15 -0700 on 21 November, commit b5107c53 landed:

docs(narrative): serial 2026-11-21 — the archive that was rewritten (part 1/5)

That is the previous instalment, committed as the first of five parts. It was 4,903 words at that point — a fraction of the 16,266 it would eventually be.

The reason it was committed in parts is stated in the commit that added the assembler, 35247d5c:

ci(narrative): one-shot assembler for the 2026-11-21 instalment

The publishing API caps a single file write at ~30 KB, so the instalment is
committed in parts and concatenated here. No-op once .parts/ is empty.

Thirty kilobytes. The instalment is 101,467 bytes. It could not be written in one call, so it had to be written in pieces and joined. That is a constraint of the tooling, not a decision of the author, and it is the origin of everything that follows.

What follows is fourteen commits, all with the subject "assemble serial 2026-11-21 from parts" or a variant, and ten commits that modify the assembler itself. Read in order, they are a complete record of a small piece of software being debugged in production, one failure at a time, with each failure described in the commit message that fixes it.

2.1 The first assembler, and why it was order-unsafe

35247d5c added 51 lines to .github/workflows/assemble-serial.yml. It concatenated everything in docs/app/narrative/.parts/ in filename order and wrote the result to the target.

The first defect was found immediately. 1ce1a4af:

ci(narrative): make the assembler order-safe

Only concatenate once p1, p2 and p3 are all present, so the parts can be
committed one at a time without a partial run corrupting the target.

The cause is stated exactly: the parts were being committed one at a time, and the workflow ran on every push, so it concatenated whatever happened to be present. A run that fired after part 1 but before part 2 would write a one-part file over the target. The fix was a guard — wait until all three named parts exist.

That guard was the wrong shape, and the next commit says so. b305854b:

ci(narrative): assemble from numbered parts on a DONE sentinel

Some larger single writes are rejected by the publishing API, so the
instalment is committed in small numbered parts and concatenated in
filename order once .parts/DONE exists.

The guard moved from "three named files exist" to "a sentinel file exists". This is a better design: the sentinel is committed last, by the author, when the author knows the parts are complete. It removes the workflow's need to guess.

But the trigger was still push on the parts directory, and that is what broke next.

2.2 The run that deleted its own input

74ebe539:

ci(narrative): assembler runs on manual dispatch only

The push trigger fired on every part commit and deleted .parts2/ after the first
one, so the target was assembled from a partial set. Dispatch-only means the
parts are all in place before assembly runs.

This is the failure that matters most, because it is a class of failure rather than an instance. The workflow's job ended with rm -rf "$PARTS" — it cleaned up after itself, which is normally correct hygiene. But because the trigger was a push to the directory it was cleaning, the first part commit fired the workflow, the workflow assembled a one-part file and deleted the directory, and every subsequent part commit landed in a directory that no longer existed.

The workflow destroyed its own input on the first run. The commit message says so plainly: "the push trigger fired on every part commit and deleted .parts2/ after the first one, so the target was assembled from a partial set."

The fix was to remove the automatic trigger entirely and require a manual dispatch. That is a retreat from automation, and it is the right one: a workflow that cannot tell "the parts are ready" from "a part has arrived" should not run automatically.

2.3 The 125,740-byte polluted file

3bd8f7fa:

ci(narrative): assembler replaces target from .parts2, never appends

The first run appended the existing target and picked up leftover failed-attempt
files, producing a polluted 125,740-byte file. This version starts from empty
and reads only .parts2/.

One hundred and twenty-five thousand, seven hundred and forty bytes. The correct file is 101,467. The polluted file was 24,273 bytes larger than it should have been, and the cause is two mistakes compounding: the assembler appended to the existing target instead of replacing it, and the parts directory still contained files from earlier failed attempts.

This is the first place in the window where a number can be checked against another number and the error is visible without reading any code. 125,740 against 101,467 is a 24% overshoot. A reader who noticed the file size would have known something was wrong before anyone read the diff.

The fix: start from empty, read only .parts2/. Both halves matter. Starting from empty removes the append; reading only .parts2/ removes the stale files.

2.4 The newline the API eats

905a68e0:

ci(narrative): strip the API's trailing newline per part

The contents API appends one newline to every file it writes, which would insert
a newline at each chunk boundary. Strip exactly one per part so the assembled
file is byte-identical to the local source.

This is a subtle one, and it is the kind of defect that only shows up when you compare bytes rather than reading the file. The GitHub contents API appends a newline to every file it writes. If you write a document in ten parts, you get ten extra newlines — one at each boundary. The document still reads correctly. It is still valid Markdown. It is simply not the file you wrote.

The fix strips exactly one newline per part. "Exactly one" is the important phrase: strip more and you eat a real blank line, strip fewer and the boundary newline survives.

That fix was then superseded, because it was solving the problem at the wrong end. 3ab008f4:

ci(narrative): assembler overwrites from empty, parts boundary-safe

The API strips trailing whitespace per write, so parts are now split on
non-whitespace boundaries and the assembler writes the target from empty with a
single final newline.

And then dbcb6f39:

ci(narrative): assembler joins parts with a newline

The API strips trailing whitespace per write, so parts are split on line
boundaries and joined with a newline, which restores exactly what the strip
removed.

Read those two together and you have the whole problem in two sentences. The API does not append a newline; it strips trailing whitespace. So a part that ends with a newline loses it, and the join between two parts collapses. The fix is to split on line boundaries and join with a newline — the join puts back exactly what the strip removed.

The earlier commit (905a68e0) had the direction of the error backwards. It assumed the API added a newline; the API removed one. The commit message for 905a68e0 is therefore wrong about the cause, and the later commits correct it without saying so. That is a small thing, and it is exactly the kind of small thing the chronicle exists to record: a fix that works for the wrong reason, followed by a fix that works for the right one.

2.5 The trigger that fired on the sentinel

6191a9bc:

ci(narrative): assembler triggers on a dedicated sentinel file

The .parts2/ push trigger fired on every part commit and deleted the parts
directory after the first one. The trigger is now a single sentinel file
committed last, once every part is in place.

This is the same defect as 74ebe539, fixed a second time. The first fix was to make the workflow manual-dispatch-only. That worked, but it meant a human had to click a button, and the human was an agent, and the agent's way of clicking a button was to commit a file. So the trigger came back — but scoped to a single sentinel path rather than the whole directory.

The final workflow, as it stands at 77b72a1a, states the design in its header comment:

# TRIGGER: push of docs/app/narrative/.assemble-trigger ONLY, committed last
# once every part is in place.

And the assembly step:

for f in $(ls "$PARTS"/*.md | sort); do
  echo "appending $f"
  if [ "$first" -eq 0 ]; then
    printf '\n' >> /tmp/assembled.md
  fi
  first=0
  cat "$f" >> /tmp/assembled.md
done
printf '\n' >> /tmp/assembled.md
mv /tmp/assembled.md "$TARGET"
rm -rf "$PARTS"
rm -f docs/app/narrative/.assemble-trigger

Read that loop carefully. It writes to /tmp/assembled.md, not to the target. It moves the result into place only after the loop completes. It removes the parts directory and the sentinel only after the move. Every one of those orderings is a fix for a failure described in an earlier commit message.
