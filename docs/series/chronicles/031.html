The gate that was never built: tag monotonicity

2026-11-21 grounded 998 words
All installments RSS

Origin: grounded. This installment reports what the repository actually did in its window. Every figure in it was measured against the tree, and the chapter names the file or command it came from. Where it could not stand behind something, it says so in its own text rather than smoothing it over.

The previous instalment's §2 ended with a question it could not answer:

Part two §12 asked whether the repository has a check that VERSION is monotonic across its release tags. 48c241a1 cuts 3.1.2, which is higher than both 3.1.0 and 3.1.1, so the current state is monotonic. Whether a check now exists is a separate question this note does not answer, and the next instalment should.

This is the next instalment, and the answer is no.

3.1 What was searched

The search was for code, not for intent. A plan document that says a gate should exist is not a gate. A docstring that describes a rule is not a gate. The question is whether there is an executable check that would fail if the rule were broken.

Searched:

  • Every file under .github/workflows/ (18 workflows) for VERSION, git tag, refs/tags.
  • Every file under scripts/ for git tag, refs/tags, semver.
  • The whole tree for monotonic, tag_monoton, tag-monoton, version_monoton, semver.*monoton.
  • git log --all --grep='monoton' -i.

3.2 What was found

In the workflows, three references to VERSION and one to tags:

  • .github/workflows/ci.yml:254 — a comment: "VERSION, pyproject.toml and version.hpp each state the version and nothing compared them: on 2026-11-01 they read 4.0.0, 3.0.0 and 3.1.0." Followed by a step that runs python3 scripts/check_version_consistency.py.
  • .github/workflows/ci.yml:495 — print("stdlib-only import ok; api_version =", h.API_VERSION), an unrelated API version.
  • .github/workflows/controlz-desktop.yml:123-124 — tagName: controlz-v__VERSION__, a release-asset naming template.
  • .github/workflows/release.yml — the Ruby SDK release, which checks that a pushed tag matches the gem version.

In scripts/, one file: scripts/check_version_consistency.py.

In the whole tree, monotonic appears in 25 files, none of them a version check. They are monotonic clocks, monotonic counters, monotonic sequence numbers — mem20orcaz/concurrency.py, mem20kimiz/batch.py, mem20ircz/hub.py, and so on. The word is used, but never about tags.

In git log --all --grep='monoton' -i, one commit: 4d166d90, "Option C batch 6: traffic control, webhook network (17 tests)". Unrelated.

3.3 What check_version_consistency.py actually does

This is the closest thing in the repository to a version gate, and it is worth reading in full because its docstring states precisely what it does and does not cover.

"""Fail when the version is stated in more than one place and the places disagree.

mem20 states its version in three files:

  VERSION                              -- the release marker, authoritative
  pyproject.toml  [project] version    -- what `pip install .` records
  sdk/cpp/include/mem20/version.hpp    -- what the C++ SDK was built against

On 2026-11-01 these read 4.0.0, 3.0.0 and 3.1.0. Nothing compared them, so the
package metadata had been two minor releases behind the tree it described and
the SDK baseline one behind. This script is the comparison.

VERSION is authoritative because it is the file the release process writes and
the only one that is a single token with no surrounding syntax to parse.

Exit 0 when all three agree, 1 when they do not, 2 when a file is missing.
"""

Three files, compared for equality. That is the whole check. It answers the question "do these three files state the same version right now". It does not answer "is this version higher than the last one", and it does not look at tags at all.

The distinction matters because the defect the previous instalment described was not a disagreement between three files. It was a tag ordering: v3.1.1 (52ffe13d) is an ancestor of v3.1.0 (73343f68). A tag cut before the release it names. check_version_consistency.py would pass on that repository state, because all three files could agree on a version while the tag graph was still inverted.

3.4 The one place tags are compared

scripts/ops/scoreboard_signals.sh does compare branches against main:

ahead=$(git rev-list --count "${MAIN_REF}..${sha}" 2>/dev/null || echo "?")
if git merge-base --is-ancestor "${sha}" "${MAIN_REF}" 2>/dev/null; then
  st=MERGED; merged=$((merged+1))
else
  st=UNMERGED; unmerged=$((unmerged+1))
fi

That is a branch-merge check, not a tag-order check. It iterates git ls-remote --heads origin, which lists branches, not tags. It answers "is this branch merged into main", which is a different question from "is this tag's version higher than the previous tag's version".

And it is a reporting script, not a gate. It prints a scoreboard. It does not exit non-zero on a violation, and it is not invoked by any workflow.

3.5 The verdict

No tag-monotonicity gate exists. Not in CI, not in scripts/, not anywhere in the tree. The repository has:

  • a check that three files agree on a version string (check_version_consistency.py, wired into

ci.yml);

  • a check that a Ruby gem's tag matches its version.rb (release.yml, scoped to one SDK);
  • a reporting script that counts merged branches (scoreboard_signals.sh, not a gate).

None of these would fail if a tag were cut with a version lower than its predecessor. The defect the previous instalment documented — v3.1.1 before v3.1.0 — could recur tomorrow and nothing would say so.

What broke. A question was asked in a published document and left open, and the answer took a separate run to establish. That is not a failure of the repository; it is a failure of the previous instalment, which should have answered it rather than deferring it.

What we learned. "There is a check for versions" and "there is a check for tag order" are different claims, and a repository can have the first while lacking the second. The way to tell them apart is to read the check's docstring and see what it compares. check_version_consistency.py says exactly what it compares — three files, for equality — and that sentence is the answer.
