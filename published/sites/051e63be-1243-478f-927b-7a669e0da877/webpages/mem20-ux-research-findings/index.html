Six findings that should shape the next design pass

  • W1 · Silent 404 and a dead clone command (Critical). The README still tells users to git clone https://github.com/JaysonAIOnline/mem20.git — a URL that now returns 404. The very first command a new user runs fails.
  • W2 · Trust badges are broken links (Critical). The MIT-license and release badges point at the old org; both resolve to 404. In a product whose whole pitch is auditability, a broken provenance link is an especially expensive contradiction.
  • W3 · Four install paths, no decision help (High). The Quick Start lists source, Penguin Linux, systemd, and pip installs back-to-back with no "choose this if…" guidance.
  • W4 · pip install mem20 is not live (High). PyPI returns 404, yet pip appears in the Installation section. The fastest path for a Python dev is a dead end.
  • W5 · Undefined domain nouns create an early cliff (High). "Grounded vs simulated", "promotion", and "ledger" name the core concept but are explained only later in the README.
  • W6 · The 0.000 adversarial hit rate is the right disclosure, but the wrong shape (Medium). Honest, but presented without the "used adversarially only" framing, it reads to a skimming engineer as "the retrieval is broken".
The headline. The product's differentiator is provable, auditable memory — but the first thirty seconds of the developer experience are currently un-audited: a dead clone URL, dead provenance badges, and a pip command that 404s. Fixing those three costs almost nothing and removes the contradiction that undermines the entire positioning.

1 Scope, Method & Evidence

This refresh re-ran a lightweight, evidence-first usability pass focused on the first-run developer experience of the canonical repository and its install documentation. It is a documentation-and-interface audit triangulated with reproducible probes, not a recruited-participant study (see Limitations for sample and confidence caveats).

Methods used

  • Interface inventory — enumerate every surface a new user meets, in order.
  • Heuristic walkthrough — evaluate each surface against time-to-first-success.
  • Link & path integrity probes — HTTP HEAD/GET every repo-dependent URL and the git protocol endpoint.
  • Content analysis — README quick-start, install matrix, and technical-claim sections.
  • Journey mapping — model the ideal path and mark the actual friction points.

Research questions

  • Can a new user reach a working memory server from the canonical repo without hitting a dead end?
  • Do the repo's own trust signals (license, release, provenance) resolve?
  • Is the install decision unambiguous for each of the three target segments?
  • Does the core concept survive a five-minute skim, or does it cliff?

3 Interface Inventory

The first-run surface of mem20 is a short, ordered sequence. Each item below is a place where a design decision determines whether the user converts to a running server.

  • S1 · Discovery — how the repo is found: HN/Reddit post, directory listing, or a blog link.
  • S2 · Repo landing — README header, status badges, one-line positioning, monorepo warning.
  • S3 · Concept — the grounded/simulated partition, promotion, and ledger — the product's whole reason to exist.
  • S4 · Capability scan — the 26-domain / 257-tool table that establishes breadth.
  • S5 · Install decision — source, Penguin Linux, systemd, or pip.
  • S6 · First run — MEM20_STORE_PATH + stdio server, or the HTTP health endpoint.
  • S7 · Connect — wire the server into an MCP host (Hermes, Claude Code, Cursor).
  • S8 · Assemble the bundle — the full SDK/platform corpus (293 subsystems) and where a newcomer should look first.

6 Usability Findings

Each finding pairs an observed defect with its user impact and a minimum-cost fix. Quoted README lines are verbatim from the canonical repo at commit c274404.

W1 · The first command in the README fails

CriticalSeverity: breaks first run · Effort: 1 line

Quick Start instructs users to clone the legacy org. The old repo returns 404 and the git endpoint rejects the request, so a new user's very first action errors out — before they ever experience the product.

git clone https://github.com/JaysonAIOnline/mem20.gitREADME.md · Quick Start → Install from source (line 186) and Penguin Linux (line 203)
Impact: Highest-severity, lowest-cost defect in the release. A 404 on step one converts a curious evaluator into a churned visitor, and it directly contradicts a product whose thesis is verifiable provenance.

W2 · Trust badges link to a dead repository

CriticalSeverity: breaks trust · Effort: 2 lines

The MIT-license badge and the release badge both resolve against the legacy org and return 404. On an auditable memory product, a broken license link is the most expensive possible broken link.

Impact: Priya's compliance review opens on a dead provenance link. Fix before any launch post goes out.

W3 · Four install paths, no decision aid

HighSeverity: slows to first value · Effort: low

Quick Start presents source, Penguin Linux, systemd, and (later) pip consecutively without a "choose this if…" table. The user must read all four to discover which one is theirs.

Impact: Every segment (Devon, Sam, Priya) pays an avoidable decision cost. A 3-row chooser table removes it entirely.

W4 · pip install mem20 is offered but unavailable

HighSeverity: dead end · Effort: label now, publish later

The Installation section documents a pip channel; PyPI returns 404. The fastest path for a Python developer is therefore a dead end unless they fall back to source.

Impact: Re-frame as "pip channel — coming" until the package is live, and point pip-first users at the source path meanwhile.

W5 · The core concept cliffs after one paragraph

HighSeverity: comprehension · Effort: low

The README opens by naming "grounded", "simulated", "promotion", and the append-only ledger. The definitions and the five hard invariants appear only much later, so a skimming reader loses the thread exactly where the differentiator is introduced.

Impact: Move the two-line partition definition to first mention; keep the invariant list where it is for depth.

W6 · The adversarial 0.000 needs a frame, not just a number

MediumSeverity: misread risk · Effort: low

Disclosing an adversarial hit rate of 0.000 is the honest move — but shown without the "this measures resistance under adversarial conditions" framing, it can read to a scanning engineer as "retrieval is broken". Keep the number; add the frame.

Impact: Preserves honesty while preventing the most likely misreading of the benchmark table.

W7 · First-run prerequisites are easy to miss

MediumSeverity: silent failure · Effort: low

Useful operation depends on a store path and an LLM bearer token (NVAPI_KEY / NVIDIA_API_KEY / MEM20_LLM_API_KEY). These live in the configuration table, well below the run recipe, so a user can start the server and still get nothing useful back.

Impact: Pull the two required settings up beside the run command; keep the full table for reference.

W8 · The monorepo needs an orientation aid

MediumSeverity: overwhelm · Effort: low

293 mem20*z subsystems plus the full platform tree make the repository impressive but disorienting. The "Repository layout" section explains it, but only after the tool table.

Impact: A four-item "start here" list at the top of the tree — core memory engine, MCP server, cognitive layer, one representative subsystem — turns breadth from intimidating into credible.

8 Success Metrics

How we will know these changes worked. Baselines for the first-run metrics are currently unmeasured — instrument them before the launch window.

Quantitative

  • Link integrity: 100% of repo-dependent links in README/site return HTTP 200 (baseline: 9 stale references).
  • Time to first green health check: median ≤ 10 min from clone (baseline: unmeasured).
  • Install-path selection errors: → 0 after the chooser table ships.
  • pip channel: published and installable (≥1 PyPI release).
  • Stars / clones: baseline 0 — track delta from launch, not absolute.

Qualitative

  • Evaluators can articulate the grounded/simulated split after a 2-minute skim.
  • No reviewer reports a broken link in the first-run path.
  • The adversarial metric is understood as a resistance measure, not a failure.
  • Support/questions trend toward advanced topics, not "install didn't work".
Measurement plan: re-run the §1 evidence table at release cut; log time-to-first-health in the launch-day dashboard; re-survey the first ten inbound questions for install-path confusion.

9 Limitations & Next-Step Research

Honesty note. This revision is a documentation-and-interface audit triangulated with reproducible link probes. The three personas are hypothesis personas synthesised from the positioning brief, not recruited participants. Treat findings W1–W8 as high-confidence (they are mechanically verifiable) and the persona detail as directional.

Recommended next research

  • N1 · Moderated first-run test — five developers, think-aloud, clone → green health, scored on time-to-first-success. Validates R1–R4 in one session.
  • N2 · Comprehension recall — after a two-minute skim, can participants explain grounded vs simulated? Tests R5.
  • N3 · Evaluator trust probe — does a clean audit story survive contact with a compliance-minded reader? Tests the auditability wedge.
  • N4 · Accessibility pass — contrast, keyboard order, and screen-reader traversal of the README-to-docs path (WCAG 2.2 AA).

Repo-state caveats carried forward

  • The canonical repo is public (MIT, main) but shows zero stars/forks — a cold start; treat any launch-time numbers as a delta from zero.
  • The marketed website did not respond during data collection; do not send launch traffic to it until confirmed.
  • pip install mem20 is not yet available; the source path is the only verified install route today.
