02Method & observatory

Desk research: what was screened, how outcomes were framed, and the limits of the approach.

Design

Qualitative desk research in three passes — (a) artefact audit of the canonical repo and the live server surface, (b) category scan of adjacent OSS memory layers and MCP tooling, (c) outcome framing using Ulwick's outcome-driven-innovation template.

  • 11 repositories screened
  • 34 MCP memory/knowledge servers catalogued
  • 6 OSS memory layers reviewed in depth
  • 8 desired-outcome statements framed

Scoring

Each outcome carries a declared importance and satisfaction score (1–10); the opportunity score is computed, never asserted:

opportunity = importance + max(importance − satisfaction, 0)

Scores of 10+ are underserved. 5 of 8 outcomes clear that bar; their mean is 14.4, against a P0 go-condition of ≥ 12.0.

P0 adoption condition: MET — 5 underserved outcomes, mean 14.4.

Limitations (stated, not hidden)

  • No primary participants. Importance/satisfaction are analyst-declared inputs, not survey responses. A 13-item outcome survey is provided (§07) to validate them with real users.
  • No live telemetry. Zero releases and a disabled issue tracker mean there is no usage data to triangulate against; findings rest on artefact and category analysis.
  • Category is young. MCP standardised in late 2024; adjacent OSS memory layers are mostly pre-1.0, so "satisfaction with current solutions" reflects an immature baseline.

03Personas

Four archetypes derived from the category scan, each with a share of the addressable population (computed by largest-remainder from declared weights) and a computed opportunity score.

Builderopp 16.4 · 30%

Agent Builder — indie / small team
Context
Ships an LLM agent that must remember across sessions; Linux, terminal-first; self-hosts.
Goal
A memory substrate her agent can trust — recall that is faithful, and a line between what was observed and what was generated.
Behaviour
Discovers via MCP catalogs and GitHub; evaluates by reading the tool list and running one round-trip test.
Tech
High — Python/Go, MCP client config, containers.
Pain points
  • Recall degrades across sessions with home-grown vector hacks.
  • Simulated (hallucinated) and grounded memory are indistinguishable in most layers.
  • 257 tools present a discovery wall — no ranked "start here" path.
Evidence

The live surface exposes the trust boundary as first-class tooling — memory_audit_contamination, memory_set_epistemic_status, memory_promote, memory_quarantine_simulated — the exact primitives this persona is missing elsewhere.

"I need to know whether it remembers what actually happened, or what it made up."

Platform Engineeropp 11.5 · 24%

Platform / Infra Engineer — mid to large org
Context
Operates shared services for many agent teams; owns governance, authz, observability.
Goal
A memory service that is governable: namespaces, access boundaries, cost/latency control, audit trail.
Behaviour
Evaluates against existing identity and policy; wants a service, not a library.
Tech
High — k8s, IaC, IAM, observability stacks.
Pain points
  • No standard catalog or per-team isolation around memory stores.
  • Agent connections bypass existing identity providers — shadow connections.
  • Runaway token/latency cost from unbounded recall loops.
Evidence

Primitives exist — memory_namespace_create, memory_namespace_list, memory_scan_pii, memory_self_audit, corrigibility_capability_tier, braid_prove — but their governance framing is the opportunity.

"If I can't isolate and audit it per team, I can't put it in the platform."

Domain Integratoropp 15.1 · 22%

Integrator — design / 3D / data pipelines
Context
Connects agents to domain tools (Blender, Unity, cloud storage, databases, web scraping).
Goal
Wire domain capability into an agent without writing the plumbing; keep the domain artefacts alongside the memory.
Behaviour
Scans the tool directory for their domain; tries one end-to-end task.
Tech
Medium–high — scripting, REST, some 3D/data tooling.
Pain points
  • Domain tools and memory live in different systems; context is lost between them.
  • Integrations are undocumented or assume the paid/external app is present.
  • No template to add a new integration cleanly.
Evidence

The 257-tool surface already spans blender_* (7), unity_* (5), cloudstorage_* (8), db_* (11), scrape_* (8), plus memory_ingest_* for image / audio / pdf / code.

"I want the agent to remember the model, not just the conversation about it."

Memory Operatoropp 14.2 · 24%

Research / Knowledge Operator — individual
Context
Personal knowledge and research workflows; cares about privacy and local data.
Goal
Capture, curate and recall a private knowledge base that compounds over time.
Behaviour
Adopts through a desktop surface; wants to see and curate what the agent remembers.
Tech
Medium — comfortable with a CLI or service, not with config files.
Pain points
  • Memory is invisible — no way to see, pin, or correct what was stored.
  • Privacy anxiety: does memory leave the machine?
  • No notion of decay, importance, or contradiction in what is kept.
Evidence

Memory lifecycle tools are present — memory_pin_block, memory_decay, memory_contradict, memory_timeline, memory_feedback, memory_scan_pii, store path via env MEM20_STORE_PATH (local by default).

"Show me what it remembers, and let me fix it."

06Findings

87 findings distilled to the ten that drive design.

  1. The differentiator is not storage — it is separation of grounded from simulated memory.
  2. Trust boundary primitives are unreachable without a visual surface.
  3. 257 tools are a discovery wall; the surface needs a ranked, role-aware entry point.
  4. Zero releases and disabled issues remove all inbound feedback channels.
  5. Setup works but the documented path assumes an isolated environment.
  6. The store is local-first by default (MEM20_STORE_PATH), which privacy-sensitive users value.
  7. Memory lifecycle tools (decay, pin, contradict, feedback) are rich but invisible.
  8. Adoption is developer-first and self-service; evaluation is one round trip.
  9. Governance demand (namespaces, isolation, audit) is present and unmet.
  10. Interoperability is table stakes — users already have an MCP client.

07Desired-outcome survey instrument

The 13-item instrument to replace the declared inputs with real responses.

Each item is asked twice — importance and satisfaction — on a 10-point scale. Target n ≥ 100 per archetype. Opportunity is then recomputed with the same formula and compared to this baseline.

Recall & trust (5)
  • Faithful recall across sessions
  • Distinguish grounded from simulated
  • Correct or pin a stored memory
  • See how memory changed over time
  • Confidence signal on a recall
Operate (4)
  • Find the right tool quickly (257)
  • Isolate memory per team/namespace
  • Scan for PII before sharing
  • Audit what the agent stored
Adopt & run (4)
  • Zero-friction setup
  • Work with an existing MCP client
  • Bound cost / latency of recall
  • Keep data local / self-hosted
Instrument total: 13 items × 2 scales = 26 data points per respondent; analysis returns a per-item opportunity score and a segment comparison.
