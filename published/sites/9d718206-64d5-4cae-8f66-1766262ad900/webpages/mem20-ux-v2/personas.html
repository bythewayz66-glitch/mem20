UX research · personas · v2 · 2026-10-14

Personas re-derived from the current segments

Four personas cover the verified audience for mem20 — an MIT-licensed Python MCP server for auditable agent memory, 257 tools across 26 domains. The v1 personas were written around a pip install world. That world no longer exists: there is no published package, so the install path is a clone. Each persona below therefore carries a ranked onboarding friction list scored against the install path that actually exists today.

Evidence base. Personas are synthesized from the program's segment definition, the verified product surfaces (repo README, landing-site content) and the recorded install blocker. They are segmented personas, not interview-validated personas — no user interviews were conducted for this refresh, and none are claimed. Where a persona assertion is an inference, it is marked. This is stated up front because a persona deck that hides its evidence basis is worse than no persona deck.

Her success criterion is a teammate recreating her setup from the same instructions without asking her a question.

SYNTHWhat the four personas agree on

Convergent finding 1

A dead install command ends the evaluation

Three of four personas hit the 404 in their first two minutes, and P4 cannot start at all without P1. Install reliability is not a documentation task — it is the top of the funnel.

Convergent finding 2

The wedge needs a surface, not a paragraph

All four describe mem20's differentiator as provable memory. None of them can see it today, because the audit story lives in a terminal. The desktop app's job is to make the partition, the promotion gate and the ledger navigable.

Convergent finding 3

Disclosed weakness is survivable; discovered weakness is fatal

Kai, Daniel and Sofia all independently reach the adversarial 0.000 row and the missing standard benchmark. Keeping both visible — as the program guardrails already require — converts the weakest fact into evidence of rigour.

Recommendation carried into the flows and designs: make the desktop app's default landing surface the audit ledger with the partition view one click away, and make the first-run experience end in a verified empty-state ledger rather than a features tour. That single decision serves P4 directly, gives P2 a committee artefact, and gives P1 a "something printed, it works" verification moment.
