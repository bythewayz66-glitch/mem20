The onboarding flow — rebuilt around the install path that exists

This is the single most important flow in the deck, because it is the one that changed. If a user cannot get mem20 running, no amount of good inspector design matters. The v1 flow assumed a one-line package install. The verified reality is a three-step source install with no PyPI package — and a currently dead canonical repo. Every step below is tagged with the gate state checked in this session.

F1Target first-run flow — what the desktop app should do instead

The design recommendation is to collapse steps 1–4 into a guided first run that ends in something printing. P1 needs a verification moment; P4 needs a non-terminal entry point.

A
Detect environment
App checks Python ≥ 3.11, git, and available MCP clients. Prints what it found, not a spinner.
→
B
Guided source install
Shows the exact clone + editable-install commands with the canonical repo URL, and a copy button per line.
→
C
MCP client wiring
Writes / shows the mcpServers entry for the detected client instead of asking the user to author JSON.
→
D
Smoke test
Runs one grounded write + read, shows the pass/fail inline. This is the "it works" moment.
→
E
Open the ledger
First run ends on the audit ledger in an explicit empty state — not a features tour.
Design intent: the flow ends where the product's differentiator begins. Landing the user on the ledger (with the partition view one click away) makes the wedge the first thing they see rather than a documented property they have to go looking for.

F2Core task flow — "prove why the agent believes X" (P2 / P4)

1
Open a memory record
Search or drill from the ledger into a single record.
→
2
Read its origin tag
Human-readable provenance line: source, session, timestamp.
→
3
See its partition
Grounded or simulated — stated unambiguously, colour-coded and labelled (never colour-only).
→
4
Trace the promotion
If it crossed from simulated to grounded, show the promotion event and the evidence attached to it.
→
5
Export the evidence pack
Selected records + their ledger entries, exportable for a committee or an incident file.
Honesty constraint on step 4: promotion is presented as "evidence-based with an append-only audit trail". It is never described as tamper-proof or provably secure, and the known self-attestation limitation of the promotion gate is surfaced in the spec rather than hidden in a tooltip.
